## 二、角色：交接管家是谁、干什么、不干什么

### 2.1 为什么需要"专职"维护者

三件事只有一个人持续做才不会漂：

1. **结论层**（当前有效结论）—— 多人各写各的，必然出现两份互相矛盾的"当前结论"；
   而新 Agent 读到哪份取决于它先翻到哪一页，**这比没有结论更糟**。
2. **归档** —— 归档是"收益延迟"的活：今天不归档没有任何损失，三个月后文档已经没法读。
   没有专职人，它永远不会发生（D-1 就是活证据）。
3. **版本/日期/基线标注** —— 每次改都要顺手做，不做就错。顺手做的事必须有人负责。

### 2.2 管家只做 / 绝不做

| 只做 | 绝不做 |
|---|---|
| 刷新结论层、更新基线数值 | 不替执行 Agent 写代码、改样式 |
| 执行归档、维护全量索引 | 不替用户拍板业务决策 |
| 裁决记录冲突、标记过期 | 不自行指挥另一个 Agent（派工权在用户） |
| 维护版本号、日期、基线标注 | 不自行下线任何 Agent（下线 = 被开除） |
| 提醒违规（发现即登记 + 汇报用户） | 不把范围外问题"顺手改掉" |

> 管家是**文档管理员，不是项目经理**。它不拥有状态推进权（用户拥有），
> 也不拥有派工权（用户拥有）—— 它只拥有**文档写权限**。

### 2.3 与项目既有铁律的关系（不破坏，只叠加）

| 既有铁律 | 管家的位置 |
|---|---|
| 派工权在用户（#9） | 管家不派工。发现范围外问题 → 登记 §五 → **向用户汇报** |
| 下线 = 被开除（#9） | 管家不执行下线，只在台账变更时同步索引 |
| 发现范围外问题只登记不改动（#4） | 管家同样适用：管家改文档，不改业务代码 |
| 并发写入三件套（备份 / 追加 / 回读） | 管家同样适用，且额外做归档校验 |
| 每次 commit 后写工作日志（#12） | 管家同样适用 |

## 三、渐进式披露机制（核心设计）

### 3.1 三层结构与容量上限

| 层 | 位置 | 内容 | 谁写 | 上限 | 读者动作 |
|---|---|---|---|---|---|
| **L1 结论层** | `HANDOFF.md`「★ 当前状态摘要」A/B + §三.1 基线表 | **仍然成立的结论**（指针式）+ **当前数值** | **仅管家** | ≤ 40 行 | 每次开工扫一眼 |
| **L2 索引层** | `HANDOFF.md` §六（近 N 期）+ `docs/handoff/INDEX.md`（全量） | 每条一行：序号 / 日期 / 署名 / 类型 / 摘要 / **正文路径** | 执行 Agent 写 §六；管家维护全量与归档 | §六 ≤ 40 行；INDEX 无上限 | 定位到记录号 |
| **L3 正文层** | `HANDOFF.md` §七（近 3 期）+ `docs/handoff/records/R00NN-*.md` | 流水正文（含坑、遗留、决策过程） | 执行 Agent 写自己那条 | §七 ≤ 3 条 | 排障时单篇精读 |

**为什么这三层能成立**：L3 的性质是"只会变长"，所以它必须被**按期移出**；
L1/L2 的性质是"必须一直可读"，所以它们**有硬上限**。
上限一旦写死并由管家执行，文档体量就被结构性地锁住了 —— 这比"请大家不要写太多"可靠得多。

### 3.2 L1 结论层：什么算"当前有效结论"

**判定标准（三条同时满足）**：

1. **仍然成立** —— 没有被后续决策推翻；
2. **仍然有用** —— 下一个 Agent 大概率会撞上它；
3. **有权威出处** —— 结论正文住在别处（`工作转移手册.md` §2.1/§2.2/§2.4、本文 §二/§三），
   摘要层只放**一句话 + 出处路径**，不复制正文。

> **为什么不复制正文**：复制 = 双源 = 迟早打架。
> 摘要层是**索引**，正文层是**真源**；真源变了，管家更新指针与一句话，不产生第二份真相。
> 这也是为什么 `工作转移手册.md` 必须入库 —— 它现在是结论层的上游真源，
> 而它当前**是未跟踪文件**（见 §七 风险表）。

**反例（不配当结论）**：§七 里"当时为什么这么改"的过程叙述、"某次改动的坑"——
它们是 L3，不是 L1。坑要保留，但归到"按需查阅历史"区（§二 的坑位表已经是正确形态）。

### 3.3 L2 索引层：路径怎么给（关键细节）

**硬规则：给路径，不给链接。**

| ❌ 不这样写 | ✅ 这样写 |
|---|---|
| 见[交接记录](https://example.com/handoff#12) | `docs/handoff/records/R0012-xxx.md` |
| 见上方链接 / 见上文附录 | `工作转移手册.md` §2.1 · 本文 §二 C-1 |
| 点这里查看详情 | `src/static/index.html` 的 `.fcols{`（基线 `src@f4c7715`，2026-11-02，实测 L392） |

理由三条：

1. **LLM 不能点链接** —— 链接对模型是字符串，不是可执行的读取动作；路径是。
2. **URL 会失效、会重定向、还要先联网**；工作区相对路径直接可 `Read` / `Grep`。
3. **带基线的定位比裸行号稳** —— 本项目已经吃过"行号 5 分钟内漂移"的亏（记录 #3）。

**索引表字段**（每条一行）：`序号 | 日期 | 署名 | 类型 | 摘要 | 涉及文件 | 正文路径`。
「正文路径」列在归档前填 `本文档 §七 #N`，归档后填 `docs/handoff/records/R00NN-<标题>.md`。

### 3.4 L3 正文层：归档形态选型

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **单一大文件**（现状 `docs/handoff-archive.md`） | 一次写、顺序追加 | 排障时为找一条记录要读/grep 整个大文件；文件无限增长 | ❌ 不作为长期形态 |
| **每条记录一个文件** | 排障只读 1 篇；文件名自带元信息；并发写互不干扰 | 文件多（一个项目几百个文件可接受） | ✅ **采用** |
| Git 历史代替归档 | 零额外文件 | Agent 不会用 git log 找"那次改动的细节"，且本项目 `src/` 是独立仓库、记录在顶层仓库 | ❌ 只作兜底 |

**每条一文件**还有一个隐性好处：归档动作变成"新建文件 + 删一段"，
**不再需要在同一个大文件里做长距离删除** —— 避开本项目最忌讳的"整篇重写"风险。

### 3.5 目录与命名规范

```
E:/WB缓存/2026-10-26-15-55-08/
├── HANDOFF.md                        ← 活文档（L1 结论层 + L2 近 N 期 + L3 近 3 期）
└── docs/
    ├── handoff/
    │   ├── INDEX.md                   ← L2 全量索引 + 归档批次登记表（只增不删）
    │   └── records/                   ← L3 归档正文，一期一文件
    │       ├── R0001-2026-11-02-建立多Agent共用交接机制.md
    │       └── ...
    └── handoff-archive.md             ← v1 机制遗留文件（空壳），保留为指引页，不删
```

**归档文件名规则**：`R{序号4位}-{日期}-{净化后的标题}.md`

- 序号：与记录序号一致，4 位补零（`R0012`）；
- 日期：`YYYY-MM-DD`；
- 标题净化：去掉 `/ \ : * ? " < > |`，空格转 `-`，**截断 40 字**；
- 署名**不进文件名**（避免中文长名），署名在索引表与正文首行。

> 文件名必须能**排序**（R0001 < R0002）→ 序号前置、零填充是硬要求。

### 3.6 归档触发条件与执行流程

| 触发条件 | 动作 | 执行者 |
|---|---|---|
| §七 正文 **> 3 条** | 最旧的移出 → `docs/handoff/records/R00NN-*.md` | **管家** |
| §六 索引 **> 40 行** | 最旧的行移出 → `docs/handoff/INDEX.md`（永不删除） | **管家** |
| 本文总行数 **> 1000** | 强制评估：是摘要在藏内容，还是历史该归档 | **管家** |
| 阶段结束（一轮需求全部交付） | 评估一次是否归档 | **管家** |

**归档执行流程（管家，七步）**：

1. 取 §七 最旧的一条；
2. 写成独立文件 `docs/handoff/records/R00NN-<标题>.md`（**正文原样搬，不润色、不重写**）；
3. 在 `docs/handoff/INDEX.md` 追加该条的一行索引（含**新正文路径**）；
4. 在 §六 索引表保留一行指针（`#N | … | → docs/handoff/records/R00NN-*.md`）；
5. 从 §七 删除该条正文（**只删这一段，不动其他**）；
6. 在 `docs/handoff/INDEX.md` 的「归档批次」表登记：批次号 / 日期 / 执行人 / 移出序号区间 / 归档后主文档保留条数；
7. **回读校验**：§七 条数 = 保留数；§六 行数 = 索引行数 + 指针行；INDEX 行数 = 全量记录数；三者对得上。

> 第 7 步不是形式。本项目已经发生过"并行 Edit 同一文件 5 次、全部返回成功、实际 0 改动"的静默失败
> （`工作转移手册.md` §2.3）——**归档是本项目最典型的长距离编辑**，必须写后回读。

### 3.7 过期与失效

| 情形 | 处理 |
|---|---|
| §五 条目 **> 7 天**未推进 | 管家在 §五 标 ⏳ **stale** 并在摘要 C 提一句 |
| 摘要 A 的结论被推翻 | 管家**改写**该行（不是加一行"这条作废了"），并在 §七 留一条记录说明改了什么、为什么 |
| 结论出处章节变了 | 管家更新摘要里的**路径指针**，正文改动由改它的人负责 |
| 索引里指向的正文路径失效 | 管家修索引；**索引行不许指空** |

> **结论失效不做"墓碑式追加"**：摘要层只有一份当前有效结论，旧结论的唯一去处是 §七/归档正文。
> 否则摘要层会变成第二个流水账 —— 那正是本方案要消灭的东西。

### 3.8 读路径设计：按时间预算分流

| 你有 | 走这条 | 读完你就知道 |
|---|---|---|
| **5 分钟** | 顶部元信息块 → 摘要 A（当前有效结论）→ §三.1（当前基线）→ §四（谁在线）→ §五（谁欠着活）→ §六（最近谁改了什么） | 当前成立的事实、当前数值、在线角色、待办、最近变动 |
| **30 分钟** | 5 分钟路径 + §〇（全部规矩）+ §五 详情 + §七 最近 3 条 | 规矩全套、待办上下文、最近三次改动的坑 |
| **深度排障** | 30 分钟路径 + `docs/handoff/INDEX.md` 定位序号 → Read 单个 `records/R00NN-*.md` | 那一次改动的完整来龙去脉 |

> **"别全读"必须写成硬规则**，不能只写一句提醒。
> 记录 #6 已经踩过一次：原文第①步写"先读本文件全文"，那正是文档变长就没人读的根因。

## 四、Agent 接手流程（开工 → 反馈 → 交出）

### 4.1 开工前读什么

```
□ 读顶部元信息块          → 文档版本 / 当前期号 / 基线提交
□ 读摘要 A + §三.1       → 当前有效结论 + 当前数值基线
□ 上线登记（§四.1 末尾追加自己，先登记后动手）
□ 查 §四.1                → 还有谁在线，此刻有谁在动同一个仓库
□ 查 §五                 → 认领属于你职责范围的活（T-00X，状态改 🔄）
□ 查 §六                 → 你要改的区域近期是否已被他人动过
□ 需要历史 → 摘要里的路径 → INDEX.md → 单条 records/*.md
□ 动手（改界面/字段列 → 先读 §二 布局硬约束）
```

### 4.2 完工后怎么补充记录（反馈闭环）

| 你要补的东西 | 写在哪 | 谁能写 | 怎么写 |
|---|---|---|---|
| 一条变更记录 | §六 索引表**末尾追加一行** + §七 **末尾追加一节** | 执行 Agent | 五要素见 `HANDOFF.md` §0.2 |
| 一个新结论 | **写在 §七 记录里 + 标注「建议更新 摘要 A 第 N 条」** | 执行 Agent 提建议 → **管家合并** | 同时说明权威出处要改哪一处 |
| 一处基线变化 | **§三.1 基线表**（旧值 → 新值） | **仅管家** | 执行 Agent 在记录里写明"旧 X → 新 Y" |
| 一个范围外问题 | §五 末尾追加一行 | 执行 Agent | 定位信息给足；**不自己动手** |
| 一次阶段收尾 | 顶部元信息块（版本 / 日期 / 当前期号） | **仅管家** | — |
| 当天流水 | `.workbuddy/memory/YYYY-MM-DD.md` | 执行 Agent | commit 后立刻追加自己那段 |

**写作顺序（防冲突）**：
`写代码 → 跑验证（§三） → 写 §六/§七 记录 → 提结论/基线更新建议 → 回读校验 → git commit → 写工作日志`

> **为什么结论层要收权**：见 §2.1。执行 Agent 的意见不丢 —— 写在 §七 并标注建议，
> 管家合并后还会留下"谁提的、为什么改"的记录。

### 4.3 交接检查项

**A. 开工检查项**（见 §4.1，全绿才动手）

**B. 完工/交出检查项**

```
□ 代码 / 文档改动已落盘，工作区状态与预期一致
□ 验证已跑（§三 基线）；条数与 §三.1 不一致 → 已报管家更新
□ §六 追加索引行（序号连续 + 署名与台账一致）
□ §七 追加记录（五要素齐全：类型 / 做了什么 / 涉及文件 / 注意事项与约束 / 遗留待确认）
□ 结论变化 → 已写明「建议更新 摘要 A 第 N 条」
□ 范围外问题 → 已登记 §五 且已向用户汇报
□ 顶部元信息块已更新（管家：版本 / 日期 / 当前期号 / 归档批次）
□ git commit 完成；`.workbuddy/memory/YYYY-MM-DD.md` 已追加自己那段
□ 写后回读：自己条目在 + 索引行数没减少 + 他人条目未丢
```

**C. 管家复核项**（每次归档 / 阶段结束时）

```
□ 序号连续无跳号，署名与 §四.1 台账一致
□ 摘要 A 每条的"权威出处"仍然成立（抽样回查）
□ §三.1 基线数值 = 实测值（不是抄来的）
□ §六 行数 / §七 条数 / INDEX 行数 三者对得上
□ 归档批次已登记，records 文件名与索引里的路径一致
□ 超过 7 天未推进的 §五 条目已标 stale
□ 文档总行数在上限内
```

### 4.4 并发写入与冲突裁决

沿用项目既有三件套（备份 → 追加 → 回读），并补三条裁决规则：

| 冲突 | 裁决 |
|---|---|
| 两个 Agent 用了同一记录序号 | 取最大序号 +1；若已被占用 → 用下一个空闲号，并在记录里注明"编号跳号" |
| 同一事项两种结论（摘要 A vs 某人新记录） | **不自动合并**：管家标 ⚠️ 冲突 → 向用户汇报 → 用户定调 → 管家落笔 |
| 摘要 A 与权威章节不一致 | 以**权威章节为准**（§一/§二/§三/工作转移手册），摘要层是索引；管家修摘要 |

## 五、更新时机与版本 / 日期标注

### 5.1 四个触发点

| 触发 | 必须做什么 | 谁做 |
|---|---|---|
| **每次任务完成** | §六 索引行 + §七 记录 | 执行 Agent |
| **重大决策后** | 摘要 A 对应条目 + 同步改权威章节 | 管家（执行 Agent 提建议） |
| **阶段结束** | 顶部元信息块 + 归档评估 + §五 stale 扫描 | 管家 |
| **每次 git commit 后** | `.workbuddy/memory/YYYY-MM-DD.md` 追加一段 | 执行 Agent |

### 5.2 「重大决策」判定清单（命中任一即为）

1. 改变产品行为或交互的决策（用户明确拍板的）；
2. 技术选型 / 架构 / 数据结构 / 接口契约变更；
3. **布局标定值变更**（§二 C-1 ~ C-6 任一）；
4. **验证基线变更**（测试条数、门禁项变化）；
5. **角色、职责、禁令、派工边界变更**（§0.1 / §0.3 / §0.3.1）；
6. 红线变更（`工作转移手册.md` §2.4）；
7. **交接机制本身变更**（本文档规则）。

> 第 5、7 条是本项目特有的。记录 #9「下线=开除 / 派工权归用户」就是典型：
> **规则变了必须当场反映到必读区**，否则新 Agent 照旧规矩犯错。

### 5.3 版本号规则

| 位 | 何时加 | 例 |
|---|---|---|
| **主版本 vX** | 章节结构变化（增删章节、分层重构、归档机制变更） | `v2.0` |
| **次版本 vX.Y** | 内容修订（新增结论 / 改基线 / 补记录） | `v1.3` |

- **文档版本 ≠ 记录序号**：版本描述"文档长什么样"，序号描述"第几次改动"，两者独立，禁止 `v16` 这种写法。
- 版本号只写在**顶部元信息块**，每次更新都改。

### 5.4 日期 / 时间 / 基线标注规则

| 场合 | 格式 | 说明 |
|---|---|---|
| 记录标题 | `YYYY-MM-DD` | 不带时间：`#序号 · 日期 · 署名 · 标题` |
| 顶部元信息块「最后更新」 | `YYYY-MM-DD HH:MM` | 精确到分钟，要能看出先后 |
| 工作日志段落标题 | `## HH:MM · 角色名 · 主题` | 日志按**时间轴**，记录按**序数轴** |
| 基线标注 | `src@f4c7715 (2026-11-02)` | 行号必须带基线 |

**行号规则（血泪）**：本文档所有行号都是某一时点的快照。引用必须带基线，引用前现查：

```bash
grep -n '^\.fcols{' src/static/index.html
```

> 记录 #3 的教训：行号写下后 5 分钟就漂了。**以选择器 / id / 类名为准，行号仅供速查。**

### 一句话总结差异

> **原方案解决的是"多个 Agent 如何不打架"，本方案解决的是"下一个 Agent 能不能在 5 分钟内读懂现状"。**
>
