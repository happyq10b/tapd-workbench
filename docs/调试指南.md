## 零、先回答那个问题：改代码在哪改？

### 结论：**改本地 `src/`，不要直接改服务器。**

服务器上确实有 vim/nano，文件也是可写的，但**直接改服务器有三个具体的坑**：

| 坑 | 后果 |
|---|---|
| `sync.sh` 是单向覆盖 | 你在服务器改的内容，下次同步被本地版本**静默覆盖，直接没了** |
| 服务器没有 git | 改错了没法回滚，线上就是事故现场 |
| 改的就是生产 | 没有测试环节，改崩了直接影响所有人用 |

**但现在不用怕了**——我已经加了保护机制：

- `sync.sh` 每次执行前会比对本地与服务器的 `app.py` 校验值，**不一致就拦下来问你**，不会闷头覆盖
- 万一你已经在服务器上改了，`./sync.sh --pull` 可以把改动完整拉回本地并自动提交 git

所以：**改本地 → 推上去**是主流程；**服务器上临时改了**也有兜底路径。

## 〇、交付流程（先看这个）

代码变更**必须**先在本地完成并通过验证，再由你手动触发同步：

```bash
# 阶段一：本地执行与验证（必做）
cd ops && python verify.py

# 阶段二：手动触发热同步（你亲自执行）
cd ops && ./sync.sh --dev      # 推到开发环境
cd ops && ./sync.sh --prod     # 推到生产环境
```

`sync.sh` 内置**强制门禁**：没有验证凭证 / 代码改过 / 凭证过期，任一情况都拒绝同步，
且**不会推送任何内容到服务器**。

详细规范见 **[交付流程规范.md](交付流程规范.md)**。

## 〇点五、服务开关（双击即用）

根目录 **`服务开关.bat`** —— 一个菜单管住两个环境的全部启停操作。

```
┌─ LOCAL  (http://127.0.0.1:8100) ─┐  ┌─ SERVER (https://123.207.252.195) ─┐
│ [1] Start   后台启动             │  │ [6] Status   查看服务器状态          │
│ [2] Stop    停止                 │  │ [7] Restart  重启生产服务            │
│ [3] Restart 重启                 │  │ [8] To Dev   切到开发模式            │
│ [4] Status  查看状态             │  │ [9] To Prod  切回生产模式            │
│ [5] Open    打开浏览器           │  │ [10] Logs    查看日志                │
└──────────────────────────────────┘  └──────────────────────────────────────┘
```

### 等价的命令行

**本地**（`ops/local-ctl.py` 封装，进程管理用 Python 而非 bash）：

```bash
cd ops && ./local-dev.sh start     # 后台启动（脱离终端，关终端不影响）
cd ops && ./local-dev.sh stop      # 停止（清理残留进程 + 等端口释放）
cd ops && ./local-dev.sh restart
cd ops && ./local-dev.sh status
cd ops && ./local-dev.sh           # 前台运行（Ctrl+C 停止）
```

**服务器**（`ops/srv-ctl.py` 走 SSH 执行服务器上的 `tapd` 工具箱）：

```bash
cd ops && python srv-ctl.py status
cd ops && python srv-ctl.py restart
cd ops && python srv-ctl.py dev
cd ops && python srv-ctl.py stopdev
cd ops && python srv-ctl.py logs 60
```

或直接 SSH 上去用服务器端工具箱：

```bash
ssh -F ops/secrets/sshcfg tapd
tapd status / logs / restart / dev / devrestart / stopdev / devlog / backup / restore
```

### 为什么要用 Python 管进程

Windows 上 bash 管后台进程不可靠：进程随终端关闭而退出、`taskkill` 有时杀不掉、
端口会留下「僵尸 socket」（进程已死但端口不释放）。`local-ctl.py` 用
**PID 文件 + 端口探测**管理，行为可预期。

## 三、同步脚本

```bash
cd E:\WB缓存\2026-10-26-15-55-08\ops

./sync.sh              # 同步代码 + 重启生产服务（数据库不动）
./sync.sh --dev        # 同步代码 + 切开发模式（推送后自动重启）
./sync.sh --prod       # 同步代码 + 切回生产模式
./sync.sh --pull       # 从服务器拉回代码（只拉不推）→ 自动 git 提交
./sync.sh --db-local   # 连数据库一起覆盖（危险，会丢服务器新数据）
```

### 覆盖保护

每次同步前自动比对本地与服务器的 `app.py` md5：

```
⚠ 警告：服务器代码与本地不一致
  如果你在服务器上改过，请先执行 ./sync.sh --pull 拉回本地
  否则本次同步会用本地版本覆盖服务器改动

  仍要继续覆盖？(yes/no)
```

输入 `no` 直接取消，服务器改动保住。输入 `yes` 才覆盖。

### 行尾自动转换

Windows 编辑器容易写入 CRLF，`sync.sh` 会在传输前自动转成 LF（会打印 `[LF转换] xxx`）。仓库里也配了 `.gitattributes` 兜底。

## 五点十、板块与事项的新结构

### 概念层级

```
看板（board，如「成本工作事项（2026年度）」）
  └── 板块（column，如「成本组（第33周)」）
        └── 事项（card）
```

板块此前只隐含在 `cards.column_name` 字段里，**没有独立记录**。
现在新增 `board_columns` 表承载板块的元信息：

| 字段 | 说明 |
|---|---|
| `col_key` | 业务主键 = `board_id::column_name` |
| `column_id` | TAPD 原始列 ID（板块级权限 `perm_pass` 依赖它） |
| `created_at` | 创建日期 |
| `creator` | 创建人 |
| `nature` | 性质：日常 / 专项 |
| `pinned` | 置顶标记（作用域：所在看板内） |

`cards` 表另加 `pinned` 字段，作用域是**所在板块内部**。

### 事项行的字段顺序

```
展开箭头 → 序号 → 标题（可伸缩）
→ 负责人：XXX │ 创建日期：YYYY-MM-DD │ 截止日期：YYYY-MM-DD  ← 字段列（三列定宽，纵向对齐）
→ 逾期 → 代办 → 状态 → 事项置顶 → ＋子事项                   ← 行尾区块（右对齐，元素定宽槽位）
```

- **创建日期只显示年月日**：用 `fmtDate()` 归一（`2026-05-21 10:52:33` → `2026-05-21`），
  界面上不再出现时分秒；字段名统一为「创建日期」（不再叫「创建时间」）。
- **事项置顶**是按钮，与「板块置顶」共用 `.pin-btn` 样式：
  未置顶显示「📌 事项置顶」，点击后变「📌 已置顶」，再点即取消
- **子事项入口只保留一个按钮「＋ 子事项」**：原来的「子事项 N」计数按钮已移除 ——
  已有子事项时左侧展开箭头（▶）就能看到目录，计数再单独占一个操作位属于重复。
  行内「＋ 子事项」按钮直接打开**新建子事项弹窗**（`openNewSubModal`），完成输入与保存。
  显示条件：`ME.can_edit && canEditCard(c)` —— 成本看板仅管理员可见（与「编辑」按钮口径一致）。
- **列表最前方是顺序序号**（`.item-seq` 圆形徽标）：由 `renderBoard()` 排序后按
  `list.map((c,i)=>cardItem(c,i+1))` 传入，**每个板块独立从 1 开始**，不跨板块连续计数。
  置顶的事项序号徽标会变成橙色（`.item-seq.pin`）。
- **负责人 / 创建日期 / 截止日期是三个定宽列**（`.fcols` + `display:grid`）：
  - 父事项行与子事项目录行**共用同一个渲染函数** `fieldCols()`，
    字段集合与顺序由 `fieldItems()` 单一数据源定义 → 父子必然一致，不会各写一份而漂移。
  - 列宽定死（父 166/146/178px，子 156/132/168px），**姓名长短、空值占位都不影响后续列的起点**。
  - **空值统一占位为「—」**（灰色）：负责人为空 → `负责人：—`，与「截止日期：—」同一套 `.fcol-empty` 样式。
    ⚠️ 类名**必须带 `fcol-` 前缀**：全局已有 `.empty{padding:48px}`（无数据占位块），
    若子元素直接用 `empty` 类会被一并命中，48px padding 会把行高从 46px 撑到 139px。
  - 行尾的逾期 / 代办 / 状态 / 置顶 / 子事项五个可选元素**无论有无都渲染定宽槽位**
    （`.slot-overdue` / `.slot-subtask` / `.slot-status` / `.slot-pin` / `.slot-sub`），
    行尾区块整体 `margin-left:auto` 右对齐 → **所有行的三列起点完全一致**，
    标题长短、逾期标签有无、代办有无都不再推移字段列。
  - **grid 容器必须显式给宽度**（`width:520px;flex:0 0 520px`）：
    grid 的列宽只定义轨道，不定义容器本身；容器宽度默认由内容反推，
    空间不足时会塌缩导致内容换行、把行高撑高。`flex:0 0` 同时保证它不被压缩。
  - 字段列**不使用 `margin-left:auto`**：auto margin 在可用空间不足时会失效，
    字段列会被挤到标题上方重叠。右对齐统一由行尾区块的 `margin-left:auto` 承担。

#### 父子事项的字段列对齐

父事项行与子事项目录行要**逐列对齐**（同一垂线），实现靠两条：

1. **行尾槽位宽度完全一致**
   父子两行的行尾都是 5 个定宽槽位：`slot-overdue`(46) / `slot-subtask`(52) /
   `slot-status`(58) / `slot-pin`(84) / `slot-sub`(72)，gap 同为 10px。
   子事项行**没有「＋子事项」按钮，那一格（`.slot-sub`）留空即可**；
   `.slot-subtask`（代办计数）子行也留空。
   → 行尾总宽相同，右对齐锚点才相同。
2. **子树右边距标定为 `8px`**
   `.sub-tree` 的缩进 = margin-left 32 + padding-left 12 + border-left 2 = 46px。
   这个缩进只影响左侧标题区，但会让子行的**右边界**比父行左移 46px →
   右对齐锚点不同 → 字段列起点错位。
   用 `margin-right:8px` 把右侧推回来（= 子行 padding-right 8px 与父行 14px 的差 +
   缩进经实测标定的偏移），使父子右边界一致。
   ⚠️ 这个数值是 **headless Chrome 逐像素实测标定**的；
   改动缩进量或行 padding 时必须重新标定（改完要用快照页测 `getBoundingClientRect().left`）。

> 实测标定方法：`ops/snap4.js` 生成父行+子行同构快照 → 另起 http.server 托管 →
> headless Chrome 读每行三列的 `left` 值比对。快照页脚本要**离线**（不调后端接口），
> 否则本地服务热重载期间会静默失败、一直读到旧快照。
- **负责人父子各自独立取值**：父事项只显示自己 `owner` 字段的值，
  **不做任何继承或汇总**（后端已移除 `sub_owners` 字段，前端也不再兜底）；
  子事项同样只取自己的 `owner`。父事项没填就显示「负责人：—」，不会借用子事项的负责人。
- **行内没有编辑按钮**：编辑入口已移入事项详情弹窗（见下）。

|---|---|

状态只由状态按钮单独写入。两条入口互不干扰，不会互相覆盖。

关键实现：

- `statusPickerHtml(status, ctx)` —— 渲染状态按钮与菜单；`ctx='d'` 详情弹窗 / `'e'` 编辑弹窗，

- `toggleStatusMenu(ev, ctx)` —— 展开/收起菜单。**先记下目标状态再统一收起**，
  否则「收起后又被自己打开」会变成永远打不开。
- `setCardStatus(ctx, st)` —— 写回 `status` + `status_name`（文案由 `statusText()` 统一生成）。
- `closeStatusMenu()` —— 点菜单外部时收起（事件委托到 `document`，两个弹窗共用一条）。
- `renderDetailOps(c)` —— 渲染详情弹窗的操作区。
- `openDetailEdit()` —— 从详情进入编辑：**先关详情再开编辑**（两个弹窗同级，详情在 DOM 靠后会把编辑弹窗盖住）；
  用 `EDIT_FROM_DETAIL` 记录来源，`closeEdit()` 关闭编辑后自动回到详情，操作上下文不断。
- `openDetail(id)` 改用 `GET /api/cards?card_id=<id>` 精确取数 —— 原来的 `?size=2000` 列表**只含顶层事项**，
  取不到子事项（只读账号打开子事项详情会报「卡片不存在」）。

### 归属年份（2026-10-30 起：年份只在板块层）

**层级关系**：年份绑定在**板块**，不在看板。

```
看板（容器，无年份）
  └── 板块（board_columns.year = 2026）   ← 每个板块绑定唯一归属年份
        └── 事项（cards.week_no = 2026年第41周）  ← 事项归属自己的周数
```

- **看板层**：`board_config` 表**已删除 `year` 列**；看板管理界面不再有年份配置
  （无年份 pills、无年份筛选）；`/api/boards` 不再返回 `year`，改为返回
  `col_years`（该看板下各板块年份的集合）供列表展示「板块年份：2026年」。
- **板块层**：`board_columns.year` 保持不变，但语义升级为**单值必填**（留空回落创建年份）。
- **事项层**：`cards.week_no` 不变。

> ⚠️ **周数与年份不做任何强制校验或联动限制**（重要）：
> 归属「2026 年」的板块下，**允许**存在归属「2025 年第 40 周」的事项；
> 服务端既不拦截、也不提示、不做任何自动纠正。
> 代码里**故意没有**「周数年份必须等于板块年份」的校验 —— 加了就是跨年拦截。

**归属年份的默认值 = 板块创建年份**（三层兜底，任何一层缺省都能落到创建年份）：

| 层 | 规则 |
|---|---|
| 表单 | 新建时默认填创建日期的年份；改「创建日期」自动跟随（用户手动改过就不再覆盖） |
| 服务端 | `create_column` / `update_column`：`year = _norm_year(req.year) or created[:4]` —— 传空则回落到创建年份 |
| 迁移 | `init_db()` 回填老数据：`UPDATE board_columns SET year=substr(created_at,1,4) WHERE year=''` |

> 迁移是幂等的，只补空值 —— 已登记的年份不会被启动流程改掉。
>
> **年份下沉时的数据保全**：`init_db()` 会先把 `board_config.year` 补进该看板下
> **没有年份**的板块，再删列 —— 不会因为下沉而丢掉历史年份。

### 年份筛选器（标题处的多选标签组）

页头标题旁的年份筛选已从**单选下拉**改为**多选标签组**（`.year-filter` / `#yearFilter`）：

| | 说明 |
|---|---|
| 形态 | **chips 标签组**：已选年份各一个带 ✕ 的标签；另有「**＋ 年份**」与「**全部年份**」两个固定入口 |
| 三个动作 | ① **＋ 年份** → 展开下拉，勾选可**新增**年份（可多选）<br>② chip 上的 **✕** → **移除**该年份<br>③ **全部年份** → 清空所有已选（= 不过滤） |
| 选项来源 | **当前看板下各板块的归属年份**（去重、倒序） |
| 作用 | 同时选中多个年份时，只显示归属年份命中**任一**已选年份的板块及其事项；搜索结果视图同样按多选过滤 |
| 默认值 | **当前年份**（`YEAR_DEFAULT`，页面加载与切换看板后都是它） |
| 重置 | **切换看板时统一重置为当前年份**；若当前年份在新看板不存在 → 退回「全部年份」 |

> 🔴 **早期版本只有「移除」没有「新增」**：界面上只挂一个「全部年份」标签，
> 用户完全不知道还能选别的年份（反馈：「顶部年份没有选择的地方」）。
> 完整的���选体验必须有三件事 —— **能加、能减、能清空**。

实现要点：

- 状态变量 `curYears` 是 **`Set`**（不是单值）：`curYears=new Set([YEAR_DEFAULT])`；
  `pickBoard()` 里重置为 `new Set([YEAR_DEFAULT])`。
- `renderYearFilter(cols)` 每次 `renderBoard()` 时按当前看板的板块重建 chips，
  并做两级兜底：**已选年份都不存在 → 回落当前年份；当前年份也不存在 → 退回「全部年份」**。
- `paintYearChips()` 是**纯重绘**（按当前 `curYears` 出 chips，不做任何校验）；
  `toggleYearDrop()` / `toggleYearPick(y)` 负责「＋ 年份」下拉的展开与勾选。
- **事件用 document 委托**（`onYearFilterClick`）：chips 与下拉项都是 innerHTML 重建的，
  直接绑在元素上会在重建后失效 —— 这是本项目的既有教训。
- **概览统计不随年份筛选变化**：那 4 张统计卡本来就是**全局汇总**（跨所有看板）。

> 🔴 **「校验」与「重绘」必须拆成两个函数**（`renderYearFilter` / `paintYearChips`）。
> 早期版本移除单个年份后调的是 `renderYearFilter(currentCols())`，而那个函数
> 内含「丢弃当前看板不存在的年份」的校验 —— 一旦传入的板块元信息为空或过期，
> **整个 curYears 会被重置**：用户点一个 ✕，结果所有年份都被清空。
> 现在移除/清空只调 `paintYearChips()`（纯重绘，不做任何校验），
> 只有看板切换等场景才走带校验的 `renderYearFilter(cols)`。

> 🔴 **头部布局的三条约束**（实测踩坑，症状是标题被压成竖排单字）：
> - `.header-left` 必须 `flex-shrink:0`，否则右侧按钮一多，标题就被挤扁
> - `.header-left h1` 必须 `white-space:nowrap`，否则中文标题逐字换行
> - `.header-actions` 必须 `flex-wrap:wrap` + **`margin-left:auto`**：
>   靠 `.app-header` 的 `justify-content:space-between` 撑开左右时，
>   一旦右侧按钮换行，整组就会跑到左边与标题挤在一起
> - `.year-filter` **不换行、不设固定高度**：chips 换行会超出固定高度被裁掉
>
> 另：头部原有 11 个平铺按钮，低频的（备份/恢复/模板/导入/导出）已收进
> **「⋯ 更多」下拉**，常驻按钮降到 6 个，header 高度从 99px 回到 61px。

### 锁图标 🔒 的含义

全站有三处锁，含义各不相同，**不能一概删除**：

| 位置 | 含义 | 处置 |
|---|---|---|
| 看板 tab 上的 🔒 | 成本看板「仅管理员可写」 | **按当前用户是否有实际限制来决定显示**：管理员没有限制 → 不显示；非管理员 → 显示并带提示 |

> 只在限制**确实对当前用户生效**时出现，并在 title 里写明「成本看板：仅管理员可编辑」。
> 与之配套的真实权限控制在：后端 `check_cost_permission()` 403、
> 前端 `canEditCard()` / `canEditColumn()` 隐藏编辑入口、`updateNewBtn()` 隐藏「+ 新建板块」。


### 折叠交互：三角 vs 标题

板块行头（`.week-header`）上两个控件**职责分离、互不干扰**：

| 控件 | 行为 |
|---|---|
| 标题左侧三角 `.chev` | **唯一**控制该板块下事项的展开 / 收起（`toggleWeek`） |
| 板块标题 `.week-title.edit` | **只**打开板块编辑弹窗（`openColumnEdit`），**不影响展开状态** |

实现要点：

- `.week-header` **不再挂 onclick**，两个控件各自绑定，避免一次点击同时触发两件事。
- 标题的数据通过 `data-colkey` / `data-bid` / `data-cname` / `data-year` / `data-nature` /
  `data-created` / `data-creator` 携带，`openColumnEdit(this)` 从 `dataset` 读 ——
  **不要在 onclick 里拼字符串**，板块名里的括号/引号会把属性截断。
- 三角上带 `event.stopPropagation()`，防止冒泡到父级。
- 无编辑权限（只读账号 / 成本看板非管理员）时标题渲染成普通文本，不可点击。

### 页面布局：概览在上、工具栏在下

`.wrap` 内的两个主体区域做了上下对调（只调布局顺序，功能与内部结构不变）：

```
.wrap
├── .progress-overview   总事项 / 已完成 / 进行中 / 未完成   ← 原「事项明细」区
├── .toolbar             搜索 / 状态 / 负责人 / 新建板块 / 展开 / 折叠   ← 原「板块列表」区
└── .board-content       板块 + 事项列表
```

两块各自的 `margin-bottom:16px` 不变，概览区是 4 列 grid（≤900px 变 2 列），响应式不受影响。

### 排序规则

- 先排板块，板块内再排事项
- 默认按**创建时间降序**
- **被置顶的恒在最前**；置顶项内部、其他项各自保持创建时间降序

> 板块进度条的「已完成/总数」按**全量过滤结果**统计，不受分页影响。

### 数据迁移

服务启动时 `init_db()` 自动执行（幂等）：

1. 建 `board_columns` 表 + 索引
2. `cards` 增 `pinned` 列 + 索引
3. `board_columns` 增 `year` 列（归属年份），并按创建年份回填老数据
4. 从已有卡片**回填板块**：创建日期取该板块最早的事项创建时间，创建人取该板块最早事项的创建人，性质默认「日常」

> 回填必须放在 CSV 导入之后执行，否则新库在导入完成前无板块可派生。

#### 新建弹窗的双模式

`newModal` 一个弹窗承担两种新建，`NEW_CARD_MODE` 区分：

| | `'card'` 主事项 | `'sub'` 子事项 |
|---|---|---|
| 打开入口 | 列表行「＋ 事项」→ `openNewModal(boardId, colKey)` | 列表行「＋ 子事项」→ `openNewSubModal(parentId)` |
| 标题 | 新建事项 | 新建子事项 |
| 所属看板 | 可选（成本看板仅管理员可见） | **锁定为父事项的看板**（后端同样强制继承） |
| 所属板块 | 从板块行的「＋ 事项」进来时固定 | 显示**父事项所属板块**（只读） |
| 开始/截止日期 | 无约束 | **受父事项时间范围约束**（`min`/`max`，与后端校验同口径） |
| 状态 | 头部状态按钮（默认「未完成」） | 同一套组件与默认值 |
| 提交 | `createCard()` → `POST /api/cards`（无 `parent_id`） | `createCard()` → `createSubCard()` → `POST /api/cards`（带 `parent_id`） |

**两个模式共用同一段校验**（在 `createCard()` 入口）：标题不能为空、开始日期不晚于截止日期。
创建失败时**弹窗不关闭、输入保留**，用户改完可直接重试。

> ⚠️ **右侧抽屉（`.drawer` / `#drawerPanel`）已整体移除** —— 连同 `openDrawer()` /
> `renderDrawerList()` / `drawerSubTree()` / `drawerTodoTree()` / `DRAWER_STACK` /
> `DRAWER_OWNER` / `DRAWER_NEW_UNDER` 与全部 `.drawer-*` 样式。
> 子事项的**创建**改由列表行「＋ 子事项」直接打开 `newModal`（`openNewSubModal`）；
> 子事项的**查看**走详情弹窗；**代办清单**（`card_subtasks`，与子事项是两回事）
> 在详情弹窗与编辑弹窗里都有完整增删改查，不依赖抽屉。
>
> ⚠️ **本期只支持「主事项 → 子事项」两层**：后端 `POST /api/cards` 会校验父卡片
> 自身是否已有 `parent_id`，有则拒绝（400「本期不支持更深层级」）；
> 前端 `subNodeHtml()` 也不再渲染孙节点。


关键实现（`src/static/index.html`）：

- `statusTag(cardId, s, style, isSub)` / `statusOptions()` / `pinBtn()` —— 状态与置顶的**共享渲染基元**，主事项行与目录行共用，避免两处各写一份。
  `statusTag()` 本身带 `onclick`，**行内状态标签就是唯一的状态快捷切换入口**；行内不再另设「完成」按钮（同一行出现两个做同一件事的控件是冗余）。
- `openSubModal(id)` —— 子事项的**详情弹窗**入口：统一调 `openDetail(id)`（与主事项同构），不再直接进编辑弹窗；无编辑权限时同样只读展示。
- `openEdit(id, preloaded)` —— 主事项弹窗；`EDIT_IS_SUB` 为真时进入子事项模式。子事项保存**不发 `cc`、不跨看板移动**（子事项继承父看板）。
- `applyOwnerSlot(isSub)` —— 「负责人」字段的位置搬运：子事项模式下把它 **DOM 搬到「状态」行**（`statusRow.appendChild`），
  原「负责人 / 参与人」行收起；主事项模式还原。用搬同一个 DOM 节点而不是复制一份，保证只有一份输入框、不会错位。
- `patchSubTreeNode()` —— 子事项就地改状态/置顶后，目录局部刷新，**不整页 reload**（否则已展开的目录会被折叠掉）。
- `attachRipple(container, selector)` —— 点击涟漪；事件委托挂在 `#boardContent` 上，容器重绘不用重绑监听。
  自身带独立交互的元素（展开箭头、置顶、状态标签）不触发行级涟漪，避免双重反馈。

#### 踩过的坑：创建子事项失败后的表单残留

`createDrawerSub()` 的成功路径原本会清空表单，**失败路径只弹了个 toast**，导致上一次选中的「负责人」等临时状态留在表单里，下次提交会把脏数据一起带过去。

修法：把清空逻辑抽成 `resetDrawerNewForm()`，**成功与失败都调用**：

```js
} catch (e) {
  resetDrawerNewForm();   // 失败：同样清空，避免脏数据残留
  toast(e.message);
}
```

「无负责人」这一档的哨兵值仍是 `__no_owner__`：

```js
const OWNER_NONE='__no_owner__';                  // 与后端一致
function personLabel(v){return v===OWNER_NONE?'无负责人':v}
```

```python
# 后端 /api/cards 的 person 分支
pnames = [x.strip() for x in person.split(',') if x.strip()]
if pnames:
    want_none = OWNER_NONE in pnames
    real = [p for p in pnames if p != OWNER_NONE]
    def _person_hit(r):
```

#### 5.2 周数排序 —— 必须按「年×100 + 周号」的组合整数序

> ⚠️ **2026-11-02 修复**：候选面板里的周数原本用**字符串排序**，
> 于是「第3周」被排到了「第31周」**后面**（字典序比较到 `'3'` 与 `'周'` 时 `'3'` 更大），
> 列表变成「第31周、第33周、第3周、第44周、第4周、第5周…」这种乱序。

**正确口径**：把「2026年第41周」折成 **202641** 这样的组合整数再比：

```python
# 后端 app.py
def week_sort_key(v):
    """把「2026年第41周」折成 (2026, 41) 这样的组合整数。
    ⚠️ 不能直接按字符串排序 —— 字典序下「第3周」会排在「第31周」后面。"""
    s = (v or '').strip()
    m = re.match(r'^(\d{4})年第(\d{1,2})周$', s)
    if m:
        return (int(m.group(1)), int(m.group(2)), 0, s)
    return (9999, 0, 1, s)   # 非标准标签排最后，彼此保持原序
```

```javascript
// 前端 index.html（与后端同口径）
function weekSortKey(v){
  const m=/^(\d{4})年第(\d{1,2})周$/.exec(String(v||'').trim());
  if(m)return parseInt(m[1],10)*100+parseInt(m[2],10);
  return 999999;
}
```

**三处排序点都要用这个键**（漏一处就会出现"接口排对了、面板又乱了"）：

| 位置 | 作用 |
|---|---|
| 后端 `/api/filter-options` | `sorted(weeks, key=week_sort_key)` —— 候选面板的全量来源 |
| 后端 `/api/cards` | `week_options = sorted({...}, key=week_sort_key)` —— 列表接口回传的周数选项 |
| 前端 `paintFilterCombos()` | `.sort((a,b)=>weekSortKey(a)-weekSortKey(b))` —— 面板实际渲染顺序 |
| 前端 `renderWeekFilter()` | 同上 —— 看板级周数集合的顺序 |

> ⚠️ **只改顺序、不改选项集合**：排序键只影响展示次序，
> 哪些周数会出现仍由数据本身决定（不增删、不合并、不重排到别的字段）。

#### 5.3 创建日期区间筛选

工具栏上的两个 `<input type="date">`（起 / 止）+ 中间的 `~` + 一个清除按钮（`✕`）。

| 情况 | 行为 |
|---|---|
| 两端都空 | 不参与筛选（请求里不带日期参数） |
| 只填起 | 单边区间：从这天起 |
| 只填止 | 单边区间：到这天止 |
| 起 > 止 | **前端自动交换**，后端也再兜一层 |
| 清除按钮 | 清空两端 → 取消该筛选 |

**查询参数名是 `created_start` / `created_end`**，⚠️ **不要叫 `created_from`** ——
`cards` 表本身有一个 TAPD 原始字段叫 `created_from`（xlsx 导入用），同名会混淆。

**后端实现要点**：

```python
cf = _norm_date(created_start)     # 归一化：非法值返回 None（忽略，不报错）
ct = _norm_date(created_end)
if cf and ct and cf > ct:
    cf, ct = ct, cf                 # 起止颠倒自动纠正
if cf or ct:
    w, p = ['deleted=0'], []
    if cf: w.append('substr(created,1,10) >= ?'); p.append(cf)
    if ct: w.append('substr(created,1,10) <= ?'); p.append(ct)
    pool = [dict(r) for r in dbq('SELECT * FROM cards WHERE ' + ' AND '.join(w), p)]
else:
    pool = all_rows
```

- **用 `substr(created,1,10)` 取日期部分比较** —— `created` 里可能带时分秒
  （`2026-08-17 01:37:05`），直接跟纯日期做字符串比较会漏掉当天 00:00 之后的记录。
- **全量行必须单独查**：`all_rows` 用于统计每个事项的子事项数（`sub_count`），
  不能被日期区间裁剪，否则子事项计数会随筛选变化。
- `_norm_date()` 接受 `YYYY-MM-DD` / `YYYY-MM-DD HH:MM[:SS]` / `YYYY/MM/DD`；
  **非法值一律忽略而不是抛错** —— 一个脏参数不该让整个列表接口 500。

## 五点九、评论 @ 提及 与消息中心

### @ 提及的两态分离

评论输入区刻意分成**两个视觉状态**：

| 状态 | 位置 | 形态 |
|---|---|---|
| **输入态** | 输入框内 | 纯文本（用户正在打的字） |
| **已插入态** | 输入框**下方** | 蓝底圆角 chip（`.mention-chip`），带 ✕ 可单独移除 |
| 候选中 | 输入框下方浮层 | `.mention-drop` / `.mention-opt`，↑↓ 切换、Enter 选中、Esc 收起 |

流程：`onCommentInput()` 检测光标前的 `@词` → `renderMentionDrop()` 出候选 →
`pickMention(name)` 插入 chip（同时把输入框里的 `@词` 删掉）→ 提交时
`addComment()` 把 chip 合并成正文里的 `@姓名`，并把成员名数组放进 `mentions`。

**为什么不用 contenteditable**：光标管理在跨浏览器时极易出错；
两态分离的实现更稳，且 chip 可单独移除（contenteditable 做不了）。

### 消息投递链路

```
评论（mentions=["苏春景"]）
  → _mention_receiver("苏春景")   查 team_members.account → "scj"
  → INSERT INTO messages (receiver='scj', sender='admin', card_id=..., kind='mention')
  → 被提及人登录后 GET /api/messages 收到
```

**收件人匹配**：`receiver IN (当前账号, 该账号绑定的成员姓名)` —— 两种都收，
避免「成员改了账号绑定」导致漏收。

### 消息中心

- 顶部铃铛 `#msgBtn` + 未读徽章 `#msgBadge`（`99+` 封顶）
- 消息栏 `#msgPanel`：未读有**蓝色圆点 + 淡蓝底 + 加粗标题**，已读无圆点
- 点消息 → `POST /api/messages/{id}/read` 标记已读 → **跳转到对应事项**
  （`jumpToCard()` 跨看板时先 `pickBoard()` 再 `openDetail()`）
- 「全部已读」→ `POST /api/messages/read-all`
- **越权保护**：标记已读时校验 `receiver` 属于当前用户，否则 404

| `org_nodes` | 架构节点（中心 / 部门 / 常规小组 / 专项小组），`UNIQUE(parent_id,name)` |
| `org_roles` | 岗位定义：节点类型 → 可设岗位，`unique_slot=1` 表示节点内至多一人 |
| `org_appointments` | 任职关系（人 × 节点 × 岗位），`UNIQUE(node_id,member_id,role_key)` |

### 层级与岗位

```
中心（center）      → 中心负责人(唯一) / 总经理(唯一) / 中心骨干(可多人)
  ├ 部门（dept）    → 部门长(唯一) / 部门骨干(可多人)
  │   ├ 常规小组    → 组长(唯一) / 组员(可多人)
  │   └ 专项小组    → 组长(唯一) / 组员(可多人)      ← 跨部门临时协作
  └ 专项小组（special）                              ← 全公司级专项
```

| 节点类型 | 允许的上级 |
|---|---|
| `center` | 无（全局唯一） |
| `dept` | `center` |
| `group` | `dept` |
| `special` | `center` 或 `dept` |

前后端共用同一套规则（前端 `ORG_CHILD_RULES`，后端 `ORG_PARENT_RULES`）。

### 三类校验

| 类别 | 规则 | 错误提示示例 |
|---|---|---|
| **层级完整性** | 类型合法、父类型匹配、不自指、**不挂到自己的后代下（防环）**、中心唯一、子节点类型兼容 | `常规小组只能挂在「部门」下，「财务中心」是中心` |
| **角色唯一性** | 岗位必须属于该节点类型；**唯一槽位节点内至多一人** | `「组长」在一个节点内只能有一人，当前已由 王伟娜 担任` |
| **多归属一致性** | 一人多岗 / 一人多组织均允许；任职变更同步旧视图 | `该成员在此节点已有该岗位` |

唯一槽位有**双层保障**：应用层 `_check_unique_slot()` 给中文提示，
DB 层 partial unique index `ux_org_unique_slot` 兜底。

> ⚠️ **改 `org_roles` 的 `unique_slot` 集合时，必须同步改那条索引** ——
> SQLite 的 partial index 的 `WHERE` 不允许子查询（不能引用 `org_roles`），
> 岗位键是写死的。

### 新旧模型共存

- **新模型是权威源**；旧表 `workgroups` 与 `team_members.workgroups` 是**派生视图**
- `_org_sync_legacy(node_id)` 在任命 / 免职 / 调整任职 / 删除节点后回写：
  `workgroups.leader` ← 唯一槽位任职人；`team_members.workgroups` ← 小组成员的组员任职
- 旧权限逻辑 `_leader_boards` / `_group_boards` **零改动**继续可用
- 存量迁移 `_migrate_org(conn)` 幂等，由 `init_db()` 调用

### 界面

- **点节点行** = 查看该节点的岗位与任职；**「编辑」** = 进编辑模式
- 节点行带**类型徽章**（🏛️ 中心 / 🏢 部门 / 👥 常规小组 / 🎯 专项小组）
- 右侧「岗位与任职」每个岗位一个槽位：唯一槽位标「唯一」，可多人标「可多人」
- 成员 chip 带 `+N` = 另有 N 个组织任职（多归属提示）
- **类型下拉按上级过滤**（`fillOrgTypeOptions`），无合法子类型时禁用
- **不再有「职能说明」输入框**：该字段已整体下线（表单 / 渲染 / 提交 / 接口模型 /
  数据列全部清理），存量库的 `description` 列由 `_drop_description_columns()` 迁移删除

### 右栏空白占位的修复（只调布局，不动功能）

未选中节点时，右栏「岗位与任职」区只有一句「在左侧选中一个节点后…」的引导文字，
却被**两层 `flex:1` 撑成一大片空白**（配置区容器 `flex:1` 撑满右栏全高，
岗位区又是 `flex:1` 吸收剩余空间）。

修法 —— **保留全部任命功能，只让布局按内容自适应**：

| 元素 | 改前 | 改后 |
|---|---|---|
| 配置区容器 | `flex:1;min-height:0;overflow:hidden` | `flex-shrink:0;max-height:100%;overflow-y:auto` |
| 「岗位与任职」块 | `flex:1` | `flex-shrink:0` |
| `#g_roles_box` | `flex:1;min-height:0` | `max-height:240px;overflow:auto` |

实测：未选中时占位区高度 **57px**（原为撑满整屏）、配置区底部余量 **15px**；
选中节点后岗位槽位正常渲染（每个槽位带「选择成员…」下拉 + 「任命」按钮 +
任职人员 chip + 免职 ✕），岗位区高度受控在 240px 内可滚动。

> ⚠️ **教训**：看到「这块是空白 / 占位」时，先分清是**功能多余**还是**布局多余**。
> 本次误判为前者，把任命模块整个删了 —— 实际用户要的只是后者。
> 改动前先确认清楚：**是不要这个功能，还是不要这块空白？**

### 选中态与底色高亮（踩过的坑）

架构树行曾经出现「点了一行，高亮还留在旧行」的不一致。根因是用行内
`style="background:..."` 写死底色，与 CSS `.sel` 规则互相覆盖。

现改为**类驱动 + 统一回写**：

| 机制 | 说明 |
|---|---|
| 真相来源 | `ORG_SELECTED`（节点 id），唯一 |
| 定位锚点 | 行上的 `data-org-id` |
| 底色 | `.org-node-row.sel{background:#f0f7ff!important}` + 左侧 2px 蓝内阴影 |
| 回写函数 | `paintOrgSelection()` —— 按 `dataset.orgId === ORG_SELECTED` 切换 `.sel` |

调用点覆盖三个场景：`renderWgList()`（列表刷新）、`selectOrgNode()`（点击切换）、
`editWg()`（进入编辑态）。**新增场景时记得调用 `paintOrgSelection()`**。

**残留高亮的根因与修法**：树行曾经同时存在**两个 `.sel` 真相来源** ——
渲染时按 `ORG_SELECTED===n.id` 内联拼 `' sel'`，回写函数又按 `dataset.orgId`
toggle `.sel`。两者一旦不同步，就会留下「已取消选中却仍高亮」的残留。
现在树行**不再内联生成 `.sel`**，`.sel` 只由 `paintOrgSelection()` 回写。
另外 `openWgModal()` / `resetWgForm()` 都会把 `ORG_SELECTED` 置 0，
保证打开弹窗时是干净的未选中态。

**重复点击同一节点即取消选中**：`selectOrgNode()` 检测到 `ORG_SELECTED===nid`
时转调 `clearOrgSelection()`，复位选中态、表单标题、岗位区、板块绑定区。

> 无头 Chrome 验证时注意：`.org-node-row` 有 `transition:background .12s`，
> 虚拟时间下过渡未走完会读到过渡起始值。测量前注入 `transition:none !important`。

## 五点十一、看板管理：归属部门联动 / 选择与删除 / 批量配置

> 回归测试：`node ops/test-board-perm.js`（102 条）。

### 归属部门联动【架构管理】

看板管理的「归属部门」下拉**不再用固定枚举**，数据源是架构管理里的
**中心 / 部门**节点（`/api/boards` 返回 `depts`）：

| 归属类型 | 语义 | 效果 |
|---|---|---|
| **中心级**（如财务中心） | 视为**全部板块**，自然添加 | 该板块**对全员展示** |
| **部门级** | 该部门拥有的板块 | **挂靠该部门的成员**可见 |
| **未配置** | 无归属 | 全员可见（目录树里的「未配置」节点） |

数据落库在 `board_config`：

| 字段 | 说明 |
|---|---|
| `dept` | 归属部门名称（冗余，便于按名分组展示） |
| `dept_node_id` | 归属部门对应的 `org_nodes.id`（**权威关联**，0 = 未配置） |

> ⚠️ **看板层没有「年份」**（2026-10-30 起）：年份绑定在**板块**层
> （`board_columns.year`），看板管理界面不再有年份配置项，列表行显示的是
> 「板块年份」（该看板下各板块年份的集合，来自 `/api/boards` 的 `col_years`）。
> 详见「五点十、板块与事项的新结构 → 归属年份」。

下拉里中心级选项带标注「（全部板块 · 对全员展示）」，切换时同步写 `dept_node_id`。

架构管理侧的「板块绑定」对部门/中心节点改为**只读派生**（`nodeBoardScope()`）：

- 部门节点 → 显示 `owned_boards`（`/api/org/tree` 返回），不可手动勾
- 中心节点 → 全部板块，不可手动勾
- 小组节点 → 沿用旧逻辑，手工勾选写 `workgroups.boards`

> 口径统一原则：**看板管理是唯一真相**，架构管理只做派生展示，避免两处不一致。

### 权限过滤的三层判定流程

成员登录后可见板块 = 三层过滤的交集（`user_allowed()`）：

```
① 归属部门层（第一层）
   依据 board_config.dept_node_id：
     · 成员挂靠部门所拥有的板块 → 可见
     · 归属中心的板块 → 对全员展示
     · 未归属的板块 → 全员可见
   成员无部门归属或挂靠中心 → 本层不收窄

② 负责范围层（部门长 / 组长）
   额外拥有其负责范围（自身 + 全部后代）绑定的全部板块

③ 工作组绑定层（最终收窄）
   普通成员按所属工作组的板块白名单收窄
   （workgroups.boards：'*'=全部，逗号分隔=白名单，空=跟随账号权限）

   叠加：账号级 users.allowed_boards / allowed_columns 与上述结果取交集
```

成员部门范围的推导（`_member_dept_scope()`）取两个来源的**并集**：
`org_appointments`（新模型任职）+ `team_members.workgroups`（旧字段，向后兼容），
小组归属**向上取最近的部门/中心祖先**。

### 看板管理弹窗的批量操作

进入看板管理时**默认不选中**（`BC_SEL` 为空集），所有板块都需用户主动勾选：

| 控件 | 位置 | 行为 |
|---|---|---|
| 列表项复选框 | 左侧列表 | 逐个勾选/取消 |
| **单个**全选按钮（`#bcPickAllBtn`） | 左侧工具条 | 点击时按当前状态取反：全未选 → 全选；已全选 → 取消全选。**按钮文案随状态切换**（「全选」↔「取消全选」），不再并排两个按钮 |
| 「删除所选」按钮（`#bcDelBtn`） | 左侧工具条 | 与全选按钮**同一行横排**、样式统一；未勾选时禁用。**按钮不带个数** —— 个数统一由右侧「已选 N 个」显示，避免同一信息重复两处 |
| 「已选 N 个」计数 | 左侧工具条右端 | 实时显示勾选数量，靠右对齐 |
| 「应用到已选 N 个板块」 | 右侧编辑区页脚 | 调 `POST /api/board-config/bulk` 批量写入归属部门/年份/属性/状态 |
| 「删除该看板配置」 | **右侧编辑区页脚** | 单条删除当前选中看板的配置（仅已配置的看板显示） |

> 筛选条件变化时 `BC_SEL` 会**清空**（保持「默认不选中」语义，避免误批量操作）。
> 勾选态（`.bc-pick`）与高亮态（`.active`）是两套独立状态，互不干扰。

批量接口返回 `{ok, created, updated, skipped}`，并写审计日志。

### 删除入口的分工

| 删除类型 | 入口 | 位置 |
|---|---|---|
| **单条** | 编辑区页脚「删除该看板配置」 | **右侧编辑区**（选中某个看板后操作） |
| **批量** | 工具条「删除所选」 | **左侧列表上方**（基于勾选集合操作） |

单条删除放在编辑区，是因为它作用于「当前正在编辑的这一个看板」，
与右侧表单是同一个对象上下文；列表行内只保留复选框与「编辑 ›」，
避免每行都堆按钮导致列表拥挤、误点。

> ⚠️ **工具条按钮竖排的坑**：`.bc-opbar` 与 `.bc-filter-row` 作用于**同一个元素**，
> 而 `.bc-filter-row` 带 `flex-direction:column` —— 后定义的 `.bc-opbar`
> 只覆盖了 `display`，没覆盖 `flex-direction`，按钮就被压成了竖排。
> 现 `.bc-opbar` 显式声明 `flex-direction:row;flex-wrap:nowrap`，
> 并用 `.bc-opbar-btns` 把两个按钮包成一组（`flex-shrink:0`）保证不换行。

### 删除的确认层级

| 操作 | 确认次数 | 入口 |
|---|---|---|
| **单条删除** | **1 次** | 编辑区页脚「删除该看板配置」（`bcDeleteOne`） |
| **批量删除** | **2 次** | 工具条「删除所选」（`bcDeleteSelected`） |

- 两次确认**逐级拦截**：第一次取消/关闭 → 直接返回，**不会**弹第二次，**不会**执行删除；
  第二次取消/关闭 → 同样不执行。
- 两次都确认 → 调 `POST /api/board-config/bulk-delete` 批量删除配置。
- 删除**只删 `board_config` 配置行**，不动看板本身与卡片；删除后该板块回到「未配置」状态。
- 删除完成后统一走 `bcAfterDelete()`：清空 `BC_SEL` → 重新拉列表 → 刷新 `ME` 与目录树
  → 重绘列表与编辑区。**选择状态与勾选框都会归零。**

> 确认对话框用 `window.confirm`（抽出 `bcConfirm()` 便于测试注入）。若要做自定义弹窗，
> 改 `bcConfirm()` 一个函数即可，调用点无需改动。

### 架构管理的选中态（重复点击即取消）

| 交互 | 结果 |
|---|---|
| 打开架构管理弹窗 | **默认未选中**，无任何高亮残留，右侧显示「在左侧选中一个节点后…」引导 |
| 点击某个节点 | 该节点高亮（`#f0f7ff` + 蓝色左边框），右侧显示它的岗位与任职 |
| **再次点击同一节点** | **取消选中** —— 高亮消失，右侧面板复位为引导态 |
| 点击另一节点 | 正常切换（旧高亮清除） |
| 关闭后重新打开 | 仍为未选中态，无残留 |

实现要点：

- 树行**不再内联拼接** `' sel'`，`.sel` **只**由 `paintOrgSelection()` 回写 ——
  消除「渲染内联」与「统一回写」两个真相来源导致的高亮残留。
- `openWgModal()` / `resetWgForm()` 都会把 `ORG_SELECTED` 置 0。
- `clearOrgSelection()` 负责复位：选中态归零、表单标题回「新增节点」、
  岗位区与板块绑定区回引导文案、搜索框禁用。

## 五点十二、成员保存校验 · 权限优先级 · 末级人员筛选

> 回归测试：`node ops/test-org-priority.js`（102 条）。

### 一、「ID N 的姓名不能为空」中断保存（已修复）

**现象**：在【成员与账号管理】里改了账号/密码，点「保存全部」弹
「ID 17 的姓名不能为空」，整批保存被中断。

**根因**：表格按筛选条件渲染，但 `saveAllTeamMembers()` 遍历的是**全量** `TM_ALL`。
被筛掉的成员在 DOM 里**没有输入框** → `getElementById('tm_edit_name_17')`
取不到 → 姓名判空 → `return`，**整批保存全废**。

实测数据：成员总数 25，可见 21 —— 隐藏的 4 位必然触发这个问题。

> 更危险的是：若当初硬取空值继续提交，会把隐藏成员的
> **账号/角色/工作组一并清空**（账号是空串 = 关闭登录账号）。

**修法**：

- `renderTeamList()` 记录可见成员 id 到 `TM_VISIBLE_IDS`；
- 保存时 `const visible=TM_ALL.filter(m=>TM_VISIBLE_IDS.has(m.id))` ——
  **只提交可见行**，隐藏行既不校验也不提交；
- 提示里说明「另有 N 位成员被筛选隐藏，未提交」；
- 筛选结果为空时明确提示，不静默失败。

> 通用教训：**遍历数据源 ≠ 遍历 DOM**。表格渲染是筛选后的，
> 保存逻辑若按全量遍历，就会拿到不存在的元素。

> 顺带修掉：**角色筛选默认改为「全部角色」**（原默认是「无权限」，
> 打开弹窗只显示 21/25 人，已开通账号的成员被藏起来，
> 管理员想改他们的账号/密码得先手动切换筛选）。
> `TM_FILTER.role` 的**空数组 = 全部角色**（不过滤），默认值改为空数组，
> 筛选按钮文案由「角色（全部）」改为「全部角色」。
> 配套修掉一个潜在漏人：弹窗「全选」会把 role 设为 4 个具体值，
> 此时「有账号但 users 表无角色记录」的成员（`m.role` 为空串）匹配不上会被漏掉
> → 勾满 4 类时视同「不限角色」，与「不勾选」等价。
> 弹窗里加了一行提示「不勾选任何角色 = 显示全部角色」。

### 二、架构管理 vs 工作组选择：冲突与优先级

系统里两套机制表达同一件事 —— 「这个人属于哪个组织节点」：

| 机制 | 入口 | 存储 | 性质 |
|---|---|---|---|
| 【架构管理】「任命」 | 架构管理右栏「岗位与任职」 | `org_appointments` | **权威源**（唯一有效入口） |
| ~~【人员与账号管理】「工作组选择」~~ | ~~成员表格「🌳 选择工作组」~~ | ~~`team_members.workgroups`~~ | **已下线**（见下方「成员页面工作组控件下线」） |

**冲突根源**：`_org_sync_legacy()` 把架构管理的任命**单向增量**回写旧表 ——
`workgroups.leader` 是覆盖式（✅），但 `team_members.workgroups` **只追加、从不删除**（⚠️）。
于是两套机制**累积叠加**：

- 旧机制下设置的工作组，永远不会被架构管理的任命顶掉；
- 早期 `_member_dept_scope()` 取两者**并集** → 部门范围被放大 → **权限被意外放宽**；
- `_group_boards()` / `_leader_boards()` 原本只读旧字段 →
  架构管理里新配的任命在没触发同步的场景下**不生效**。

**优先级规则（本次确立）**：

> **架构管理优先**。成员只要在 `org_appointments` 里有**任何任命**，
> 其组织归属**完全以架构管理为准**，人员管理里的 `workgroups` 字段一律忽略；
> 架构管理里**没有任命**时，才回退用旧字段（兼容未迁移的历史成员）。

落地在三个推导函数上，两层用同一套权威集合：

| 函数 | 作用 | 权威来源 | 回退 |
|---|---|---|---|
| `_member_authority_nodes()` | 部门层级范围 | `org_appointments` | `team_members.workgroups` |
| `_member_workgroup_names()` | 工作组名 | 任命的节点 | `team_members.workgroups` |
| `_org_leader_nodes()` | 负责人范围 | 任职岗位 ∈ {group_leader, dept_head, center_head, gm} | `workgroups.leader` |

**成员表格的可见标注**（`/api/team` 返回 `org_source` / `org_nodes` / `org_conflict`）：

| 标注 | 含义 |
|---|---|
| 🏛 架构管理任命 | 权威来源，按此判定 |
| ⚠ 忽略：综合工作组、海南工作组 | 旧字段有、架构管理没有 → **不生效** |
| 👥 历史归属（架构管理未任命） | 回退来源（该成员架构管理里无任命） |
| 未分配 | 两边都没有 |

实测：25 位成员中 23 位来自架构管理、1 位回退、1 位未分配；
**王伟娜**存在真实冲突（旧字段含架构没有的「综合工作组/海南工作组」），
现已按架构管理（核算部 / 收入组 / 统筹）覆盖。

> 排查权限问题时先看这个标注 —— 如果可见范围比预期宽，
> 九成是「架构管理与工作组选择不一致」造成的。

【成员与账号管理】里的【工作组选择】控件**整体下线**，
组织归属的配置入口、校验与操作权限统一收敛到【架构管理】。

> ⚠️ **最容易踩的坑**：后端如果只是「不再接收」workgroups 却仍然写库，
> 前端不传 → Pydantic 默认值 `[]` → **把架构管理同步来的归属数据全部清空**。

**只读层级树的实现**（`renderMemberWgTree()` / `memberWgTreeNodes()`）：

- 数据源以【架构管理】为准：`org_source==='org'` 时用 `org_nodes`（架构任命的节点），

- **默认收起**，点击箭头逐级展开；**纯展示，无勾选框、无输入框、无任何编辑入口**；
- 展开状态记在 `WG_TREE_EXPANDED`，整表重绘后能恢复。

> 🔴 **展开必须用局部 DOM 操作，不能重绘表格**。
> 早期实现 `toggleWgTree()` 调 `renderTeamList()` 重绘 tbody，
> 结果用户在表格里改好的**姓名/账号/密码输入框内容被清空**（还没点保存就丢了），
> 滚动位置也归零。现改为只切子级容器的 `display` + 箭头文案，不碰表格其余部分。

**配套修复：删除成员时清理架构管理的任职记录**

`org_appointments` 虽声明了 `ON DELETE CASCADE`，但本库**未开启**

删成员会残留孤儿任职数据。现已在 `del_team` 里显式

### 三、树形组件的末级人员与人员筛选

树形选择组件的 `pickMode:'person'` 模式：**在架构节点下追加末级人员条目**，
人员可勾选。勾选结果在**筛选栏**里写入 `PERSON_SEL`（锚定负责人维度），
在**卡片编辑弹窗**里直接回填选择器。

| 位置 | 入口 | 行为 |
|---|---|---|
| **卡片列表页筛选栏** | 「👤 人员」控件旁的「🌳」按钮 | 勾选人员 → 并入人员筛选集合（与负责人条件取交集）→ 重查列表 |
| **卡片编辑弹窗** | 负责人 / 参与人旁的「🌳 从架构选人」 | 勾选人员 → 直接回填选择器（**与手动输入并存**） |

后端 `/api/cards` 的 `owner` / `cc` / `person` 都支持
**逗号分隔多值 = 任一命中**（单值时保持原有子串匹配语义）；
`owner` 与 `person` **指向同一字段**、同时提交时求**交集**（详见「五点十九」）。

实现要点：

- **人员来源**：`/api/org/tree` 每个节点返回 `members`
  （该节点及后代节点的任职人，含姓名与岗位），`_collect_node_members()` 收集，
  同一人只出现一次；
- **与节点名区分**：人员条目在 `selected` 里用前缀 `ORG_PERSON_PREFIX`（`__P__`）标记，
  回传时按**常量长度**剥离 —— 曾写成 `slice(4)`（实际是 5）导致人名残留 `_`；
- **person 模式的节点框**：早期是置灰的（`.tp-box-na`，节点只作导航）。
  现改为**可点击级联**（`.tp-box-node`）：点父节点 = 勾选/取消其下属全部人员，
  并显示三态（全选 ✓ / 半选 ▣ / 未选）。⚠️ `setBox()` 会覆盖 `className`，
  必须保留 `tp-box-node`，否则节点框又变回死元素；
- **人员条目的归属**：后端 `_collect_node_members()` 返回的是「本节点 **+ 全部后代**」
  的人员，同一个人会在父节点与子节点各出现一次（层级错乱）。
  现由后端补 `node_id`（实际任职节点），前端按 `m.node_id === n.id` 过滤；
- **人员必须在可折叠容器内**：旧代码把人员拼在 `tp_children_*` **外面**，
  折叠父节点时人员依然显示。现已移入容器内；
- **架构树按需加载**：`ensureOrgTree()` 幂等 —— 「按人员筛选」「从架构选人」
  是**独立入口**，不能依赖用户先打开过架构管理弹窗；
- **内联 onclick 的坑**：`onclick="f('cc',["刘自琴"])"` 里的双引号会**截断 HTML 属性**，
  导致按钮点了没反应 —— 改用 `onclick` 赋值绑定。

### 二、双滚轮（表格容器自己一条 + 弹窗主体一条）

**根因不是「两条滚动条难看」，而是 flex 压缩**：

`modal-body` 是 `display:flex;flex-direction:column`，表格容器（1400px+）作为
flex 子项会被**压缩**到容器高度内；`overflow:visible` 让内容溢出显示，
但父容器 `scrollHeight` 不涨 → **表格被压扁且滚不动**。

| 方案 | 效果 |
|---|---|
| 给容器加 `max-height + overflow:auto`（旧） | 容器自己产生滚动条 → **双滚轮** |
| 容器改 `overflow:visible` 但不管 flex | 表格被压扁 → **滚不动** |
| 容器改 `overflow:visible` + `flex-shrink:0`（现） | ✅ 弹窗主体是唯一滚动容器 |

配套：
- `.tm-table-scroll{overflow:visible;flex-shrink:0}`
- `#teamModal .modal-body>*{flex-shrink:0}`（其他子项同样不许压缩）
- `thead th{position:sticky;top:var(--tm-sticky-top);z-index:2}`，
  `--tm-sticky-top` 由 `syncTmStickyTop()` 测量**常驻筛选栏高度**写入，
  避免表头与筛选栏重叠；视口变化时用 `document.addEventListener('resize')` 重算

> ⚠️ 测试沙箱里 `window` 没有 `addEventListener`（只有 `document` 有），
> 用 `window.addEventListener('resize')` 会让 3 个测试文件直接崩溃 —— 改用 document。

### 三、架构管理点击后无弹窗

**根因**：上一轮把 `const od = await api('/api/org/tree')` 挪进 `ensureOrgTree()` 后，
**漏改了后面两行仍引用 `od` 的代码** → `ReferenceError: od is not defined`
→ `openWgModal()` 在 `await` 处抛错中断 → 弹窗永远不显示。

修法：`ORG_ROLES_BY_TYPE` / `ORG_TYPE_NAMES` 的赋值一并移进 `ensureOrgTree()`。

> 通用教训：把一段代码抽成独立函数时，**函数体内所有对被移动变量的引用都要一起搬**，
> 否则就是「函数声明成功、调用即抛 ReferenceError」——
> 而且这种错误只在**点击时**才暴露，静态语法检查发现不了。

## 五点十四、架构管理任命后弹窗未刷新

**现象**：在【架构管理】里任命组长后，弹窗的树不刷新 ——
行内「负责人」仍是「未任命」、任职人数不变，像是"点了没反应"。

**根因**：`ensureOrgTree()` 被抽出来时带了**幂等缓存**：

```js
if(ORG_TREE && ORG_TREE.length) return ORG_TREE;   // 有缓存就直接返回
```

而任命成功后的"刷新"靠 `await openWgModal()`，`openWgModal()` 内部调的
**正是** `ensureOrgTree()` → **拿到旧数据 → 只是把旧数据重绘一遍**。
树行的「负责人」「任职人数」都取自 `ORG_TREE` 里的 `node.appointments`，
缓存不刷新 = 这两列永远不更新。

> 这个坑很隐蔽：代码看起来"刷新了"（`await openWgModal()` 确实执行了），
> 但**数据是旧的**，很容易被误判成渲染 bug。

**修法**：

| 入口 | 模式 | 理由 |
|---|---|---|
| `openWgModal()` | **强制** `ensureOrgTree(true)` | 每次打开都要最新任命数据 |
| 「从架构选人」（编辑弹窗） | 缓存 | 独立入口，不该每次点击都打接口 |
| 「🌳 架构选人」（筛选栏） | **强制刷新** | 人员筛选要反映最新任命（免职/任命后立即生效） |

**连带修掉**：任命后 `openWgModal()` 会 `resetWgForm()` 把选中态清零，
用户「点节点 → 任命 → 想继续看同一个节点」时视线被打断。
现改为记住并恢复 `keepSel`（节点还在就恢复选中，只重绘不重置表单）。

> 通用教训：**带缓存的加载函数被当作「刷新」用时，必须提供强制刷新通道**。

## 五点十五、个人界面：头像 / 个人状态 / 修改密码

> 回归测试：`node ops/test-profile.js`（127 条）。

### 入口
**顶栏右上角的用户名区域**（头像 + **姓名(账号)** + 角色标签）可点击 → 打开「个人界面」。

| 保存 | 与头像、状态共用「保存资料」按钮，一次提交 `{avatar, photo, status_text}` |

> 压缩时 canvas 先填白底再绘制 —— PNG 的透明区域转 JPEG 会变黑。

### 统一占位图与裁切编辑

#### 1. 默认占位图

用户未上传头像 / 个人照片时，**两处统一展示同一张默认占位图**
（`src/static/default-photo.jpg`，由「案例.jpg」压缩而来，600×1067 / 138KB）。

| 应用场景 | 展示位置 | 展示规则 |
|---|---|---|
| **头像** | 顶栏 26px 圆形 + 个人界面 96px 圆形 | `object-fit:cover` + `object-position:center` 居中裁切 |
| **个人照片** | 个人界面 200px 宽的 3:4 竖版框 | 同上，居中裁切 |

回退逻辑统一走 `profileImgSrc(saved)`：

```js
saved 非空 → 用上传图（已是裁切后的定比例图）
saved 为空 → DEFAULT_PHOTO_URL（'/static/default-photo.jpg'）
```

提示区会标注「默认占位图」小标签；上传后标签消失。

> ⚠️ **占位图不用角标**：头像是圆形容器（`border-radius:50%` + `overflow:hidden`），
> 左下角角标会被圆弧裁掉 → 改为图片**下方**的标签，两处统一。

#### 2. 裁切规格

| 用途 | 裁切框比例 | 裁切框形状 | 最小输出尺寸 | 画布尺寸 |
|---|---|---|---|---|
| **头像** | **1:1**（正方形） | **圆形** | **512×512** | 420×420 |
| **个人照片** | **3:4**（竖版） | 矩形 | **720×960** | 330×440 |

「最小输出尺寸」= 保存入库的实际像素尺寸，保证在高分屏/大图场景下依然清晰。

**头像的裁切框是圆形**（与最终展示的圆形头像一致，所见即所得）：
- 裁切台加 `.crop-round`（`border-radius:50%` + `overflow:hidden`）→ 圆形外不再显示图片；
- 导出时用 `ctx.arc()` + `clip()` 按圆形裁剪，圆外保持白底
  （展示时圆形容器会再裁一次，肉眼无差别）。

个人照片的裁切框仍是 3:4 矩形。

#### 3. 裁切交互

选图后**自动打开裁切弹窗**（不再直接使用原图）：

| 操作 | 效果 |
|---|---|
| **拖动**（鼠标 / 触摸） | 移动图片位置；始终约束为「图片盖满裁切框」，**不留白**（`cropClamp()`） |
| **缩放**（滚轮 / 滑块 100%~300%） | 以裁切框中心为锚点缩放，1×~3× |
| 三分构图线 | 辅助对齐（`cropPaint()` 绘制）；圆形模式下圆外自动不显示 |
| **确认裁切** | 按最小输出尺寸导出 JPEG（质量 0.88），写入 `PROFILE_AVATAR` / `PROFILE_PHOTO` 并刷新预览 |
| **取消 / ✕** | **丢弃本次调整**，保留裁切前的暂存值，不影响已保存的数据 |

#### 4. 保存与取消的语义

```
选图 → 裁切器 → [确认裁切] → 暂存值更新 → [保存资料] → 落库
                     ↓
                 [取消] → 暂存值不变
```

- **裁切器的「确认」只是更新暂存值**，还需点「保存资料」才写入数据库；
- **裁切器的「取消」完全丢弃本次选择**，等同于没选过这张图；
- 「保存资料」一次提交 `{avatar, photo, status_text}`；
- 「清除」按钮把暂存值置空（预览立即回退占位图），保存后数据库字段为空，
  **下次渲染再次回退到占位图**。

#### 5. 提示文案规范（单行）

个人界面与裁切弹窗的提示文案**必须一行显示**，不允许换行撑高布局：

| 位置 | 文案 |
|---|---|
| 头像区 | `点击上传（JPG/PNG/GIF/WebP，≤512KB）` |
| 个人照片区 | `点击上传（JPG/PNG/GIF/WebP，≤2MB，自动压缩）` |
| 裁切弹窗 | `拖动调整位置 · 滚轮/滑块缩放 · 比例 1:1 · 输出 512×512` |

> 上方 label 已经写明「头像」/「个人照片」，提示里**不必重复**。

实现要点：

1. **提示行是 `display:flex` + `nowrap`**，文案包在 `.hint-text` 里
   （`overflow:hidden;text-overflow:ellipsis;white-space:nowrap;min-width:0`）——
   即使将来文案变长也只会省略号，不会换行。
2. **上传说明常驻，状态只作后缀**（关键约定）：
   ```
   点击上传（JPG/PNG/GIF/WebP，≤512KB） · 已裁切
   └────────── 基础上传说明（永远在） ──────────┘  └ 状态后缀
   ```
   早期实现用状态文案**整体覆盖**提示行，导致「已裁切待保存」时
   **上传说明整条消失** —— 用户就找不到怎么换图了。
3. **状态后缀一律 ≤5 字**：`正在裁切…` / `已裁切` / `已清除` / `已保存` /
   `格式不支持` / `图片过大` / `读取失败` / `仍然过大`。
4. **错误详情走 toast**，不挤占提示行（如「图片过大（512KB），请压到 512KB 以内」）。

各状态实测文案：

| 状态 | 头像区提示 | 照片区提示 |
|---|---|---|
| 未上传 | `点击上传（…≤512KB）` | `点击上传（…≤2MB，自动压缩）` |
| 正在裁切 | `点击上传（…） · 正在裁切…` | 同左 |
| 裁切完成待保存 | `点击上传（…） · 已裁切` | 同左 |
| 已保存后重开 | `点击上传（…）` | 同左 |
| 清除后 | `点击上传（…）` | `点击上传（…） · 已清除` |

#### 6. 个人照片上传流程

1. 点击照片区 → 选文件（前端先校验类型与大小）；
2. `compressProfilePhoto()` 压缩（长边 ≤1200px / JPEG 0.85）；
3. **进入裁切器** → 拖动/缩放 → 确认裁切；
4. 照片区内即时预览；
5. 点「保存资料」→ `POST /api/profile` 携带 `photo` → 落库；
6. 再次进入个人界面自动读回；点「清除」可移除（清除后需保存才生效）。

### 头像上传流程
1. 点击头像 → 选文件（前端先校验类型与大小，避免白跑接口）；
2. `FileReader` 读成 data URL → 弹窗内预览；
3. 点「保存资料」→ 提交 → 同步 `ME` 并刷新顶栏头像；
4. 再次选文件会替换；清空头像则顶栏头像隐藏。

#### ⚠️ 登录页的小眼睛必须写死尺寸（踩过的坑）

登录页 `login.html` 是**独立文件**，样式不与主页面共享，它有一条通用规则：

```css
button{width:100%; ...}   /* 登录按钮要撑满 */
```

我第一版写 `.pwd-eye{position:absolute;...}` 时**没声明 width** → 被通用规则继承成
`width:100%` → 绝对定位后按钮宽度 = 容器宽（实测 **288px**，等于整个输入框宽），
**整个盖在密码框上方**：

- 点密码框任何位置都点到按钮 → **密码无法输入**
- 按钮压在输入框上 → **显示错乱**

修法（双保险）：

1. 通用规则的 `width:100%` **收窄到 `#btn`**（只有登录按钮需要撑满）；
2. `.pwd-eye` 显式写 `width:28px;height:28px`（与 index.html 既有 `.pwd-eye` 视觉一致）。

> 🔴 **通用教训**：给按钮加绝对定位 + 图标时，**必须显式写死宽高**，
> 否则会被页面级的通用 `button{}` 规则撑大。
> 验证时除了测「点击能否切换」，还要测「**元素是否遮挡目标**」
> —— 用 `document.elementFromPoint()` 命中检查，而不是只看 `type` 有没有变。
> （本轮第一版验证只测了 `type` 切换，漏掉了遮挡检查，才让这个 bug 溜过去。）

### 二、登录失败锁定策略

| 参数 | 值 | 常量 |
|---|---|---|
| 冷却阈值 | 连续失败 **5** 次 | `LOGIN_FAIL_THRESHOLD` |
| 冷却时长 | **180 秒**（3 分钟） | `LOGIN_COOLDOWN` |
| 锁定阈值 | 连续失败 **10** 次 | `LOGIN_LOCK_THRESHOLD` |

**数据表** `login_attempts`（账号级，主键 username）：

| 列 | 说明 |
|---|---|
| `fail_count` | 累计连续失败次数 |
| `last_fail_ts` | 最后一次失败的 unix 时间戳（冷却窗口从它起算） |
| `locked` | 1 = 永久锁定，需管理员重置 |
| `last_ip` | 最后一次失败的来源 IP |

**判定流程**：

```
登录请求
  ├─ locked=1 或 fail_count ≥ 10 → 423 永久锁定（任何密码都拒绝）
  ├─ 密码正确 → 放行 + 【失败计数立即清 0】✅
  └─ 密码错误 → fail_count+1
       ├─ ≥10 → 423 永久锁定（需 admin 重置）
       ├─ ≥5  → 429 冷却 180 秒
       └─ <5  → 401 账号或密码错误
```

**三条关键设计**：

1. **密码成功一次 → 失败计数立即清 0**（`_login_record_success()` 执行
   `DELETE FROM login_attempts WHERE username=?`，删整行，含锁定标记）。
   已在 `ops/test_login_lock.py` 用例 6 固化为回归断言。
2. **冷却期内再试仍累加计数**（只是继续 429）。
   否则 5 次之后永远停在冷却 → **永远到不了 10 次锁定**，规则自相矛盾。
3. **冷却期内密码正确仍放行**。受限的是「密码错误次数」，不是「登录」本身 ——
   用户突然想起正确密码时不该被挡 3 分钟。实现上先验密码再判冷却。

**接口**：

| 接口 | 说明 |
|---|---|
| `POST /api/login` | 401 / 429（带 `Retry-After` 头）/ 423 |
| `GET /api/login/lock-status?username=xx` | 登录前查状态：`{blocked, retry_after, message}` |
| `GET /api/admin/login-locks` | 管理员查看锁定列表（含阈值与剩余秒数） |
| `POST /api/admin/login-lock/reset` | 管理员重置（清计数 + 解锁） |

### 三、登录页提示

- 输入账号时（防抖 300ms）自动查锁定状态并提示；
- 冷却期：黄色警告框「⏳ 密码错误次数过多，请在 **N** 秒后再试」，每秒倒计时，禁用登录按钮；
- 永久锁定：红色提示「🔒 …账号已锁定，请联系管理员重置密码」；
- **每 5 秒轮询一次**状态 —— 管理员重置后，登录页提示自动消失、按钮恢复
  （否则用户要手动刷新页面才知道）。

> ⚠️ **admin 自己被锁了怎么办？**（`require_admin` 同样要 token，进不去）
> 可直接执行 `DELETE FROM login_attempts WHERE username='<账号>';` 解锁。

## 五点十七、看板与板块可见性失效（架构权限 filter 失效）

**现象**：普通用户登录后仍能看到**全部看板和板块**，架构管理里明明做了归属配置。

### 一、先分清「谁能看」和「谁能改」

本项目的看板/板块可见性由后端 `user_allowed()` 统一判定，返回
`(boards, columns)`；前端只是消费 `/api/me`、`/api/cards` 的结果。
**排查第一步永远是：直接调接口看后端给的是什么**，不要看界面：

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8100/api/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"<账号>","password":"<密码>"}' | python -c "import sys,json;print(json.load(sys.stdin)['token'])")

curl -s http://127.0.0.1:8100/api/me -H "Authorization: Bearer $TOKEN" \
  | python -c "import sys,json;d=json.load(sys.stdin);print(len(d['boards']),[b['board_id'] for b in d['boards']])"
```

- 接口返回**全部**看板 → 问题在后端权限计算（往下看第三节）；
- 接口只返回部分，但界面全都有 → 问题在前端渲染（看 `ME.boards` 是否被绕过）。

### 二、四个根因（2026-10-30 定位）

| # | 根因 | 表现 | 修法 |
|---|---|---|---|
| 1 | **fail-open 空值语义** | `_dept_stage_boards()` / `_group_boards()` 用 `None` 同时表达「不收窄」「不适用」；成员无架构归属时三层全返回 `None` → 可见集合 = 全部 | 架构层改为**永远返回显式集合**（可为空），`None` 只留给超级管理员 |
| 2 | **账号白名单默认 `*`** | 新建账号 `allowed_boards='*'`（=不额外收窄），与 1 叠加后架构过滤形同虚设 | 保持 `*` 语义不变，但必须在架构层 fail-closed 之后才叠加 |
| 3 | **负责范围层恒为空** | 部门/中心节点的绑定读 `workgroups.boards`，该字段对部门/中心恒空 → 负责人范围永远是空集 | `_node_bound_boards()` 按节点类型派生（中心=全部 / 部门=`board_config.dept_node_id` / 小组=手工绑定） |
| 4 | **工作组白名单失效** | 白名单里混入「归属部门自有看板」→ 集合永远覆盖前两层，本层收窄不了任何东西 | 只取**显式绑定**（`merged if bound else None`） |

外加两个口径不一致：

- **超级管理员两套口径**：`user_allowed` 用「账号名 == 'admin'」，
  `require_admin` 用「角色 == 'admin'」→ `role=admin` 的账号被架构过滤，
  却又能调全部管理接口。已统一到 `is_admin()`（角色口径）。
- **读接口没有可见性校验**：评论 / 操作日志 / 子事项 / 子卡片树只有登录校验，
  「前端看不到、API 能读」。已补 `check_card_access()`。

### 三、判定链（改完后的唯一真相）

```
⓪ admin（role=admin）→ 全部可见，不做架构过滤
① 架构授权集（fail-closed）
     归属部门层：公共看板（未归属部门 / 归属中心）+ 挂靠部门拥有的看板
                 挂靠中心 = 管理层全范围；无归属 = 只剩公共看板
     负责范围层：负责人额外拥有其负责范围（节点+后代）绑定的看板
     工作组层  ：显式白名单才收窄
② 账号白名单 allowed_boards 与①取交集（只能收窄，不能越权授予）
③ 板块白名单 allowed_columns 在可见看板内继续收窄
```

### 四、手工验证

```bash
# 1) 架构任命一个成员到某部门（【架构管理】→ 岗位与任职）
# 2) 该成员登录后：/api/me 只应返回该部门拥有的看板
# 3) 换一个部门的人登录：看板集合应完全不同
# 4) 未被任命的账号登录：看板集合应为空（fail-closed）
# 5) admin 登录：应看到全部看板（不受架构过滤）
```

回归测试：`ops/test_perm_scope.py`（27 项断言，端到端）。
浏览器核对：`ops/ui_check_perm.py <账号> <密码>`（Chrome headless + CDP），
打印 `ME.boards`、部门树计数、板块 tab 与空状态提示。

### 五、别把「账号白名单」当成授权开关

账号级 `allowed_boards` 现在**只是收窄器**：它只能在架构授权范围内再砍一刀，
不能凭空授予架构之外的看板。要给某人开某个看板，正确做法是
**在【架构管理】里把他任命到拥有该看板的部门/小组**。

### 六、顺带修掉的性能问题：数据库连接按线程复用

改造过程中实测发现：一次权限判定要查 20 多个小表，耗时 25ms，
根因不是算法，而是**每个查询都新建一个连接**：

```
1 conn + 1 stmt     1.153 ms      ← 新建连接 + 执行第一条语句（Windows 文件锁开销）
1 conn + 10 stmts   1.151 ms      ← 同一连接上跑 10 条：几乎免费
1 conn + close      0.062 ms      ← 光开光关很便宜
```

已改为**每线程复用一个连接**（`threading.local`），实测：

| 指标 | 改前 | 改后 |
|---|---|---|
| `dbq('SELECT 1')` | 1.075 ms | 0.014 ms |
| `user_allowed()`（普通用户） | 14~19 ms | 0.3~0.5 ms |
| `GET /api/me` | 12.5 ms | 1.7 ms |

> ⚠️ **改连接管理时要记住三件事**：
> 1. `dbq()` / `dbe()` **不能再关连接**（否则把线程的连接关掉 → 后续请求报
>    "Cannot operate on a closed database"）；
> 2. 出错必须 `rollback()` —— 连接是复用的，不回滚会把未提交事务留给该线程的后续请求；
> 3. 批量接口（`/api/import`、`/api/import/xlsx`）原本的 `finally: conn.close()`
>    要改成 `except → rollback`。
>
> 读新鲜度没问题：Python sqlite3 默认 isolation_level 下 SELECT 不开事务，
> 每次读都看到最新提交数据（测试里直接改库，服务端立刻能读到，已验证）。

## 五点十八、复制（四层）+ 周数维度

**需求**：看板 / 板块 / 主事项 / 子事项四个层级都能复制；复制后重新选择上级归属；
主事项与子事项新增【周数】维度（自然周，周一~周日）；筛选栏加周数多选。

### 一、复制的入口与归属重选

| 层级 | 入口 | 归属重选项 | 权限 |
|---|---|---|---|
| 看板 | 【看板管理】行内「📋 复制」 | 归属部门 / 年份 / 属性 / 状态 | 仅管理员 |
| 板块 | 板块头部「📋 复制」 | 目标看板 + 创建日期 / 性质 / 归属年份 | editor + 目标看板可见 |
| 主事项 | 事项编辑弹窗页脚「📋 复制」 | 目标看板 + 目标板块 + 周数 | editor + 目标看板/板块可见 |
| 子事项 | 同上（子事项用同一个编辑弹窗） | 目标看板 + 目标板块 + **所属主事项**（必填） | 同上 + 目标主事项可见 |

副本规则：全新记录（不与原记录共享数据）、标题默认「原标题（副本）」可编辑、

**只复制本级不复制下级内容**。

### 二、权限过滤怎么落地（重点）

复制弹窗的三个下拉**不能**用全量数据，必须全部来自已按权限过滤的接口：

```js
目标看板     ← ME.boards                     （/api/me，已过滤）
目标板块     ← /api/boards/{id}/columns      （visible_columns，看板可见 + 板块白名单）
所属主事项   ← /api/cards?board_id=…&column=…（列表接口本身已过滤，且只取主事项）
```

服务端再校验一遍（**前端过滤只是体验，服务端才是边界**）：

```python
check_card_access(req.card_id, username)      # 源事项可见
check_board_access(req.board_id, username)     # 目标看板可见 + 可编辑
check_column_access(req.board_id, req.column_id, username)   # 目标板块在白名单内
perm_pass(parent_row, boards, columns)          # 目标主事项可见
```

任一不满足 → 403；子事项副本没选所属主事项 → 400。

### 三、周数怎么算

```python
iso = date(int(y), int(m), int(d)).isocalendar()
label = '%d年第%d周' % (iso[0], iso[1])
```

- 自然周 = **周一 ~ 周日**；
- 归属年按 **ISO-8601**（该周**周四**所在年份）→ 与 Excel 的周编号一致，
  所以 `2027-01-01` 属于 `2026年第53周`，别用「年内第几天/7」的土办法算；
- 默认取**创建日期**所在周，创建时可手动指定（`2026-41` 会归一成 `2026年第41周`）；
- 编辑时清空 → 回落到按创建日期重算。

### 二、人员筛选锚定在**负责人维度**（两者取交集）

**旧实现的根因**：人员筛选的「套用为负责人」分支往 `ownerFilter` 这个
`<select>` 里**注入一个自定义 option** 并把 `sel.value` 改成逗号分隔的人员名单：

```js
let opt=sel.querySelector('option[data-multi="1"]');
opt.value=names; opt.textContent='负责人：'+persons.join('、');
sel.value=names;          // ← 直接覆盖了用户自己选的负责人
```

于是两个控件抢同一个 `value`：选人员会覆盖负责人条件，改负责人又会清掉人员条件，
表现为「重复筛选 / 条件互相覆盖」，且两者无法组合。

**新模型**：

| | 指向的字段 | 前端状态 | 提交参数 |
|---|---|---|---|
| ~~负责人下拉~~ | ~~`owner`~~ | ~~`ownerFilter.value`~~ | ~~`owner=`~~ **已下线（2026-11-02）** |
| 人员筛选 | `owner`（**同一字段**） | `PERSON_SEL`（独立 Set） | `person=` |

服务端：`person` 命中集合 ∩ `owner` 命中集合（AND）。
person 集合内部为「任一命中」（逗号分隔），与 owner 多值口径一致。

> 语义后果：`负责人=甲` + `人员=乙` → 空结果（一条事项的负责人同时是甲和乙）。
> 这是交集语义的必然结果，也是需求要的行为 —— 两条件指向同一字段。

> 📌 **2026-11-02 后续**：既然两者指向同一字段、又互相重复，
> **独立的「全部负责人」下拉已整块下线**（见 5.1 节）——
> 现在人员筛选独占负责人维度，「无负责人」并入人员面板（哨兵 `__no_owner__`）。
> 后端 `owner` 参数保留（外部 API 调用方仍可用），但前端不再提交。

### 三、人员树状展开异常（三个独立根因）

1. **人员条目渲染在可折叠容器之外**
   旧代码把 `memberHtml` 拼在 `<div id="tp_children_...">` **外面**，
   所以折叠父节点时人员条目**依然显示** —— 这就是「展开/收起行为异常」的直接表现。
   修法：人员移入 `tp_children_{id}` 容器内。

2. **父节点重复列出全部后代人员**
   后端 `_collect_node_members()` 返回的是「本节点 **+ 全部后代**」的人员，
   于是同一个人会在父节点和子节点各出现一次（树上看起来层级错乱）。
   修法：后端给每条成员记录加 `node_id`（实际任职节点），
   前端按 `m.node_id === n.id` 过滤 → 每个人只挂在真正任职的那一层。

3. **展开状态放在 `TREE_PICK` 里，重开即丢**
   `expanded:new Set()` 每次 `openTreePick` 都重建 → 筛选变更后重开弹窗跳回根节点。
   修法：改用全局 `TREE_EXPANDED`（按节点 id），打开时恢复、切换时同步；
   收起父节点时清理后代标记，避免「收起后再展开，子节点莫名其妙是展开的」。

**顺带修复**：
- person 模式下节点框原为 `.tp-box-na`（置灰死元素）→ 改为可点击级联（`tp-box-node`），
  并显示三态（全选 ✓ / 半选 ▣ / 未选）。
  ⚠️ `setBox()` 会覆盖 `className`，必须保留 `tp-box-node`，否则节点框又变死元素。
- 勾选人员后要 `paintAll()` 重绘整棵树，否则父节点三态不同步。
- 同名人员出现在多个节点时 `id="tp_pbox_姓名"` 会冲突 → 改用 `data-pbox` 属性选择器。
- 架构数据刷新（`ensureOrgTree(true)`）后重绘打开中的选择器。

## 六点五、安全红线（继承自旧 WSL 时代，依然有效）

这几条是旧架构时期踩坑总结出来的，迁到云上后**依然成立**：

1. **同步只覆盖代码，永不碰** `app.db`（服务器真实库）、`venv/`、`/etc/tapd-workbench.secret`。禁用 `rsync --delete`。
2. **数据库只有服务器上那份是真的**。本地 `src/app.db` 只是副本，改它不会生效，别拿它当运行库。
3. **重启只走 `systemctl restart tapd-web`**。`kill` 会被 systemd 3 秒拉起，`nohup` 手动起必绑定失败。crash-loop 时先 `systemctl stop`。
4. **改后端先语法检查**：`python -m py_compile src/app/app.py src/app/init_db.py`，不过则禁止同步/重启（语法错会 crash-loop，端口不可用、日志刷屏）。
5. **验证以「特征字符串 grep」为准**，版本注释只是辅助（忘了更新注释会误判"已生效"，实际跑的是旧代码）。
6. **`init_db()` 每次启动都跑**（幂等：`CREATE TABLE IF NOT EXISTS`；仅当 cards 表为空才重导 CSV）。所以正常重启不动数据，但**清空运行库再重启会从 CSV 自动重灌**——清库前先确认是否有意为之。

## 七点五、关于「热重载」——一个曾经很坑的坑

### 现在的行为

| 环境 | 机制 | 延迟 |
|---|---|---|
| 本地 Windows | `dev-watchdog.py` 轮询文件指纹 → 重启 uvicorn | **约 2 秒** |
| 服务器 Linux | `sync.sh --dev` 推送后 `systemctl restart` | 约 3~5 秒（含上传） |

两端都是**显式重启**，行为一致、可预期。

### 曾经的问题（已根治，但值得知道）

uvicorn 的 `--reload` 在 **Windows 上**会这样：

```
WARNING:  StatReload detected changes in 'app\app.py'. Reloading...
（日志到此为止，再无输出）
```

**reloader 进程卡死了**。此时：
- 旧 worker 仍在运行 → 页面能打开、能登录，**看起来一切正常**
- 但代码永远不更新
- 更坑的是：**第二次修改连 "detected changes" 都不会再出现**，因为 reloader 已经死了
- 换 watchfiles 替代 statreload 也一样挂

这个现象极具迷惑性——你会以为是代码写错了、参数没生效、缓存问题，浪费大量时间。

### 怎么判断代码到底生效没有

**别看日志，看结果**。可靠做法是加一个特征探针：

```python
@app.get('/api/__probe__')
def __probe__():
    return {'marker': 'V1'}   # 改成 V2 看返回的是不是 V2
```

或者用旧文档里的**特征字符串 grep** 法：

```bash
curl -s http://127.0.0.1:8100/ | grep -c "你这次改动引入的唯一字符串"
```

### 经验

**开发环境不要依赖 `--reload` 这种隐式机制**，它在不同平台行为不一致且失败时静默。
显式重启虽然多花 2 秒，但**可预测、可观测**——出问题一眼能看出是重启了还是没重启。

### 一、顶栏左上角那个「没用的小圆点」

**现象**：页面顶部左侧、标题行上方浮着一个孤零零的蓝色小圆点，什么都不干。

**根因**：那个圆点是**个人状态栏**的状态点（`.my-status-bar .ms-dot`）。
个人状态栏的 HTML 带了 `hidden` 属性（状态文字为空时 JS 设 `bar.hidden=true`），
但 **CSS `.my-status-bar{display:flex;...}` 的优先级高于浏览器对
`[hidden]` 的默认 `display:none`** → `hidden` 形同虚设，
容器照常显示 → 状态文字被 `.ms-text:empty{display:none}` 藏掉了，
只剩那个圆点孤零零浮在左上角。

**修法**：给这条规则显式兜底（项目里已有多处同类兜底，如 `.filter-clear[hidden]`）：

```css
.my-status-bar[hidden]{display:none}
```

> 💡 **通用经验**：给元素写 `display:flex/grid/inline-flex` 又要用 `hidden`
> 属性控制显隐时，**必须**补一条 `[hidden]{display:none}`。
> 浏览器 UA 样式表的 `[hidden]` 优先级最低，会被任何作者样式覆盖。

```js
  const ids=[];
```

## 五点二十二 · 搜索框无法输入中文（IME 兼容）（2026-11-02）

**现象**：树弹窗的搜索框打不出拼音 —— 输入第一个字母就没反应 / 拼音上不了屏。

### 根因（两个叠加）

#### ① 每次输入都重建整个面板 DOM → 输入框节点被销毁

早期实现里 `tpSearch()` 调 `renderTreePick()`，后者用 `p.innerHTML = ...`
**重建整个面板**（工具栏 + 搜索框 + 树 + 底栏）。

后果：
1. 输入框 DOM 节点被销毁重建 → **焦点丢失**、光标位置丢失；
2. 更致命：中文输入法的**拼音组合状态**（拼音串 + 候选窗口）绑定在
   **原生 input 元素**上 —— 元素被替换后组合被打断，
   于是表现为「只能打第一个字母」。

修法：拆出 `renderTreePickBody()`，**只替换树内容区 `#tp_body` 的 innerHTML**，
工具栏 / 搜索框 / 底栏的 DOM 节点保持不变。

#### ② 组合期间用拼音去过滤 → 树被清空

IME 组合期间（拼音还没上屏）`input.value` 是**拼音字母**而不是最终汉字。
若此时触发过滤，`"wutingting"` 匹配不到任何人 → 树上一个人都不剩。

修法：用 `compositionstart` / `compositionend` + `input` 事件的 `isComposing`
**双重判定**，组合期间完全不刷新树，等 `compositionend` 拿到最终汉字再过滤。

#### ③（隐蔽坑）内联事件处理器访问不到顶层 `let` 变量

最初用内联属性绑定：

```html
<input oninput="tpSearchInput(this.value)"
       oncompositionstart="tpSearchCompositionStart()">
```

而标志位写作 `let TP_COMPOSING = false;`。

> ⚠️ **顶层 `let` / `const` 声明的变量不在 `window` 上**，
> 而**内联事件处理器的作用域链是 element → form → document → window**，
> **不经过 script scope** → 处理器里访问 `TP_COMPOSING` 抛 ReferenceError →
> 标志位永远设不进去 → 组合期间照样过滤 → 树被清空。

表现极具迷惑性：`Runtime.evaluate` 里能读到/改到该变量（它走 script scope），
但页面上的内联处理器改不了它 —— 单元测试全绿、实际功能却是坏的。

修法：
- 标志位改用 **`var`**（顶层 `var` 会挂到 `window`，任何作用域都能访问）；
- 事件改用 **`addEventListener`** 绑定（作用域正确，且能拿到真实 event 对象）。

### 最终形态

```js
var TP_COMPOSING=false;          // var：挂到 window，内联/闭包都能访问

function bindTpSearch(){
  const inp=document.getElementById('tp_search');
  if(!inp||inp.__tpBound)return;
  inp.__tpBound=1;
  inp.addEventListener('compositionstart',()=>{ TP_COMPOSING=true; });
  inp.addEventListener('compositionend',e=>{
    TP_COMPOSING=false;
    tpSearch((e&&e.target&&e.target.value)||inp.value);
  });
  inp.addEventListener('input',e=>{
    if(TP_COMPOSING||(e&&e.isComposing))return;   // 组合中 → 忽略
    tpSearch(inp.value);
  });
  inp.addEventListener('keydown',e=>{ if(e.key==='Escape')tpSearch(''); });
}
```

### 顺带改进的搜索体验

| 改进 | 说明 |
|---|---|
| 自动展开到命中路径 | 搜索时子树里有匹配人员的节点自动展开（`tpSubtreeHasMatch`），否则命中的人藏在折叠容器里看不见 |
| 无匹配空态提示 | 一个人都没匹配上时显示「未匹配到「xxx」的人员」，而不是留一片空白 |
| 关键词未变则跳过重绘 | IME 的 `compositionend` 之后常会补一个 `input` 事件 → 避免重复重绘 |

## 五点二十三 · 看板 / 板块负责人：管理权（不是可见性开关）（2026-11-02）

> 用户要求：「看板管理中只配置负责人，不配置参与人，其他权限统一通过架构管理的看板绑定来。
> 此外，负责人选择可以参照外部人员筛选的树状图。」
> 并拍板：**看板负责人 = 有权修改看板基本信息**；**板块负责人放在板块编辑里配置**。

### 一、语义变更：负责人不再是 ACL 收窄条件

| | 旧语义（已下线） | 新语义（现行） |
|---|---|---|
| 看板 `owner` | 配了就**只有负责人 + 参与人**可见 | **负责人 = 管理权**：可改该看板基本信息（归属部门 / 属性 / 状态 / 备注），**不影响可见性** |
| 板块 `owner` | 同上（且前端无入口） | **负责人 = 管理权**：在【板块编辑】里配置，可改该板块基本信息 |
| 参与人 `participants` | 可配多人，命中者可见 | **整体下线**（字段保留兼容，传入即被忽略并清空） |
| 谁能看见看板 | 架构链 **∩** ACL | **只由【架构管理】的看板绑定决定**（唯一出处） |

**为什么改**：ACL 与架构绑定是两套并行的可见性规则，取交集后会出现
「架构里明明绑了看板，人却看不到」的困惑。收敛为单一出处后，可见性只有一个解释。

### 二、权限链（现行）

```
user_allowed()
  ① 架构授权集（fail-closed）
     归属部门层 ∪ 负责范围层 ∩ 工作组绑定层
  ② 账号级看板白名单（users.allowed_boards）取交集
  ③ 账号级板块白名单（users.allowed_columns）在可见看板内收窄板块
  ④ 负责人层 —— **不参与可见性判定**，只提供「能不能改这个看板/板块的基本信息」
```

### 三、谁能改什么

| 操作 | 管理员 | 看板负责人 | 板块负责人 | 其他 |
|---|---|---|---|---|
| 改看板基本信息（归属部门/属性/状态/备注） | ✅ | ✅（自己负责的看板） | ❌ | ❌ 403 |
| 改板块基本信息（名称/年份/性质） | ✅ | ❌ | ✅（自己负责的板块） | ❌ 403 |
| **指定**负责人（自己或他人） | ✅ | ❌ 403 | ❌ 403 | ❌ 403 |
| 新建看板 / 批量应用 / 删除所选 | ✅ | ❌（入口隐藏） | ❌ | ❌ |

> ⚠️ **管理权不放大可见性**（fail-closed）：把某人设为负责人，
> 若他本不在架构授权范围内，**仍然看不到**该看板 —— 否则「负责人」就成了越权后门。
> （实测见 `ops/test_owner_scope.py` 用例5）

### 四、接口

| 接口 | 权限 | 说明 |
|---|---|---|
| `PUT /api/boards/{board_id}/acl` | 管理员 | 设看板负责人。`participants` 字段保留兼容，**传入即被清空** |
| `PUT /api/columns/{col_key}/acl` | 管理员 | 设板块负责人（同上） |
| `POST /api/board-config` | 管理员 **或该看板负责人** | 新建看板配置 |
| `PUT /api/board-config/{cid}` | 管理员 **或该看板负责人** | 改看板配置 |
| `DELETE /api/board-config/{cid}` | 管理员 **或该看板负责人** | 删看板配置 |
| `PUT /api/columns` | editor **且**（管理员 或该板块负责人） | 改板块；`owner` 字段仅管理员可写（`__CLEAR__` = 清除） |

`/api/me` 新增两个字段：`managed_boards` / `managed_columns`（我是负责人的看板/板块）——
前端据此决定「看板管理」入口对非管理员是否显示。

### 五、前端

**看板管理弹窗**（`renderAclSection`）：

- 只有「看板负责人」一个字段，**参与人整块删除**；
- 负责人不再是 `<select>` 下拉 → 改为 **🌳 树状图单选**
  （复用筛选栏「👤 人员」那套 `ORG_TREE` + `pickMode:'person'` 架构树）；
- 树里选的是**姓名**，负责人字段存的是**账号** → 回填时按姓名反查账号
  （`bcAccountByName`）；
- 展示为 chip，显示「姓名(账号)」。

**板块编辑弹窗**（`columnModal`）：

- 新增「板块负责人」字段（仅管理员可见与可改），同样用树状图单选；
- 板块标题的 `data-owner` 属性带回负责人账号，编辑时回填。

**树弹窗的 `requireAccount` 模式**（负责人场景专用）：

- 树里**未开通登录账号的人**置灰、不可选，并标注「（未开通账号）」——
  25 名成员里有 20 名没开通账号，让他们可选等于「配了个空」。
