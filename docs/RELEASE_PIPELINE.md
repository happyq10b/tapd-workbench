# TAPD Workbench 三环境开发与发布流程

> 版本：2026-11-07（r89）｜ 适用：本地开发 → 服务器开发 → 服务器生产

---

## 一、三环境总览

| 环境 | 访问地址 | 服务器目录 | systemd 服务 | 端口 | 数据库 | nginx 入口 |
|---|---|---|---|---|---|---|
| 本地开发 | http://127.0.0.1:8100 | `E:\WB缓存\2026-10-26-15-55-08\src` | `local-ctl.py` 管理 | 8100 | `src\app.db`（离线副本） | 无 |
| **服务器开发** | **https://123.207.252.195:8443** | `/opt/tapd-dev` | `tapd-dev` | 8001 | `/opt/tapd-dev/app.db` | 8443 → 8001 |
| 服务器生产 | https://123.207.252.195 | `/opt/tapd-workbench` | `tapd-web` | 8000 | `/opt/tapd-workbench/app.db` | 443 → 8000 |

- 服务器开发与生产**完全独立**（目录/数据库/venv/systemd 服务），可同时运行，互不影响。
- 两个环境共用同一套域名与自签证书；云防火墙仅对**公司办公网 + VPN 出口 IP** 白名单放行（80/443/8000/8443/22）。
- 生产库每日一致性备份：`/var/backups/tapd-workbench/app.db.*`，保留 7 天。

## 二、日常开发循环（本地 → 服务器开发）

```
① 本地改代码（src/）
② 本地验证门禁：    cd ops && python verify.py     （7 项检查，签发 2 小时有效凭证）
③ 同步到开发环境：  cd ops && ./sync.sh --dev      （推代码 → 重启 tapd-dev → 健康检查）
④ 浏览器验证：      https://123.207.252.195:8443   （生产全程不受影响）
```

- `sync.sh --dev` **不碰生产**：目录是 `/opt/tapd-dev`，服务是 `tapd-dev`，数据库保留 dev 自己的。
- 改一轮代码 → 重跑 ②③ 即可，验证凭证 2 小时内不用重新生成（改了代码会自动失效强制重验）。
- 本地库覆盖开发库（把本地造的测试数据带上去）：`./sync.sh --db-local`（仅允许对 dev，双重确认）。
- 直接在服务器上改过 dev 代码？先 `./sync.sh --pull-dev` 拉回本地再继续，否则会被覆盖。

## 三、数据库同步策略（核心）

系统用 SQLite 单文件库（`app.db` + WAL），代码内置 `init_db()` 幂等建表迁移。三类"数据移动"场景与工具：

### 3.1 生产数据 → 开发环境（发布前验证用，最常用）

```bash
ssh -F ops/secrets/sshcfg tapd "tapd devdb-sync"
# 或 服务开关.bat → [F] Data-Sync
```

- 原理：`sqlite3 backup API` 一致性快照（**运行中 prod 不停服**），覆盖 dev 库；dev 停机约 5 秒。
- 效果：dev 库 = 生产库某时点完整副本，用真实数据量验证新功能。
- **注意**：这会覆盖 dev 现有数据（dev 库定位就是"生产数据的演练场"，无独立价值数据）。回迁后 dev 里新造的测试数据消失。

### 3.2 本地数据 → 开发环境

```bash
cd ops && ./sync.sh --db-local     # 双重确认后覆盖 /opt/tapd-dev/app.db
```

- 适用：新功能依赖本地精心构造的测试夹具时。
- **禁止**把本地库推生产——脚本层面已锁定 `--db-local` 只指向 dev。

### 3.3 发布时的生产库处理（停服窗口内）

表结构变更**不需要手工迁移**：新代码启动时 `init_db()` 自动执行幂等 `CREATE TABLE IF NOT EXISTS`（只增列/表，不删旧数据）。
发布流程中停服的目的因此是：
1. 保证快照一致性（WAL 落盘、无并发写入）；
2. 避免新旧代码/表结构并存期出现脏写；
3. 缩短"半新半旧"状态到零（停服后才推代码）。

若某次发布需要**数据级**变更（批量改值、清洗），约定：写成幂等 SQL 补丁放 `ops/migrations/NNN-描述.sql`，在停服窗口、启动新代码**之前**手工执行一次，并在 HANDOFF.md 登记已执行。

## 四、发布流程（开发 → 生产，含停服）

日常发布只需一条命令，向导会带你走完全程：

```bash
cd ops && ./sync.sh --prod
```

实际执行链条（每步都有输出确认）：

```
[确认]  提示已在 dev 完成验证，输入 yes 才继续（取消则不做任何变更）
[0/4]   服务器自动拍【发布快照】= 代码 tar 包 + 一致性数据库
        → /var/backups/tapd-workbench/release/prod/<时间戳>/
[1/4]   停止 tapd-web（进入发布窗口，用户不可访问）
[2/4]   推送代码 app/ static/ manage_users.py requirements.txt（停服窗口内）
[3/4]   启动 tapd-web（启动时 init_db 自动迁移表结构）
[4/4]   健康检查（HTTP 200）→ 人工浏览器验收 https://123.207.252.195
```

**停服时长 ≈ 推代码时间，通常 10~30 秒。** 建议发布窗口选在低峰时段。

### 发布前检查清单（人工确认）

- [ ] dev 环境（8443）完整走一遍受影响功能
- [ ] 已做生产数据回迁（`tapd devdb-sync`）后复验过
- [ ] `verify.py` 7 项全过（sync.sh 强制门禁，凭证 2 小时内）
- [ ] 低峰时段，知会使用者

## 五、回滚机制

**入口：双击 `发布回滚.bat`**（菜单式），或 SSH 后用 `tapd` 工具箱。

```
发布回滚.bat
  [1] 列出生产快照          [3] 立即拍生产快照
  [2] 列出开发快照          [4] 立即拍开发快照
  [5] 回滚生产 → 选快照 → 输入 yes 确认
  [6] 回滚开发 → 选快照 → 输入 yes 确认
```

服务端实际动作（`tapd rollback <prod|dev> <快照名>`）：

```
1/5 回滚前自动再拍一次快照（rollback-before-<名>，保证可反复回滚/后悔）
2/5 停服
3/5 恢复代码（tar 解包覆盖）+ 恢复数据库（快照副本覆盖）
4/5 启动
5/5 健康检查（HTTP 200，异常打印日志排查命令）
```

全程约 20 秒。**快照同时包含代码与数据库**——回滚不出现"旧代码配新库"或反之的错位。

等价手工命令（SSH）：

```bash
tapd rollbacklist prod          # 列快照
tapd rollback prod 20261107-110000
tapd status                     # 回滚后复查双环境
```

另有独立兜底：`tapd restore <文件>` 可从每日例行备份恢复生产库；`/var/backups/tapd-workbench/` 保留 7 天例行备份 + 全部发布快照。

## 六、停服 / 恢复开关

**双击 `服务开关.bat`**：

| 键 | 动作 | 说明 |
|---|---|---|
| [A] / [B] | 生产 停服 / 恢复 | 发布窗口手动控制；[A] 后用户不可访问 |
| [C] / [D] | 开发 停服 / 恢复 | dev 独立停启 |
| [E] | 开发重启 | 服务器上直改代码后生效用 |
| [F] | 生产数据回迁开发库 | 见 §3.1 |
| [6] | 双环境状态 | 服务状态 + 本机健康检查 + 库大小 |
| [1]~[5] | 本地开发服务 启/停/重启/状态/开浏览器 | 不变 |

等价 SSH 命令：`tapd stopprod | startprod | stopdev | startdev`。
**停服期间用户访问表现为连接失败**（nginx 返回 502），恢复后立即正常，无需清缓存。

## 七、注意事项与风险控制

1. **白名单即边界**：80/443/8000/8443/22 仅对公司办公网与 VPN 出口放行。新出口 IP 上不去时，先在腾讯云轻量服务器防火墙加规则（或找管理员），不要临时关闭白名单。
2. **永远不要直接在生产库上做实验**：任何"先在生产试试"的念头都改为 → dev 回迁 → dev 验证 → 正式发布。
3. **发布中断电/断网怎么办**：发布链条任何一步中断，服务要么未动（确认前取消）、要么已停（重新执行 `sync.sh --prod` 完成剩余步骤，代码已在服务器上）。最坏情况走 `发布回滚.bat`。
4. **快照会积累**：`release/<env>/` 不自动清理；每个约 2.3MB，量大后可手工删旧的（保留最近 5 个）。
5. **dev 库无保护价值**：dev 数据随时可被 `devdb-sync` 覆盖——不要在 dev 存唯一副本数据。
6. **两小时凭证**：`sync.sh` 门禁拒绝过期凭证是特性不是故障——代码变了必须重验。
7. **服务器直改代码**：`sync.sh` 有行数差检测（>5 行强制确认）；正确姿势是 `--pull` / `--pull-dev` 拉回本地改。
8. **日志位置**：生产 `journalctl -u tapd-web`；开发 `/var/log/tapd-dev.log`（bat [8] 可看 15 秒片段）。

```
日常开发:  python verify.py → ./sync.sh --dev → 看 8443
发布前:    tapd devdb-sync（真实数据复验）
发布:      ./sync.sh --prod（向导：确认→快照→停服→推码→启动→健康检查）
验收:      https://123.207.252.195 人工过一遍
出问题:    发布回滚.bat → [5] → 选快照 → yes（20 秒回到发布前）
```
