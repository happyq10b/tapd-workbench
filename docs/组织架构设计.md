# 组织架构模块 · 数据模型与接口设计

> 版本：2026-10-29　　适用代码：`src/app/init_db.py`、`src/app/app.py`、`src/static/index.html`
> 回归测试：`ops/test-org.js`（97 条）

---

## 一、需求与设计目标

### 1.1 业务要求

| 维度 | 要求 |
|---|---|
| **架构层级** | 中心为顶级节点 → 部门 → 常规小组；**中心与部门均可设立专项小组** |
| **岗位角色** | 小组配**组长 / 组员**；部门配**部门长 / 部门骨干**；中心配**中心负责人 / 总经理 / 中心骨干** |
| **多重归属** | 同一人员可同时挂在不同组织架构节点下（一人多岗、多组织任职） |

### 1.2 旧模型的不足（为什么必须新建表）

旧表 `workgroups` 只能表达「一棵没有类型的树 + 每节点一个 leader 字符串」：

| 旧模型 | 局限 |
|---|---|
| `leader TEXT` 单字段 | 只能记一个人，无法表达「部门长 + 部门骨干」并存；无法区分中心负责人 / 总经理 |
| 无节点类型 | 靠 `parent_id` 猜层级，「专项小组」（跨部门临时组）与「常规小组」无法区分 |
| `team_members.workgroups` 分号串 | 无外键、无角色信息；节点改名即断链；无法表达「一人多岗」 |
| 成员归属挂在**组**上 | 无法表达某人同时是某部门骨干、又是某专项组组长 |

因此新建三张表承载新模型，**旧表 `workgroups` 保留**作为兼容视图 —— 旧权限逻辑
（`_leader_boards` / `_group_boards`）零改动继续可用，新旧模型通过 `_org_sync_legacy()`
双向同步。

## 二、数据模型

### 2.1 实体关系

```
                    ┌──────────────────┐
                    │  org_roles       │  岗位定义（按节点类型）
                    │  node_type       │
                    │  role_key        │
                    │  unique_slot     │
                    └────────┬─────────┘
                             │ 按 (node_type, role_key) 引用
                             │
   ┌─────────────────────────┴──────────────────────────┐
   │                                                    │
┌──▼────────────────────┐              ┌────────────────▼───────────────┐
│  org_nodes            │  1        N  │  org_appointments              │
│  id                   │──────────────│  id                            │
│  name                 │              │  node_id      ──┐              │
│  node_type  ◄─────────┼──┐           │  member_id   ──┼──┐           │
│  parent_id (自引用树)  │  │           │  role_key       │  │           │
│  wg_id  ──► workgroups│  │           │  is_primary     │  │           │
│  function            │  │           │  UNIQUE(node,member,role)      │
│  description         │  │           └────────────────┬──┘──┬────────┘
│  UNIQUE(parent,name) │  │                            │     │
└──────────────────────┘  │                            │     │
                          │                    ┌───────▼┐  ┌▼─────────┐
              ┌───────────┘                    │members │  │ 成员任职  │
              │                                │team_.. │  │ 视图接口  │
              ▼                                └────────┘  └──────────┘
   ┌──────────────────────┐
   │  workgroups（旧表）  │  ← 兼容视图：板块绑定 / 权限判定仍读它
   │  id, name, parent_id │
   │  leader, boards ...  │  ← leader 由 org_appointments 同步回写
   └──────────────────────┘
```

### 2.2 表结构

#### `org_nodes` —— 架构节点（一棵树）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | |
| `name` | TEXT | NOT NULL | 节点名 |
| `node_type` | TEXT | NOT NULL, CHECK IN (`center`,`dept`,`group`,`special`) | 节点类型 |
| `parent_id` | INTEGER | NOT NULL DEFAULT 0 | 上级节点 id；0 = 顶级（中心） |
| `wg_id` | INTEGER | NOT NULL DEFAULT 0 | 关联旧 `workgroups.id`（兼容视图），0 = 未关联 |
| `is_anchor` | INTEGER | NOT NULL DEFAULT 0 | 1 = 主架构锚点节点（与 workgroups 一一对应） |
| `function` | TEXT | NOT NULL DEFAULT '' | 职能 |
| `sort` | INTEGER | NOT NULL DEFAULT 0 | 排序权重 |
| `created_at` | TEXT | NOT NULL DEFAULT datetime('now','localtime') | |

约束：`UNIQUE(parent_id, name)` —— 同级不得重名。

#### `org_roles` —— 岗位定义（节点类型 → 可设岗位）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK | |
| `node_type` | TEXT | NOT NULL, CHECK IN (四种类型) | 归属的节点类型 |
| `role_key` | TEXT | NOT NULL | 岗位标识 |
| `role_name` | TEXT | NOT NULL | 岗位显示名 |
| `unique_slot` | INTEGER | NOT NULL DEFAULT 0 | **1 = 该节点内至多一人；0 = 可多人** |
| `sort` | INTEGER | NOT NULL DEFAULT 0 | |

约束：`UNIQUE(node_type, role_key)`。

岗位清单（迁移时由 `INSERT OR IGNORE` 写入）：

| 节点类型 | 岗位 | role_key | unique_slot |
|---|---|---|---|
| 中心 | 中心负责人 | `center_head` | **1** |
| 中心 | 总经理 | `gm` | **1** |
| 中心 | 中心骨干 | `center_backbone` | 0 |
| 部门 | 部门长 | `dept_head` | **1** |
| 部门 | 部门骨干 | `dept_backbone` | 0 |
| 常规小组 | 组长 | `group_leader` | **1** |
| 常规小组 | 组员 | `member` | 0 |
| 专项小组 | 组长 | `group_leader` | **1** |
| 专项小组 | 组员 | `member` | 0 |

#### `org_appointments` —— 任职关系（人 × 节点 × 岗位）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | INTEGER | PK | |
| `node_id` | INTEGER | NOT NULL, FK → `org_nodes(id)` ON DELETE CASCADE | 任职节点 |
| `member_id` | INTEGER | NOT NULL, FK → `team_members(id)` ON DELETE CASCADE | 任职人员 |
| `role_key` | TEXT | NOT NULL | 岗位 |
| `is_primary` | INTEGER | NOT NULL DEFAULT 0 | 1 = 主岗 |
| `created_at` | TEXT | NOT NULL DEFAULT datetime('now','localtime') | |

约束：

- `UNIQUE(node_id, member_id, role_key)` —— 同一节点同一人同一岗位不重复；
  **但同一人可在不同节点任职（多组织），也可在同一节点兼任多个岗位（一人多岗）**。

### 2.3 层级规则

| 节点类型 | 允许的上级 | 说明 |
|---|---|---|
| `center` 中心 | 无（`parent_id = 0`） | 全局唯一 |
| `dept` 部门 | `center` | |
| `group` 常规小组 | `dept` | |
| `special` 专项小组 | `center` 或 `dept` | **跨部门协作组**，挂在中心下即全公司级专项 |

反向（父节点类型 → 允许的子节点类型）：

| 父节点类型 | 允许的子节点类型 |
|---|---|
| `center` | `dept`、`special` |
| `dept` | `group`、`special` |
| `group` | 无 |
| `special` | 无（本期不支持更深层级） |

前后端共用同一套规则（前端 `ORG_CHILD_RULES`，后端 `ORG_PARENT_RULES` / `ORG_CHILD_RULES`）。

## 三、接口设计

所有写操作需 `require_admin`；读操作需 `require_auth`。

### 3.1 节点 CRUD

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/org/tree` | 节点树（含类型、岗位清单、任职明细、多归属标记） |
| POST | `/api/org/nodes` | 新增节点 |
| PUT | `/api/org/nodes/{id}` | 修改节点（名称 / 类型 / 上级） |
| DELETE | `/api/org/nodes/{id}` | 删除节点（级联删除子节点与任职关系） |
| POST | `/api/org/nodes/{id}/move` | 移动节点（换上级） |

**GET /api/org/tree** 响应结构：

```jsonc
{
  "tree": [{
    "id": 7, "name": "收入组", "node_type": "group", "type_name": "常规小组",
    "parent_id": 4, "wg_id": 7, "is_anchor": 1,
    "roles": [
      { "role_key": "group_leader", "role_name": "组长", "unique_slot": 1 },
      { "role_key": "member",       "role_name": "组员", "unique_slot": 0 }
    ],
    "appointments": [
      { "id": 3, "node_id": 7, "member_id": 4, "role_key": "member",
        "role_name": "组员", "member_name": "吴婷婷", "account": "",
        "is_primary": 0, "other_org_count": 1 }
    ],
    "children": []
  }],
  "roles_by_type": { "center": [...], "dept": [...], "group": [...], "special": [...] },
  "type_names": { "center": "中心", "dept": "部门", "group": "常规小组", "special": "专项小组" }
}
```

`other_org_count` = 该成员在**其他**节点还有几处任职（多归属提示）。

**POST /api/org/nodes** 请求体：

```jsonc
{ "name": "成本优化专项组", "node_type": "special", "parent_id": 4,
  "function": "", "description": "" }
```

### 3.2 任职关系维护

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/org/appointments` | 新增任职（任命） |
| DELETE | `/api/org/appointments/{id}` | 解除任职（免职） |
| POST | `/api/org/appointments/move` | 调整任职（换节点 / 换岗位） |
| GET | `/api/org/members/{member_id}/appointments` | 某人的全部任职（多归属视图） |

**POST /api/org/appointments**：

```jsonc
{ "node_id": 7, "member_id": 17, "role_key": "group_leader", "is_primary": 1 }
```

**POST /api/org/appointments/move**：

```jsonc
{ "appt_id": 3, "node_id": 8, "role_key": "member" }
```

`node_id = 0` 表示不换节点；`role_key = ''` 表示不换岗位。

### 3.3 兼容别名（旧前端不受影响）

| 方法 | 路径 | 映射到 |
|---|---|---|
| GET | `/api/org` | `/api/workgroups` |
| POST | `/api/org` | `/api/workgroups` |
| PUT | `/api/org/{id}` | `/api/workgroups/{id}` |
| DELETE | `/api/org/{id}` | `/api/workgroups/{id}` |

### 3.4 新旧模型同步

新模型是**权威源**，旧表是**派生视图**。`_org_sync_legacy(node_id)` 在任命 / 免职 / 调整
任职 / 删除节点后调用：

1. `workgroups.leader` ← 该节点唯一槽位岗位的任职人（组长 / 部门长 / 中心负责人 / 总经理优先）
2. `team_members.workgroups` ← 该成员在小组 / 专项组节点的「组员 / 骨干」任职，分号串

`_org_sync_member_legacy(member_id)` 在解除任职 / 删除节点后调用，清理成员侧残留。

> 这样旧权限逻辑（`_leader_boards` 读 leader、`_group_boards` 读 workgroups 串）
> **无需任何改动**，且与新模型判定完全一致。

## 四、关键校验规则

### 4.1 层级完整性

| 规则 | 触发点 | 错误提示 |
|---|---|---|
| 节点类型合法 | 新增 / 修改 / 移动 | `节点类型必须是 center/dept/group/special 之一` |
| 中心无上级 | 新增 / 修改 | `中心是顶级节点，不能有上级` |
| 非中心必须有上级 | 新增 / 修改 | `常规小组必须挂在「部门」下` |
| 父节点类型合法 | 新增 / 修改 / 移动 | `常规小组只能挂在「部门」下，「财务中心」是中心` |
| 父节点存在 | 新增 / 修改 / 移动 | `上级节点不存在` |
| 不能自指 | 修改 / 移动 | `上级节点不能是自身` |
| **不能挂到自己的后代下（防环）** | 修改 / 移动 | `上级节点不能是自己的下级（会造成层级环）` |
| 中心全局唯一 | 新增 / 修改 | `中心节点全局只能有一个` |
| **子节点类型兼容性** | 改类型 / 移动 | `子节点「XX」的类型不允许挂在「YY」下，请先调整子节点` |
| 同级不重名 | 新增 / 修改 | `同级下已存在同名节点「XX」` |

防环实现：`_org_node_descendants(node_id)` 用「父 → 子」索引做迭代下探（带 visited 去重），
若目标父节点落在后代集合内则拒绝。

### 4.2 角色唯一性

| 规则 | 触发点 | 错误提示 |
|---|---|---|
| 岗位属于该节点类型 | 任命 / 调整 | `「部门」不可设置该岗位；可用岗位：部门长、部门骨干` |
| **唯一槽位节点内至多一人** | 任命 / 调整 | `「组长」在一个节点内只能有一人，当前已由 王伟娜 担任` |
| 成员必须存在 | 任命 | `成员不存在` |
| 同节点同岗位不重复 | 任命 | `该成员在此节点已有该岗位` |

**双层保障**：

1. **应用层** `_check_unique_slot()` —— 先查是否已被占，给出中文提示（DB 报错是英文，对用户不友好）
2. **数据库层** partial unique index：

```sql
CREATE UNIQUE INDEX IF NOT EXISTS ux_org_unique_slot
    ON org_appointments(node_id, role_key)
    WHERE role_key IN ('center_head','gm','dept_head','group_leader');
```

> ⚠️ SQLite 的 partial index 的 `WHERE` 子句**不允许子查询**（不能引用 `org_roles`），
> 因此唯一槽位岗位键在这条索引里写死。**改动 `org_roles` 的 `unique_slot` 集合时，
> 必须同步改这条索引**，否则两层判定会不一致。

### 4.3 多归属下的一致性

| 场景 | 规则 | 实现 |
|---|---|---|
| 一人多岗 | 同一人在同一节点可兼任多个岗位 | `UNIQUE(node_id, member_id, role_key)` 只禁同岗位重复 |
| 一人多组织 | 同一人可在任意多个节点任职 | 无跨节点唯一约束，仅 `member_id` 索引加速 |
| 岗位与节点类型绑定 | 跨类型任职被拒 | `_check_role_allowed()` |
| 唯一岗位跨节点 | 同一人可在 A 部门任部门长、B 部门任骨干 | 唯一性是**节点内**概念，非全局 |
| 旧视图同步 | 新模型变更后旧表一致 | `_org_sync_legacy()` / `_org_sync_member_legacy()` |
| 级联清理 | 删除节点连带清理任职与旧引用 | `ON DELETE CASCADE` + 显式删除旧表行 + 成员侧回写 |
| 成员删除 | 成员被删则任职自动失效 | `ON DELETE CASCADE` |
| 板块绑定保护 | 仍绑定板块的节点禁止删除 | `该节点仍绑定着板块，请先解除板块绑定再删除` |

**一致性边界**：新模型是唯一权威源；旧 `workgroups` 表与 `team_members.workgroups` 是
**单向派生视图**（由新模型写，不由旧表写回）。若管理员通过旧接口
`PUT /api/workgroups/{id}` 改了 leader，新模型不会自动感知 —— 这是当前实现的
已知取舍（旧接口仅保留给旧前端与板块绑定使用）。

## 五、存量数据迁移

`_migrate_org(conn)` 在 `init_db()` 中调用，**幂等**（连跑两次结果一致）。

### 5.1 迁移步骤

1. **岗位定义**：`INSERT OR IGNORE INTO org_roles`（表上有 `UNIQUE(node_type, role_key)`）
2. **节点转换**：按层级推断类型 → 建 `org_nodes` 节点 → 回填 `wg_id`
   - `parent_id = 0` → `center`
   - 挂在中心下 → `dept`（**部门可能还没有子组，不能因「是叶子」就判成 group**）
   - 挂在部门下 → `group`
3. **leader → 任职**：旧 `workgroups.leader` 按节点类型转成对应岗位任职
   （中心→`center_head` / 部门→`dept_head` / 小组→`group_leader`）
4. **成员分组串 → 组员任职**：`team_members.workgroups` 的分号串拆成多条
   `role_key='member'` 任职；**只挂到常规小组 / 专项小组节点**（部门与中心的成员归属
   由下级组沿父链传导，与旧权限语义一致）

### 5.2 实测结果（2026-10-29）

| 项 | 值 |
|---|---|
| `org_nodes` | 12 个（1 中心 + 5 部门 + 6 常规小组） |
| `org_roles` | 9 条（4 种节点类型） |
| `org_appointments` | 32 条组员任职 |
| 多归属人员 | 2 人（王伟娜 6 个节点、杜诗煜 6 个节点） |

## 六、前端交互

### 6.1 界面结构

架构管理弹窗保持原有「左树 + 右配置」两栏布局：

| 区域 | 内容 |
|---|---|
| 左栏 | 架构树：节点名 + **类型徽章**（🏛️中心/🏢部门/👥常规小组/🎯专项小组）+ 领导岗位任职人 + 任职人数 + 板块绑定 |
| 右栏上 | 名称 / **节点类型下拉**（按上级过滤）/ 上级节点 |
| 右栏中 | **岗位与任职**：每个岗位一个槽位，唯一槽位标「唯一」，可多人标「可多人」；槽位下是成员 chip（带 ✕ 移除）+ 「选择成员…任命」 |
| 右栏下 | 板块绑定（沿用旧逻辑；**部门/中心节点为只读派生**，见 §6.3） |
| 底部 | 汇总：共 N 个节点 · M 条任职 · K 人跨组织任职 |

### 6.2 关键实现点

- **点节点行** = 查看该节点的岗位与任职（`selectOrgNode`）；**「编辑」按钮** = 进编辑模式
- **类型下拉按上级过滤**：`fillOrgTypeOptions(parentId)` 只列出该上级允许的子类型，
  无合法子类型时禁用并提示
- **事件全部走委托**：节点行、chip 都是 `innerHTML` 重建的，直接绑元素会在重建后失效
- **多归属标记**：成员 chip 后显示 `+N`（另有 N 个组织任职），hover 有 title 说明
- **右栏按内容自适应**：配置区容器用 `flex-shrink:0;max-height:100%;overflow-y:auto`，
  岗位区用 `flex-shrink:0`、`#g_roles_box` 用 `max-height:240px` ——
  未选中节点时「岗位与任职」只有一句引导文字，不再被两层 `flex:1` 撑成大片空白，
  同时**任命 / 免职功能完整保留**（实测占位区 57px，配置区底部余量 15px）

### 6.3 选中态与底色高亮的单一真相

架构树的「当前选中项」只有一个真相来源：**`ORG_SELECTED`（节点 id）**。
底色高亮不再由渲染时写死行内 `style`，而是由 CSS 类驱动、统一回写：

| 机制 | 说明 |
|---|---|
| `data-org-id` | 每个树行携带自身节点 id，作为回写的定位锚点 |
| `.org-node-row` | 默认底色 `#fff`；`.root`（顶层节点）为 `#fafafa` |
| `.org-node-row:hover` | 悬停 `#f5f8fc` |
| `.org-node-row.sel` | 选中底色 `#f0f7ff`（`!important`）+ 左侧 2px 品牌蓝内阴影 |
| `paintOrgSelection()` | 遍历所有 `.org-node-row`，按 `dataset.orgId === ORG_SELECTED` 切换 `.sel` |

**调用点（保证三个场景底色与状态始终一致）**：

1. **初始化 / 列表刷新**：`renderWgList()` 重绘树后调用
2. **点击切换**：`selectOrgNode(nid)` 改写 `ORG_SELECTED` 后调用
3. **进入编辑态**：`editWg(gid)` 切换选中项后调用

> 早期实现用行内 `style="background:..."` 写死底色，与 CSS `.sel` 规则互相覆盖，
> 导致「点了一行但高亮还留在旧行」的不一致。现统一为类驱动 + 统一回写函数。

**杜绝残留高亮的两个关键约定**：

1. **树行不再内联生成 `.sel`** —— `renderWgList()` 只输出
   `class="org-node-row${n.parent_id?'':' root'}"`，`.sel` **只**由
   `paintOrgSelection()` 回写。早期版本渲染时按 `ORG_SELECTED===n.id`
   内联拼 `' sel'`，与回写函数形成**两个真相来源**，一旦两者不同步就会留下
   「已经取消选中却仍高亮」的残留。
2. **打开弹窗时清空选中** —— `openWgModal()` 开头置 `ORG_SELECTED=0`，
   `resetWgForm()` 同步置 0 并调用 `renderOrgIdle()` 复位右侧面板。

**重复点击切换选中**：`selectOrgNode(nid)` 检测到 `ORG_SELECTED===nid` 时
转调 `clearOrgSelection()` —— 取消选中、复位右侧面板（岗位区 / 板块绑定区 /
表单标题全部回到未选中态）、并清除树内高亮。

### 6.4 部门层级与看板「归属部门」的联动

看板管理的「归属部门」不再使用固定枚举，而是绑定到 `org_nodes` 的
**中心 / 部门**节点：

| 字段 | 位置 | 说明 |
|---|---|---|
| `board_config.dept` | `board_config` 表 | 归属部门名称（冗余存储，便于按名分组展示） |
| `board_config.dept_node_id` | `board_config` 表 | 归属部门对应的 `org_nodes.id`（**权威关联**，0 = 未配置） |

联动规则：

- **中心级节点（如财务中心）** = 视为**全部板块**，其板块对**全员展示**
- **部门级节点** = 该部门拥有的板块，挂靠该部门的成员可见
- **未配置归属**（`dept_node_id = 0`）的板块 = 全员可见（对应目录树的「未配置」节点）

架构管理侧的「板块绑定」对部门/中心节点改为**只读派生**（`nodeBoardScope()`）：

| 节点类型 | 板块绑定来源 |
|---|---|
| 中心 | 全部板块（前端显示为「全部板块」，不可手动勾选） |
| 部门 | 来自 `board_config.dept_node_id` 指向本部门的板块（`/api/org/tree` 返回 `owned_boards`） |
| 常规/专项小组 | 沿用旧逻辑：手工勾选，写入 `workgroups.boards` |

这样两处口径一致：**看板管理是唯一真相**，架构管理只做派生展示。

### 6.5 权限过滤的三层判定流程（2026-10-30 重写：fail-closed）

> **本次重写的原因**：旧实现用 `None` 同时表达「不收窄」和「不适用」，
> 与账号默认 `allowed_boards='*'` 叠加后形成 **fail-open**：
> 成员只要**没有架构归属**，三层过滤全部返回 `None` → 可见集合 = 全部看板，
> 结果就是「普通用户登录后仍能看到全部看板和板块」。

**超级管理员（admin）**

`is_admin()` 是全局唯一的管理员判定：`role == 'admin'`（含内置账号 `admin`）。
超级管理员**拥有当前及未来新增的全部权限，不受架构权限过滤限制** ——
`user_allowed()` 直接返回 `(None, None)`，所有看板/板块可见、所有写接口放行。
新增接口时只需沿用 `require_admin` / `is_admin()`，无需再为 admin 单独开特例。

**普通用户：可见看板 = 架构授权集 ∩ 账号级白名单**

```
⓪ 超级管理员 → (None, None)：全部可见，不做架构过滤

① 架构授权集（fail-closed，永远是显式集合，绝不返回 None）
   _dept_stage_boards()  归属部门层
     · 公共看板：未归属部门的看板 + 归属「中心」节点的看板 → 对全员可见
     · 成员挂靠部门所拥有的看板 → 该成员可见
     · 成员挂靠的是中心 → 管理层全范围（全部看板）
     · 成员**无任何架构归属** → 只剩公共看板，其余一律不可见
   _leader_scope_boards() 负责范围层（部门长/组长/中心负责人/总经理）
     · 额外拥有其负责范围（自身节点 + 全部后代）绑定的看板
     · 绑定来源按节点类型派生（_node_bound_boards）：
         中心 = 全部看板；部门 = board_config.dept_node_id 指向本部门的看板；
         小组 = workgroups.boards 手工勾选
   _group_boards()  工作组绑定层（收窄）
     · 只有**显式绑定**了看板白名单才收窄；'*' = 不收窄；未绑定 = 不收窄

② 账号级白名单 users.allowed_boards 与①取交集
   '*' = 不额外收窄（完全跟随架构）；指定列表 = 在架构范围内再收窄
   ★ 账号白名单**不能**越权授予架构之外的看板

③ 板块级白名单 users.allowed_columns（JSON {board_id: [column_id]}）
   在可见看板内继续收窄板块；未列出的看板 = 该看板全部板块可见
```

**落点**

| 函数 | 职责 | 关键约定 |
|---|---|---|
| `user_allowed()` | 对外唯一入口，返回 `(boards, columns)` | 普通用户 `boards` **永远是集合**（可为空），`None` 只留给超级管理员 |
| `arch_visible_boards` / `_arch_scope_boards()` | 汇总①②③层 | 集合运算，全部 fail-closed |
| `_node_bound_boards()` | 节点绑定派生 | 部门/中心不再读空的 `workgroups.boards` |
| `check_board_access()` | 写接口的看板准入 | 不可见 → 403；无编辑权 → 403 |
| `check_column_access()` | 写接口的板块准入 | 写入不可见板块 → 403 |
| `check_card_access()` | 读接口的可见性兜底 | 按卡片定位看板 → 不可见 → 403 |

**后端与前端一致性**

- 看板清单：`/api/me`、`/api/boards`、`/api/board-config`、`/api/workgroups`、
  `/api/org/tree` 全部按同一可见集合过滤（非 admin 只返回可见看板）；
- 板块清单：`/api/cards` 返回的 `columns` 由 `visible_columns()` 过滤后下发，
  前端 `COLS_META` 直接用这份数据渲染；
- 写接口与实时通道（WebSocket）也按可见集合过滤，不依赖前端隐藏。

### 6.5.1 常见误判与排查

| 现象 | 根因 | 处置 |
|---|---|---|
| 普通用户看到全部看板 | 成员无架构归属 + 账号白名单 `*` → 旧实现 fail-open | 在【架构管理】把成员任命到部门/小组 |
| 负责人范围为空 | 部门/中心节点的绑定读的是恒空的 `workgroups.boards` | 已改为按节点类型派生（`_node_bound_boards`） |
| 工作组白名单不生效 | 白名单里混入了部门自有看板，永远收窄不了 | 只取显式绑定（`merged if bound else None`） |
| admin 看不到新板块 | `user_allowed` 用账号名判定、`require_admin` 用角色判定，两套口径 | 统一到 `is_admin()`（角色口径） |

### 6.6 架构管理 vs 工作组选择：冲突判定与优先级

系统里存在**两套并行的成员组织归属机制**，它们表达的是同一件事 ——
「这个人属于哪个组织节点」，因此必然可能冲突：

| 机制 | 入口 | 存储 | 性质 |
|---|---|---|---|
| **架构管理「任命」** | 【架构管理】右栏「岗位与任职」 | `org_appointments`（node_id + member_id + role_key） | 新模型，**权威源**（唯一有效入口） |
| ~~人员管理「工作组选择」~~ | ~~【人员与账号管理】表格「🌳 选择工作组」~~ | ~~`team_members.workgroups`~~ | **已下线**（成员页面不再提供入口） |

**冲突是怎么产生的**

`_org_sync_legacy()` 把架构管理的任命**单向增量**回写到旧表：

- `workgroups.leader` ← 该节点的负责人任职（每次重算，覆盖式 ✅）
- `team_members.workgroups` ← 该节点的组员任职（**只追加、从不删除** ⚠️）

因为是单向增量，两套机制会**累积叠加**而非互相覆盖：

- 旧机制下设置的工作组，永远不会被架构管理的任命「顶掉」；
- 一个人在架构管理里被任命到 A 组，又在人员管理里选了 B 组 → 两边都在，
  早期实现取**并集** → 部门范围被放大为 A∪B，**权限被意外放宽**；
- 而 `_group_boards()` / `_leader_boards()` 原本只读旧字段，
  架构管理里新配的任命在没触发同步的场景下**不生效**。

**冲突判定与优先级规则（本次确立）**

> **架构管理优先**：只要该成员在 `org_appointments` 里**有任何任命**，
> 其组织归属**完全以架构管理为准**，人员管理里的 `workgroups` 字段一律忽略；
> 该成员在架构管理里**没有任何任命**时，才回退使用旧 `workgroups` 字段
> （兼容尚未迁移的历史成员）。

落地在三个推导函数上，**两层用同一套权威节点集合**，避免一层放宽一层收紧的错配：

| 函数 | 作用 | 权威来源 | 回退 |
|---|---|---|---|
| `_member_authority_nodes()` | 部门层级范围（归属部门层） | `org_appointments` → 最近部门/中心祖先 | `team_members.workgroups` |
| `_member_workgroup_names()` | 工作组名（工作组绑定层） | 任命的节点对应的 workgroups 名 | `team_members.workgroups` |
| `_org_leader_nodes()` | 负责人负责范围（负责范围层） | 任职岗位 ∈ {group_leader, dept_head, center_head, gm} | `workgroups.leader` |

**可见性提示**

`/api/team` 每个成员返回 `org_source`（`org` / `legacy` / `none`）、
`org_nodes`（架构管理里任命的节点名）、`org_conflict`（旧字段里架构未覆盖的组）。
成员表格据此标注：

- 🏛 **架构管理任命**：核算部、收入组 —— 权威来源
- ⚠ **忽略**：综合工作组、海南工作组 —— 旧字段有、架构管理没有，按规则**不生效**
- 👥 **工作组选择（架构管理未任命）** —— 回退来源

### 6.7 末级人员与人员筛选

树形选择组件支持 `pickMode:'person'`：在架构节点下**追加末级人员条目**，
人员可勾选，勾选结果直接套用为**负责人 / 参与人**筛选条件。

- **人员来源**：`/api/org/tree` 每个节点返回 `members`（该节点及其后代节点的
  任职人，含姓名与岗位），由 `_collect_node_members()` 收集，同一人只出现一次；
- **与节点名区分**：人员条目在 `selected` 里用前缀 `ORG_PERSON_PREFIX`（`__P__`）标记，
  回传时按**常量长度**剥离，避免与节点名混淆；
- **person 模式节点不可勾选**：节点只作导航，勾选框置灰（`.tp-box-na`），
  避免节点名混进人员集合；
- **架构树按需加载**：`ensureOrgTree(force)` —— 「按人员筛选」和「从架构选人」
  是**独立入口**，不能依赖用户先打开过架构管理弹窗，故走**缓存模式**；
  而 `openWgModal()` 用**强制模式**（每次打开都重新拉取），
  否则任命/免职后弹窗拿到的还是旧数据（见 §6.10）。

两个使用位置：

| 位置 | 入口 | 行为 |
|---|---|---|
| **卡片列表页筛选栏** | 「👤 按人员筛选」按钮 | 勾选人员 → 选择「套用为负责人」或「套用为参与人」→ 写入筛选条件并重查 |
| **卡片编辑弹窗** | 负责人 / 参与人选择器旁的「🌳 从架构选人」 | 勾选人员 → 直接回填到对应选择器（**与手动输入并存**，手工添加的名字不会被覆盖） |

后端 `/api/cards` 支持两个筛选参数：

- `owner` —— 负责人，逗号分隔多值 = 任一命中（单值时保持原有的子串匹配语义）
- `cc` —— 参与人，逗号分隔多值 = 任一命中

### 6.8 成员页面：工作组控件下线与只读归属树

组织归属的配置入口、校验与操作权限**统一收敛到【架构管理】**，
【成员与账号管理】不再提供任何工作组的编辑入口。

| 位置 | 处理 |
|---|---|
| 成员表格「工作组」列（含「🌳 选择工作组」按钮） | 整列删除 |
| 顶部「添加成员」的「工作组（可选，多选）」 | 整块删除 |
| 成员表格「已选工作组（最细颗粒）」 | 改为只读层级树，字段名去括号注释 → 「已选工作组」 |
| `TeamReq` / `TeamUpdateReq` 的 `workgroups` 参数 | 移除 |
| `POST /api/team` / `PUT /api/team/{id}` 写 `team_members.workgroups` | 移除 |

> ⚠️ 后端若只「不接收」workgroups 却仍写库，前端不传 → 默认值 `[]`
> → **会把架构管理同步来的归属数据全部清空**。必须同步去掉 UPDATE 里的 `workgroups=?`。

**只读归属树**（`renderMemberWgTree()` / `memberWgTreeNodes()` / `toggleWgTree()`）：

- 数据源以【架构管理】为准 —— `org_source==='org'` 用 `org_nodes`，
  架构管理无任命时才回退旧 `workgroups` 字段；
- 在 `WG_ALL` 里定位归属节点并**向上取全部祖先**，裁剪出只含相关分支的子树；
- **默认收起**，点击箭头逐级展开；**纯展示，无勾选框、无输入框、无编辑入口**；
- 展开状态记在 `WG_TREE_EXPANDED`，整表重绘后恢复；
- 展开用**局部 DOM 操作**（只切子级容器 `display` + 箭头文案）——
  若重绘 tbody，用户在表格里改好的姓名/账号/密码输入内容会被清空。

**表头冻结**：表格容器 `.tm-table-scroll` **不独立滚动**（否则与弹窗主体形成双滚轮），
`thead th` 用 `position:sticky;top:var(--tm-sticky-top);z-index:2` 固定 ——
`--tm-sticky-top` 由 JS 测量常驻筛选栏高度写入，避免表头与筛选栏重叠。

> 🔴 **flex 压缩的坑**：`modal-body` 是 `display:flex;flex-direction:column`，
> 表格容器（1400px+）作为 flex 子项会被**压缩**到容器高度内，
> `overflow:visible` 让内容溢出显示但父容器 `scrollHeight` 不涨 → **表格被压扁且滚不动**。
> 必须给 `.tm-table-scroll` 加 `flex-shrink:0`（并对 `#teamModal .modal-body>*` 统一设置）。

**配套修复**：`org_appointments` 声明了 `ON DELETE CASCADE`，但本库未开启
`PRAGMA foreign_keys`（SQLite 默认关闭）→ 级联不生效 → 删成员会残留孤儿任职数据。
`del_team` 改为显式 `DELETE FROM org_appointments WHERE member_id=?`。

### 6.9 板块写权限：不再有特例

历史上「成本看板仅管理员可编辑」是一条**硬编码**规则：

- 前端 `b.board_id === COST_BOARD_ID && !is_admin` → tab 上挂 🔒
- 后端 `check_cost_permission()` → 403「成本卡仅管理员可操作」

而成本看板与其余 6 个板块的归属**完全相同**（都是核算部 `dept_node_id=4`），
没有任何特殊配置 —— 它被单独挑出来靠一个写死的 board_id 禁止编辑，
与「归属统一以【架构管理】为准」的原则冲突。

该特例已**整体移除**（前端 6 处 + 后端 9 处调用 + `.tab-lock` 死样式）。
板块写权限统一由「**账号角色 + 板块归属 + 板块可见性**」判定。

> ⚠️ **移除特例时必须补上板块可见性校验**。
> `check_cost_permission()` 此前顺带承担了「板块不可见的人不能写」的兜底作用，
> 特例移除后卡片类写接口（改 / 删 / 新建 / 子事项 / 移动）**没有任何可见性校验** →
> 实测可见板块数为 0 的成员也能直接调 API 编辑该板块的卡片（越权）。

现新增统一校验 `check_board_access(board_id, username)`：

1. 看板对该用户**不可见** → 403「无权访问该看板」
2. 可见但角色是 viewer → 403「无编辑权限，请联系管理员」

并接入 8 个写接口：改卡片 / 删卡片 / 新建卡片 / 增子事项 / 改子事项 / 删子事项 /
移动卡片（源 + 目标）。

> 2026-10-30 补充：`check_board_access` 只管**看板**粒度。账号若配置了板块白名单
> （`users.allowed_columns`），还需 `check_column_access(board_id, column_id, username)`
> 拦住「往看不见的板块写」（已接入 新建 / 修改 / 移动 三个接口）；
> 读接口则统一用 `check_card_access(card_id, username)`（按卡片定位看板 → 403），
> 覆盖 评论 / 操作日志 / 子事项 / 子卡片树，避免「前端看不到、API 能读」的越权读。

### 6.11 看板与板块可见性失效专项（2026-10-30）

**现象**：普通用户登录后仍能看到**全部看板和板块**。

**根因（4 处叠加）**

| # | 根因 | 说明 |
|---|---|---|
| 1 | **fail-open 的空值语义** | `_dept_stage_boards()` / `_group_boards()` 用 `None` 同时表达「不收窄」与「不适用」；成员无架构归属时三层全部返回 `None` → 可见集合 = 全部 |
| 2 | **账号白名单默认 `*`** | 新建账号默认 `allowed_boards='*'`（= 不额外收窄），与 1 叠加后架构过滤形同虚设 |
| 3 | **负责范围层恒为空** | 部门/中心节点的绑定读的是 `workgroups.boards`，而该字段对部门/中心恒为空 → 负责人的范围算出来永远是空集 |
| 4 | **工作组白名单失效** | 白名单里混入了「归属部门自有看板」，集合永远覆盖前面两层 → 本层收窄不了任何东西 |

另外还有 2 个**口径不一致**问题：

- 超级管理员判定两套口径：`user_allowed` 用「账号名 == 'admin'」，
  `require_admin` 用「角色 == 'admin'」→ `role=admin` 的账号被架构过滤，
  却又能调全部管理接口；
- 读接口（评论 / 操作日志 / 子事项 / 子卡片树）只有登录校验，没有可见性校验。

**修法**：见 §6.5（fail-closed 三层 + 超级管理员豁免 + `check_card_access` /
`check_column_access`）。回归测试：`ops/test_perm_scope.py`（27 项断言）。

### 6.10 架构管理任命后的刷新

**现象**：在【架构管理】里任命组长后，弹窗的树**没有及时刷新** ——
行内的「负责人」仍是「未任命」、任职人数不变。

**根因**：把架构树加载抽成 `ensureOrgTree()` 时带了**幂等缓存**
（`if(ORG_TREE && ORG_TREE.length) return ORG_TREE;`），
而任命成功后的刷新靠 `await openWgModal()`，而 `openWgModal()` 内部调的正是
`ensureOrgTree()` —— **有缓存就直接返回 → 永远拿旧数据**。

树行的「负责人」「任职人数」都取自 `ORG_TREE` 里的 `node.appointments`，
缓存不刷新 = 这两列不更新。

**修法**：

1. `ensureOrgTree(force)` 支持强制重新拉取；
2. `openWgModal()` 用**强制模式**（每次打开都取最新架构树）；
   「按人员筛选」「从架构选人」等独立入口继续走缓存，不重复打接口；
3. 顺带修掉连带问题：任命后 `openWgModal()` 会 `resetWgForm()` 清掉选中态，
   用户「点节点 → 任命 → 想继续看同一个节点」时体验断裂 ——
   改为**记住并恢复当前选中节点**（`keepSel`），只重绘不重置表单。

> 通用教训：**带缓存的加载函数被当作「刷新」用时，必须提供强制刷新通道**。
> 否则「刷新」只会重绘旧数据 —— 表现为「界面没更新」，很容易误判为渲染 bug。

### 6.12 复制（四层） + 周数维度（2026-10-30）

#### 6.12.1 复制的四个层级

| 层级 | 入口 | 接口 | 归属重选 | 权限级别 |
|---|---|---|---|---|
| 看板 | 【看板管理】列表行「📋 复制」 | `POST /api/boards/{board_id}/copy` | 归属部门 / 年份 / 属性 / 状态 | **管理员**（与看板新建、配置同级） |
| 板块 | 看板内板块头部「📋 复制」 | `POST /api/columns/copy` | 目标看板（+ 创建日期 / 性质 / 归属年份） | editor + 目标看板可见 |
| 主事项 | 事项编辑弹窗页脚「📋 复制」 | `POST /api/cards/copy` | 目标看板 + 目标板块（+ 周数） | editor + 目标看板/板块可见 |
| 子事项 | 同上（子事项打开的是同一个编辑弹窗） | `POST /api/cards/copy` | 目标看板 + 目标板块 + **所属主事项**（必填） | 同上 + 目标主事项可见 |

**统一约定**

1. **副本是全新记录**，与原记录**不共享任何数据**：新的 `card_id` / `col_key` /
   `board_id`，独立的配置行；改副本不影响原记录。
2. **标题等关键字段可编辑**，默认「原标题（副本）」；同名冲突时自动追加序号
   （`X（副本）` → `X（副本2）`）。
3. **副本标识**：`copy_from` 字段记录来源（板块 `col_key`、事项 `card_id`、
   看板 `board_id`），配合标题后缀明确区分「这是副本」。
4. **只复制本级记录，不复制下级内容**（复制看板不带板块与事项、复制事项不带
   子事项目录）—— 避免"悄悄改归属"；需要内容时按层级逐个复制。
5. **运行态字段重置**：副本状态 = 「未完成」、完成时间清空、创建人 = 当前账号、
   创建时间 = 当前时间、置顶 / 编辑锁 / 评论 / 附件 / 子事项目录均不复制。

#### 6.12.2 归属重选的权限过滤（重点）

复制弹窗里的三个下拉**全部来自已按权限过滤的接口**，越权数据既不出现、也提交不上去：

| 选项 | 数据来源 | 过滤口径 |
|---|---|---|
| 目标看板 | `/api/me` 的 `boards` | `user_allowed()` 的可见看板集合 |
| 目标板块 | `GET /api/boards/{board_id}/columns` | `visible_columns()`（看板可见 + 板块白名单） |
| 所属主事项 | `GET /api/cards?board_id=…&column=…` | 列表接口本身已按可见性过滤，且只取主事项 |

服务端再校验一遍（前端过滤只是体验，服务端才是边界）：

- 源记录可见性：复制事项 → `check_card_access()`；复制板块 → 源看板可见 + 源板块在白名单内；
- 目标归属可见性：`check_board_access()`（可见 + 可编辑）、`check_column_access()`（板块白名单）、
  目标主事项 `perm_pass()`；
- 任何一项不满足 → **403**；子事项副本未选所属主事项 → **400**。

#### 6.12.3 周数维度

- **格式**：`2026年第41周`；**自然周 = 周一 ~ 周日**；归属年按 ISO-8601
  （该周**周四**所在年份，与 Excel / ISO 周编号一致，故 `2027-01-01` 属于
  `2026年第53周`）。
- **默认**：按**创建日期**所在自然周自动计算（`week_label()`），新建 / 编辑时
  可手动调整；清空则回落到按创建日期计算。
- **存储**：`cards.week_no`（主事项与子事项同表），老数据由 `init_db()` 幂等回填。
- **展示**：列表字段列 `负责人 / **周数** / 创建日期 / 截止日期` —— 周数位于
  创建信息列之前；主事项行与子事项行**共用同一套 `fieldItems()` 与同一套网格
  列宽**（`166px 118px 146px 178px`，容器宽 648px），保证父子两行纵向对齐。
- **筛选**：工具栏「📅 周数」勾选式下拉（多选，任一命中）；选项来自
  `/api/cards` 返回的 `weeks`（当前看板 + 权限可见范围内出现过的周数），
  勾选后其余周数仍在选项里（不因筛选而收缩）。

#### 6.12.4 归属年份的层级下沉（2026-10-30）

年份从**看板层**下沉到**板块层**：

```
看板（容器，无年份）  board_config 无 year 列
  └── 板块  board_columns.year = 2026      ← 每个板块绑定唯一归属年份（单值必填）
        └── 事项  cards.week_no = 2026年第41周   ← 事项归属自己的周数
```

| 层 | 改动 |
|---|---|
| 数据模型 | `board_config.year` **列已删除**（`init_db()` 幂等迁移：先把旧年份补进该看板下**没有年份**的板块，再删列）；`board_columns.year` 语义升级为单值必填 |
| 接口 | `BoardConfigReq` / `BoardConfigBulkReq` / `CopyBoardReq` 去掉 `year`；`_validate_board_config()` 不再校验年份；`ALLOWED_YEARS` 移除（板块年份是自由 4 位数字）；`/api/boards` 不再返回 `year`，改返回 `col_years`（该看板下各板块年份集合） |
| 校验 | 板块：年份未填 → 回落创建年份；非法格式 → 400。**事项周数与板块年份之间不做任何校验** |
| 展示 | 看板管理列表行显示「板块年份：2026年」（来自 `col_years`）；板块头部年份徽标（`.week-year`）；事项行显示自身周数，悬停提示带出「所属板块年份」 |

> ⚠️ **关键约束（刻意不实现的东西）**：周数与年份**不做强制校验或联动限制** ——
> 归属「2026 年」的板块下允许存在归属「2025 年第 40 周」的事项，
> 服务端既不拦截、也不提示、不做自动纠正。代码里**故意没有**
> 「周数年份必须等于板块年份」的校验。

### 6.13 筛选栏：可输入多选 + 人员锚定负责人维度（2026-10-30）

#### 6.13.1 两个筛选控件的形态

| 控件 | 形态 | 输入 | 多选 |
|---|---|---|---|
| 👤 人员 | **只读触发器 + chips**（点击 → 架构树弹窗） | 树内搜索框按姓名过滤 | chips 逐个删除 / 树上勾选 |
| 📅 周数 | 输入框 + chips + 勾选式候选面板 | `41` / `2026-41` / `2026年第41周` | 同上 |

- 周数输入经 `normWeekInput()` 归一（纯数字按当前年补全），非法值给出 toast 提示。
- **周数排序按「年×100 + 周号」的组合整数序**（`weekSortKey()` / 后端 `week_sort_key()`）——
  字符串序会把「第3周」排到「第31周」后面。**只改顺序，不改选项集合**。
- 人员候选来自**架构树**（全部末级人员），不再是"当过负责人的人"名单。

#### 6.13.2 人员筛选独占负责人维度

「👤 人员」筛选**指向 `owner` 字段**，独立状态下拉已下线（2026-11-02）：

| | 字段 | 前端状态 | 提交参数 |
|---|---|---|---|
| ~~负责人下拉~~ | ~~`owner`~~ | ~~`ownerFilter.value`~~ | ~~`owner=`~~ **已下线** |
| 人员筛选 | `owner`（唯一入口） | `PERSON_SEL`（独立 Set） | `person=` |

服务端 `person` 内部为「任一命中」（逗号分隔）；若外部 API 调用方同时传
`owner`，两者**求交集**（AND）。

「无负责人」这一档**不在筛选栏里**，而是移到了
**【架构树】弹窗的「显示选项」区**（2026-11-02）：一个独立复选项，
启用后树上以**「无负责人」标签节点**呈现（`.tp-none-node`），
可独立启用 / 取消。哨兵值 `__no_owner__`（与后端 `OWNER_NONE` 一致），
前端用 `personLabel()` 显示为中文文案。

> **为什么这样设计**：旧实现把人员名单写进 `ownerFilter` 这个 `<select>` 的
> 自定义 option 里并覆盖 `sel.value`，两个控件抢同一个 `value` → 互相覆盖、
> 无法组合。后来两者状态分离、参数分离、由服务端求交集；
> 最终因为两者**功能完全重复**，索性把独立下拉整块下线，只留人员筛选。
> 再后来「无负责人」也从下拉面板移到树上 —— 同一个筛选维度只保留一个入口，
> 避免两处并存、语义不一致。

#### 6.13.3 人员树的展开 / 收起语义

- 人员条目渲染在**可折叠容器内**（`tp_children_{id}`）→ 折叠父节点时人员随之隐藏；
- 后端成员记录带 `node_id`（实际任职节点），前端据此过滤 →
  每个人只挂在真正任职的那一层，不会与父节点重复；
- 父节点框**可点击级联**（勾选/取消其下属全部人员），显示三态（全选/半选/未选）；
- 展开状态存全局 `TREE_EXPANDED`（按节点 id）→ 筛选变更后重开、数据刷新后重开都保持；
- 收起父节点时清理后代展开标记。

**批量展开 / 折叠**（2026-11-02 新增）：树弹窗顶部工具栏提供
「展开全部 / 折叠全部」两个按钮，支持多级批量操作。

| 操作 | 实现 | 效果 |
|---|---|---|
| 展开全部 | 递归收集所有有下级/人员的节点 id → 写入 `TREE_EXPANDED` + `TREE_PICK.expanded` | 所有层级子容器 `display:block` |
| 折叠全部 | `TREE_EXPANDED.clear()` + `TREE_PICK.expanded.clear()` | 所有子容器收起，**顶层节点行仍可见** |

> **「折叠保留顶层可见」是渲染结构自带的**：节点行永远渲染，
> 只有子容器按 `expanded` 决定显隐 → 清空展开集合即达到该效果，
> 无需额外特判。
>
> **展开/折叠只动展开集合，绝不碰 `selected`** → 与筛选条件互不影响
> （实测：勾选「无负责人」后再批量展开/折叠，该条件始终保留）。

### 6.12 密码小眼睛与登录失败锁定策略

**密码小眼睛**：改密的三个输入框复用项目既有的 `.pwd-wrap` / `.pwd-eye` /
`togglePwd(inputId, btn)` / `pwdEyeHtml(inputId)`（成员管理已在用），
不另造实现 —— 同名 class 的重复定义会覆盖既有样式。

**登录失败锁定**：`login_attempts` 表（账号级）记录 `fail_count` / `last_fail_ts` / `locked`。

| 参数 | 值 |
|---|---|
| 冷却阈值 | 5 次 |
| 冷却时长 | 180 秒 |
| 锁定阈值 | 10 次（需管理员重置） |

判定顺序：**永久锁定 → 423**；**密码正确 → 放行并清零计数**；
**密码错误 → 计数+1**（≥10 → 423 锁定，≥5 → 429 冷却，否则 401）。

> 三条关键约定：
> ① **密码成功一次即清零**（DELETE 整行）；
> ② 冷却期内再试**继续累加计数**，否则永远到不了 10 次锁定；
> ③ 冷却期内**密码正确仍放行** —— 受限的是「错误次数」而非「登录」。

管理接口：`GET /api/admin/login-locks`、`POST /api/admin/login-lock/reset`；
登录页每 5 秒轮询 `/api/login/lock-status`，管理员重置后提示自动解除。

端到端用例要点：

1. 复制主事项 → 新记录、标题可编辑、`copy_from` 有值、状态重置、创建人 = 当前账号、
   **改副本不影响原记录**；
2. 复制子事项 → 未选所属主事项 400；选中后副本挂在该主事项下；
3. 复制板块 → 副本落在目标看板下；复制看板 → 仅管理员可用，配置随附可改；
4. 越权：复制不可见事项 / 复制到不可见看板 / 复制板块到不可见看板 /
   子事项挂到不可见主事项 / 复制到越权板块 → 全部 403；

> 进而污染其它用例（如可见性测试突然多出一个看板）。
> 清理必须同时按 `board_id` / `copy_from` 一起删。
