# 执行策略：代码探索与成果验证（边界控制 + 分层验证）

> 版本 v1.4 · 2026-11-06 · 主设计师（v1.0 初版 · v1.1 全量改判断制 + 必读项进 HANDOFF · v1.2 实测案例按复杂度取舍 + 人工确认流 · v1.3 轮次 tag 锚点 + 测试/文档分笔提交 · v1.4 留痕写入方式纪律——禁 heredoc + grep 回读）
> 适用：本项目所有涉及代码/脚本/文档改动的执行轮次。
> 核心原则：**验证层级与改动范围同步缩放，默认停留在满足当前改动所需的最低层级**；
> **全量不是绝对红线，而是判断项 —— 非必要不全量**，判断结论随轮次留痕；
> **实测案例按复杂度取舍 —— 简单视图改动不写测试，截图交用户人工确认**。

---

## 〇、为什么需要这套策略

本项目的教训（均有实证记录）：

- 一次样式微调触发全量 UI 回归（17 组 × 数分钟），而实际受影响的只有 1 组；
- 探查阶段无边界读文件，浪费大量上下文（用户原话：「你在浪费我的积分瞎打转」）；
- 全量跑测试时，**其他测试的夹具泄漏**被误判为「自己刚改的代码坏了」（#61 中 test_perm_scope / test_perm_matrix 两个既有泄漏的排查耗时）。

策略目标：**每一轮执行都先声明边界，验证只做到「刚好够」**。

## 一、每轮执行的固定流程（六步）

```
① 申报 → ② 定点探查 → ③ 最小实施 → ④ 分层验证 → ⑤ 升级判定 → ⑥ 收尾留痕
```

### 第①步 申报（动手前，不可跳过）

在开始任何探查/修改前，先明确列出以下五项并在回复中给出（多轮任务每轮重新申报）：

```
【本轮申报】
1. 锁定点与目标：     本次要解决什么问题、成功的判定标准是什么
2. 涉及范围：         预计改动的文件/模块清单（尽量精确到函数/区块）
3. 排除区域：         明确声明本轮不碰的目录/文件/接口
4. 允许命令清单：     本轮允许执行的命令（清单外一律禁止）
5. 本轮门禁：         对应第二节的门禁档位（不是一律全量）
```

- 用户给了明确指令时可直接自确认开工（申报内容仍须列出，供事后追溯）；
- 申报与执行出现偏差（要改申报外的文件）→ **停下来重新申报**，不得边扩边做。

### 第②步 定点探查（只读、受限）

- 探查范围 = 申报文件清单 + 其直接依赖（按需追加，追加即更新申报）；
- 优先用 **Grep 定点检索** + **Read 带 offset/limit**，禁止无目的通读大文件（`app.py` 4600+ 行、`index.html` 9000+ 行）；
- 查历史结论先读 `HANDOFF.md` ★ 摘要 + §六 索引表定位，**一次只读一篇** `docs/handoff/records/`；
- 禁止全仓库递归扫描（`grep -rn .`、全量 glob）——需要全库检索时说明理由并单独申报。

### 第③步 最小实施

- 改动严格限制在申报文件清单内；
- **范围外发现只登记不改动**（HANDOFF §五 待转交），派工权在用户；
- 临时脚本/夹具用专属前缀（`__xx_`），`try/finally` 保证清理，用完即删。

### 第④步 分层验证（见第二节，默认最低层级）

按申报的门禁档位执行，从 L1 开始，满足即停。

### 第⑤步 升级判定

按第三节的触发条件判断是否升级到下一层。**升级 = 影响范围扩大 → 需要同步扩大申报范围**。

### 第⑥步 收尾留痕

- 夹具残留自查（注意 `LIKE '__%'` 的 `_` 通配符坑，须用 `ESCAPE`）；
- HANDOFF §六 索引表 + §七 署名留痕（署名与台账一致）；
  **留痕写入方式（2026-11-06 v1.4 增补 · #74 实踩）**：HANDOFF / 工作日志一律用
  **Edit / Write 工具**写入，**禁止 bash heredoc（`cat <<'EOF'` / `python - <<'PYEOF'`）追加**——
  含中文引号、反斜杠的转义会被环境吃掉，轻则 SyntaxError、重则**静默写丢**
  （#74：提交成功但 HANDOFF 整段没进去）；写完必须 grep 回读校验锚点再 commit；
- git 提交；**若要同步服务器 → 必须过 `ops/verify.py`（7/7）后才允许 sync**（sync.sh 凭证机制强制，无法绕过）；
- **轮次 tag 锚点**（2026-11-05 v1.3 增补）：每轮全部落地后，给顶层收口提交打轻量 tag
  `r<期号>`（如 `r72`）——这是「当时代码 + 当轮测试」的可 checkout 快照，复现历史回归
  直接 `git checkout r72`，不必翻 HANDOFF 索引找提交号；
- **提交拆分规范**（2026-11-05 v1.3 增补）：同一轮内**测试脚本与文档分笔提交**
  （① 测试断言/夹具变更一笔；② 文档/留痕一笔）—— 测试可单独回滚，不为文档改动
  混入测试 diff。

## 二、边界控制：门禁随范围缩放

### 2.1 门禁档位表

| 改动范围 | 最低门禁档位 | 具体内容 |
|---|---|---|
| 纯文档 / 注释 / README | **G0 人工复查** | 内容自查即可，无命令门禁 |
| **简单视图改动**（纯展示：文案/样式值/间距/颜色/显隐/按钮文案） | **L1 + 人工确认流**（见 2.3） | 语法检查后**截图交用户确认**，不写实测案例 |
| 单文件局部改动（含行为逻辑：单个函数/交互行为） | **L1**，行为复杂则 +L2 | 语法检查；逻辑改动按 2.3 判断是否附带实测案例 |
| 单模块行为改动（一个接口/一个前端函数族） | **L1 + L2** | 对应该功能点的测试文件（通常 1 个） |
| 跨模块改动（共享函数/权限判定/公共组件） | **L1 + L2 + L3** | 目标测试 + 全部调用方测试 + 相关 UI 实测 |
| 提交 `src/` 代码 / 同步服务器 | **全量候选**（见 2.2 判断） | 判断为必要才跑 `ops/verify.py` 7 项 |

**判档口诀**：改了谁就测谁；谁消费了被改的东西，就把它也测了；要出门先判断，必要才全量。

### 2.2 全量必要性判断（v1.1 改判判断制，非绝对红线）

到达「全量候选」情形时，**先回答三问，再决定跑不跑**：

| # | 判断问题 | 是 → | 否 → |
|---|---|---|---|
| 1 | 本轮改动**真的要同步出门**吗？（能攒批与后续改动一起同步吗？） | 跑全量（sync.sh 的凭证机制强制要求） | 不跑 |
| 2 | 改动触及**全局性结构**吗？（表结构/迁移、权限模型核心、`_filter_cards_for_user` 等全局工具、index.html 全局骨架） | 跑全量 | 不跑 |
| 3 | 近几轮累积的局部改动，影响面**已经无法逐轮追踪**吗？（阶段收口） | 跑全量 | 不跑 |

- **三问全否 → 不跑全量**，以 L3（或更低层）结论收口，并在 §七 留痕写明「全量判断：三问皆否，依据 ××」；
- 判断本身花不了 10 秒，但能省掉一次数分钟的全量与它带来的夹具干扰误判；
- A-12（「改了 src/ 必须重跑 verify.py」）按此收窄理解为：**凭证机制层面**，只有 sync.sh 需要 stamp；判断为不必要时不跑，但不得同步。

### 2.2 允许命令清单的构造规则

- 每轮申报第 4 项只列**本轮真正需要**的命令，其余一律不跑；
- 常用命令按档位预制（见第四节速查表），申报时直接引用档位名即可，如「允许命令 = L1 档 + git commit」；
- 清单外的命令（包括看起来无害的全量跑批）**默认禁止**，需要时重新申报。

### 2.3 实测案例取舍：并非所有修改都写测试（v1.2 增补，用户定则）

**只有较复杂的修改才需要附带实测案例；简单的视图修改无需实测案例，走人工确认流。**

| 改动类型 | 实测案例 | 收口方式 |
|---|---|---|
| **简单视图改动**：纯展示层 —— 文案、样式值（宽高/间距/颜色/字号）、显隐、按钮文案、纯静态布局 | **不写** | L1 语法 → **截图交用户人工确认** → 按反馈迭代 |
| **复杂修改**：行为逻辑、状态流转、数据流、权限、接口、跨模块联动 | **要写**（新增或更新对应 `ui_check_*` / `test_*`） | 分层验证到对应档位 |

**人工确认流（简单视图改动的固定三步）**：

1. 改完过 L1 → 起本地服务渲染目标界面 → **提供界面给用户确认**（截图留档 `ops/.shots/` 并展示，或本地预览地址），同时说明改动点；
2. **等用户回复效果**——认可或指出需调整点；
3. 按反馈继续调整（回到第 1 步）或收尾提交留痕。**在用户回复前不追加测试、不自行判定"已完成"。**

**边界与例外**：

- 人工确认中**暴露出 bug 且修复涉及逻辑**（如隐藏态测量、状态同步）→ 修复本身按复杂度规则**补一个针对性实测**防回归（实例：#65 首开尺寸修复补 `ui_check_bc_first_open.py`）；
- 截图判定不了的（交互行为、权限视角差异、多角色）→ 不属于"简单视图"，按复杂修改带案例；
- 一轮改动同时含简单视图 + 复杂逻辑时，**拆开处理**：视图部分走人工确认，逻辑部分带案例。

### 2.4 测试脚本的选取与拆分

- 现有测试已按功能点拆分（`ops/test_*.py` / `test-*.js` / `ui_check_*.py`，一期一文件）；
- 每轮**只选取与申报功能点对应的测试文件**，禁止「顺手全跑一遍求安心」；
- 新增功能无对应测试时，**新建独立测试文件**（不复用旧文件追加），自带专属前缀夹具 + `try/finally` 清理；
- 测试文件内断言不得硬编码全局基线数字（用相对基线），避免被其他轮次的夹具污染。

## 三、分层验证三级（逐级向上，默认最低层）

### 3.1 第一级：语法/类型检查

**做什么**（按改动文件类型选其一）：

| 文件 | 命令 |
|---|---|
| Python（app.py / init_db.py / 测试脚本） | `python -m py_compile <文件>` 或 `python -c "import ast; ast.parse(open(...).read())"` |
| JS（index.html 内嵌脚本） | 抽取 `<script>` 块为临时文件 → `node --check`（完事即删临时文件） |
| HTML 结构 | Grep 断言关键结构存在（标签/函数名/按钮 onclick） |
| 文档 | 无（人工复查） |

**通过标准**：零语法错误。

**升级触发条件（L1 → L2）**：
- 改动包含**行为逻辑**（不只是语法/文案/样式值），语法通过也不代表行为正确；
- L1 发现的问题修复本身涉及逻辑调整；
- 改动了测试文件中的**断言**（断言变了必须跑该测试确认）。

纯文案/样式值/注释改动 → 停在 L1 即可。

### 3.2 第二级：目标模块单元测试

**做什么**：运行与申报功能点直接对应的**单个**测试文件：

```bash
ops/.localvenv/Scripts/python.exe ops/test_<功能点>.py     # 后端/逻辑
node ops/test-<功能点>.js                                   # 前端静态断言
```

注意部分测试对工作目录敏感（需从仓库根运行）。

**通过标准**：目标文件 0 失败（既有失败需先用 `git stash` 对照法确认与本轮无关——暂存改动 → 重跑 → 失败依旧 = 既有问题，只登记不修）。

**升级触发条件（L2 → L3）**：
- 改动了**被多个调用方消费的东西**：接口签名/请求模型、共享工具函数（如 `_filter_cards_for_user`）、权限判定（`perm.py` / 能力位）、公共 CSS 类、全局 JS 函数；
- 目标测试通过，但改动语义与**其他测试文件已编码的行为**相关（改权限矩阵 → 所有断言该矩阵的测试都要过）；
- 改动跨了申报外的模块边界（此时同时触发重新申报）。

单接口/单函数的局部行为改动 → 停在 L2。

### 3.3 第三级：相关调用方回归测试

**做什么**：运行消费被改动模块的**全部直接调用方**测试（通常 2–4 个文件，不是全量）：

- 改后端接口 → 调该接口的所有 `test_*.py`；
- 改前端交互/布局 → 相关的 `ui_check_*.py`（实测浏览器行为）+ 静态断言 `test-*.js`；
- 改权限 → 权限矩阵 + 各角色 scope 测试。

**通过标准**：0 新增失败；既有失败逐个 stash 对照确认并登记。

**升级触发条件（L3 → 全量候选）**——到达候选后按 **2.2 三问**判断，非必要不全量：
- 本轮或累积改动**要同步出门**（sync.sh 凭证机制强制）；
- 改动触及**全局性结构**：数据库表结构/迁移（`init_db.py`）、权限模型核心、`_filter_cards_for_user` 等全局工具、`index.html` 全局布局骨架；
- 连续多轮局部改动后的**阶段收口**（累积影响面已无法逐轮追踪时）。

### 3.4 层级速记

```
L1 语法（~秒级）──逻辑动了→ L2 目标测试（~十秒级）──别人也消费→ L3 调用方回归（~分钟级）
                                                            ──三问判断→ 全量 verify.py（必要才跑）
```

| 档位 | 命令 |
|---|---|

| L1-JS | 抽 script 块 → `node --check`（临时文件用完删） |

| 本地起服务 | `cd ops && ./local-dev.sh start / restart / stop` |

## 五、违规自查清单（每轮收尾过一遍）

1. 本轮是否跑了**申报清单外**的命令/测试？（跑了 → 下轮收紧）
2. 到达全量候选时，**是否做了 2.2 三问判断并留痕**？（没判断就跑 = 违规；判断为不必要仍跑 = 违规）
3. 简单视图改动是否**误写了实测案例 / 误跑了 UI 实测**？（应走 2.3 人工确认流）
4. 探查是否退化成无边界通读？（单文件读取是否带了明确 offset/limit 或 Grep 前置）
5. 升级是否同步扩大了申报范围？
6. 夹具是否零残留？临时文件（script 块抽取件等）是否已删？
7. 留痕是否完成（HANDOFF §六/§七 + git 提交）？
8. **轮次收口是否打了 `r<期号>` tag、测试与文档是否分笔提交？**（2026-11-05 v1.3 增补）
9. **留痕是否用 Edit/Write 工具写入并 grep 回读过？**（2026-11-06 v1.4 增补——heredoc 追加会静默写丢）

## 六、与既有交付流程的关系

- 本策略约束的是**阶段一内部的执行粒度**（怎么改、怎么验）；
- `docs/交付流程规范.md` 的两阶段分离（verify.py 门禁 → sync.sh）**不变**：sync.sh 的凭证机制决定了「要同步就必须跑过 verify.py」，这条是机制强制、不可绕过；**判断的空间在「要不要此刻同步出门」** —— 能攒批就攒批，提交但不同步时按 2.2 判断必要性；
- 与 HANDOFF 三条硬规矩兼容：上线登记 / 范围外只登记不改动 / 引用给路径；
- **必读项已进 HANDOFF**：「🔴 开工前必读 ② 开工检查项」含执行纪律条目（指向本文），确保每轮动手前过一遍。
