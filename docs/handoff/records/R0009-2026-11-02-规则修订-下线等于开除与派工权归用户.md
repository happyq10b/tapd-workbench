**做了什么**

用户澄清了两条此前文档写错的规则，并要求写进**必读部分**。两条都是**方向性错误**，
不是措辞问题 —— 原规则会让 Agent 做出用户明确禁止的动作。

#### ① 「下线」= 开除，不是「收工」

**原文写错了**。§4.3 原本写「状态流转：🟢 在线 → ⚪ 已下线。**没有"暂停"**，不干了就是下线」，
§5.2/附录 A 原本写「下线登记（**收工时做**）」—— 按这个写法，
Agent 干完一轮活就该把自己改成 ⚪ 退出项目。**这与用户的实际意图完全相反**：
Agent 是**常年常驻**的角色，交付完一轮活**状态不变**，随时可被再次指派。
"下线"在用户语境里是**开除**——把人踢出项目。

**修订后的规则**（写进必读区 §0 的「开工前必读」铁律框）：

| 位置 | 改动 |
|---|---|
| 顶部「开工前必读」 | 加 🔴 铁律框第①条：「下线」= 开除，不是收工；**不得自行下线**，不得因"我这轮没活干"就改 ⚪ |
| 顶部十步流程 | **删掉原第⑩步**「下线时 → 改状态 ⚪」—— 因为下线不是 Agent 的日常动作，不该出现在"开工前必做"里 |

#### ② 派工权归用户：需要他人改动 → 先汇报，不能自行指挥

**我上一轮（记录 #8）自己写错了**：§0.3.1 的「交接方式」写的是
「主设计师把 UI 活写进 §五，指名 UI设计师；UI设计师 认领（改 🔄）」——
这条链路**跳过了用户**，等于让主设计师直接指挥另一个 Agent。
按用户澄清，正确链路是：**登记 → 向用户汇报 → 用户指派 → 对方认领 → 做完标 ✅**。

| 位置 | 改动 |
|---|---|
| 顶部「开工前必读」 | 加 🔴 铁律框第②条：**派工权在用户**；Agent 之间**不自行互相派工** |
| 「各角色的处置分工」表 | 新增一行「需要别的 Agent 干活 → **先向用户汇报**，由用户指派；不自行指挥他人」；新增「主设计师」行 |
| §4.4 末尾 | 加：「台账里写着该谁干」≠「可以直接叫 TA 动手」；**派工权在用户，不在 Agent 之间** |
| §五 开头 | 加：「**建议接收方只是建议，最终指派权在用户**」+ 四步链路；⚠️ 登记完就直接指挥别人**同样违规** |
| §5.3 处置纪律 | 新增 🚫「**不自行指挥另一个 Agent** —— 即便派工单写着建议接收方，也不能绕过用户直接叫 TA 动手」 |
| §0.3.1 交接方式 | **改正上一轮写错的链路**：加「需向用户汇报，由用户指派」+ 🔴 提示「主设计师自己不能直接叫 UI设计师 动手」 |
| 附录 A | 新增 ④「需要别的 Agent 干活 → 先向用户汇报」，含 ⚠️ 不登记完就直接指挥别人同样违规 |

**注意事项与约束**

- 🔴 **这两条改的是「谁有权做什么」，比改样式重要得多**。
  原规则若不改，Agent 会**主动把自己踢出项目**（干完活就置 ⚪），
  也**主动指挥别的 Agent**（跳过用户）—— 两个都是用户明确禁止的。
- ⚠️ **历史记录不重写**：记录 #5 里的「不干了就是下线」是当时的事实，
  就地加 📌 括注指向本条修订即可 —— 与本文档一贯的「不重写历史，就地加括注」原则一致。
- 💡 **「在线 = 常驻，不是在线忙」**这个区分很重要：
  台账回答的是「项目里有哪些角色」，不是「此刻谁在敲代码」。
  否则读者会以为台账里的 Agent 都正占着 `src/static/index.html`，
  从而不敢动手 —— 实际没人时反而互相推诿。
- ⚠️ **§五 的「建议接收方」列名保留不变**，但语义已从「指派给 TA」降级为
  「建议由 TA 做」；真正的指派在**用户**那里。改列名会破坏历史记录的引用。
