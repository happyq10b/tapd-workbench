**做了什么**

---

#### 根因：小组节点被"向上提升"成父部门

苏春景（`scj`）在【架构管理】里的任命是：

| 节点 | 类型 | 该节点绑定了哪些看板 |
|---|---|---|
| 管理部 | dept | **无**（管理部不拥有任何看板） |
| 费用组 | group | **无**（`workgroups.boards` 为空） |
| 税务组 | group | **无**（`workgroups.boards` 为空） |

按语义，他**不该看到任何看板**。但修复前他能看到**全部 7 个**。

**根因链**（逐层实测得出）：

```python
# ① _member_authority_nodes() —— 把任命的节点「向上提升」到最近的部门/中心祖先
for nid in node_ids:
    anc = _dept_ancestor_of_node(nid, nmap)   # 费用组(9) → 父节点 核算部(4)
    if anc: scope.add(anc['id'])
# → 苏春景的 scope = {管理部(2), 核算部(4)}    ← 核算部是被「提升」进来的

# ② _dept_stage_boards() —— 把 scope 里的 id **直接当部门**去查归属看板
for nid in scope:
    visible |= owned.get(nid, set())           # owned[4] = 核算部的全部 7 个看板
# → 可见 7 个看板
```

**问题出在 ②**：scope 里混着「小组提升上来的 id」和「真正的部门 id」，
代码却一律当部门处理 → **小组的成员被当成核算部的成员，继承了核算部的全部看板**。

而事实上系统里**早就有正确的分节点类型实现** —— `_node_bound_boards()`：
「中心 = 全部看板；部门 = 归属该部门的看板；**小组 = 工作组手工勾选的看板**」。
第一层只是**没用它**。

#### 修复

**① 新增 `_member_appointed_nodes()`** —— 返回**原始任命节点**（不做向上提升）：

```python
def _member_appointed_nodes(username):
    """该成员**直接被任命到的**架构节点 id 集合（不做向上提升）。
    与 _member_authority_nodes 的区别：
      · _member_authority_nodes：把小组节点提升到部门祖先 → 用于「这个成员属于哪个部门」（展示用）
      · 本函数：保留原始任命节点 → 用于**权限判定**
    """
```

**② `_dept_stage_boards()` 改用原始任命节点 + `_node_bound_boards()` 派生**：

```python
scope = _member_appointed_nodes(username)[0]     # ← 不再是提升后的
...
if any(nmap.get(nid, {}).get('node_type') == 'center' for nid in scope):
    return set(all_ids)                          # 中心 = 管理层全范围（按原始节点类型判定）
visible = set(public)
for nid in scope:
    visible |= _node_bound_boards(nmap.get(nid), owned, wg_by_id)
```

修正后的语义（与 `_node_bound_boards` 完全一致）：

| 成员任命 | 可见看板 |
|---|---|
| 部门(dept) / 中心(center) | 该节点**自己拥有**的看板 |
| 小组(group) | 该小组**自己绑定**的看板（`workgroups.boards`；**没绑定 = 没有**）<br>**不继承父部门** |

**③ 顺带修掉 `_group_boards()` 的第二个同类 bug**

它此前会**沿 workgroups 父链向上收集**绑定 → 「费用组成员」会拿到「核算部」上绑的看板、
「核算部成员」会拿到更上层的绑定。现改为**只取小组节点自己的显式绑定**，
不再沿父链传导。

> ⚠️ **区分**：写入侧仍保留「父级收缩 → 级联清理后代超范围绑定」（`_cascade_boards`）——
> 那是**数据一致性维护**（防止子节点绑着父节点已收回的看板），
> 与读取侧的「传导」是两回事，不能一起删。

**注意事项与约束**

- 🔴 **「展示用 scope」与「权限用 scope」是两回事，不能混用**：
  - `_member_authority_nodes()`（提升后）→ 回答「这个成员属于哪个部门」→ **展示用**
  - `_member_appointed_nodes()`（原始）→ 回答「这个成员能看到哪些看板」→ **权限用**
  两者都保留，但**权限判定一律用后者**。
- 🔴 **节点的绑定只属于该节点自己**，不向上传导。
  读取侧不传导；写入侧的「父级收缩 → 级联清理后代」是**数据一致性维护**，保留。
- 🔴 **小组成员与部门成员的可见范围必须不同** —— 这是本次的立论。
  小组没绑定看板 = 该组成员看不到那些看板，与「部门拥有看板」是两回事。
- 💡 **修复前所有非管理员账号看到的都是同样 7 个看板**（因为 7 个看板全归属核算部，
  而几乎所有成员都被提升到了核算部）—— 这个「整齐得不正常」的现象就是线索。
- ⚠️ **夹具必须设 `org_nodes.wg_id`**（指向 `workgroups.id`）——
  `_node_bound_boards` 靠它找小组的绑定；`wg_id=0` → 小组绑定永远读不到。
  本轮在这个坑上绕了一次（症状：G1 成员看不到自己组绑定的看板）。
- ⚠️ **测试里「真实数据断言」必须放在夹具清理之后**：
  夹具的看板会混进真实账号的可见集合，数字对不上（本轮踩到，
  表现为「余河可见 9 个看板」—— 实为夹具的 2 个混进来了）。
- ⚠️ **断言里的正则要匹配 Python 源码的真实写法**：
  Python 是单等号 `==`，我写成 `===` 导致断言失败（已修正）。
