**类型**：后端（权限语义）+ 界面调整（选人交互）+ 文档

**做了什么**

用户要求：「看板管理中只配置负责人，不配置参与人，其他权限统一通过架构管理的看板绑定来。
此外，负责人选择可以参照外部人员筛选的树状图。」

两处语义由用户拍板确定：
- **看板负责人 = 有权修改看板基本信息**（不是可见性开关）
- **板块负责人放在板块编辑里配置**

#### 语义变更对照

| | 旧（已下线） | 新（现行） |
|---|---|---|
| 看板 `owner` | 配了 → 只有 owner + 参与人可见 | **管理权**：可改该看板基本信息（归属部门/属性/状态/备注），**不影响可见性** |
| 板块 `owner` | 同上（前端无入口） | **管理权**：在【板块编辑】里配置 |
| `participants` | 可配多人，命中者可见 | **整体下线**（字段保留兼容，传入即忽略并清空） |
| 可见性来源 | 架构链 **∩** ACL | **只由【架构管理】的看板绑定决定** |

#### 后端改动

1. **删除 ACL 收窄层**：`user_allowed()` 里的 `_acl_filter_boards()` / `_acl_filter_columns()`
   调用移除；`_acl_hit()` / `board_acl_allows()` / `column_acl_allows()` 删除。
2. **新增管理权判定**：
   ```python
   def is_board_manager(username, board_id) -> bool:   # 管理员 或 该看板负责人
   def is_column_manager(username, col_key) -> bool:   # 管理员 或 该板块负责人
   def board_owner(board_id) -> str
   def column_owner(col_key) -> str
   ```
3. **写接口放开**：
   - `POST/PUT/DELETE /api/board-config*`：`require_admin` → `require_auth` + `is_board_manager()`
   - `PUT /api/columns`：非管理员必须是该板块负责人
   - `PUT /api/boards/{id}/acl` / `PUT /api/columns/{key}/acl`：仍限管理员（**指定**负责人 = 授予管理权）
4. **`ColumnUpdate` 新增 `owner` 字段**（`__CLEAR__` = 清除）；仅管理员可写。
5. **`/api/me` 新增** `managed_boards` / `managed_columns`（我是负责人的看板/板块）
   —— 前端据此决定「看板管理」入口对非管理员是否显示。
6. **`/api/boards` 每项新增 `is_owner`** 标记。
7. `AclReq.participants` 字段保留（兼容旧客户端），但服务端**忽略并清空**。

#### 前端改动

1. **看板管理**：参与人整块删除；负责人从 `<select>` 改为 **🌳 树状图单选**
   （复用筛选栏「👤 人员」的 `ORG_TREE` + `pickMode:'person'`）。
   - 树里选的是**姓名**，负责人存**账号** → `bcAccountByName()` 反查
   - 回显为 chip，显示「姓名(账号)」
2. **板块编辑弹窗**：新增「板块负责人」字段（仅管理员可见可改），同样树状单选；
   板块标题 `data-owner` 属性带回账号用于回填。
3. **树弹窗新增 `requireAccount` 模式**（负责人场景专用）：
   - **未开通登录账号的人置灰不可选**，标注「（未开通账号）」
   - 理由：25 名成员中 20 名没开通账号，让他们可选等于「配了个空」
4. **权限入口按角色显隐**：
   - 「看板管理」顶栏按钮：管理员 **或** 任一看板负责人可见
   - 看板管理弹窗内：非管理员只列出**自己负责的看板**；
     「+ 新建看板」「删除所选」「应用到已选 N 个」「保存负责人」对非管理员隐藏
   - 负责人选择按钮：仅管理员可见

**注意事项与约束**

- 🔴 **管理权不放大可见性（fail-closed）**：把某人设为负责人，若他本不在架构授权范围内，
  **仍然看不到**该看板 —— 否则「负责人」就成了越权后门。
  负责人**必须同时**在架构绑定范围内，管理权才用得上。
- 🔴 **树里选的是姓名，负责人存的是账号** —— 回填必须经 `bcAccountByName()` 反查，
  直接把姓名写进去会导致 `is_board_manager()` 永不命中（负责人形同虚设）。
- 🔴 **`requireAccount` 是负责人场景专用**：不能给通用的 `pickMode:'person'` 打开，
  否则会破坏筛选栏的「人员筛选」（那里要能选没账号的人，用于筛「无负责人」等）。
- ⚠️ **BC_ACL_MEMBERS 必须先加载再开树**：否则 `requireAccount` 的标灰逻辑拿不到账号信息，
  会把没开通账号的人显示成可选。已用 `Promise.all([ensureOrgTree(), bcLoadAclMembers()])` 保证时序。
- ⚠️ **`/api/me` 的 SQL 用参数化空串**：写 `owner<>''` 会被 Python 转义吃掉成 `owner<>'`，
  导致 `sqlite3.OperationalError: incomplete input`（实测踩到，/api/me 直接 500）。
- 💡 **旧 ACL 语义彻底下线**：`_acl_hit` 那套「未配置就不收窄 / 配置了就只有他们可见」
  是本项目最容易误判的地方 —— 现在**负责人与可见性彻底解耦**，别再按老逻辑读代码。
- ⚠️ **`test_acl_scope.py` 是重写不是修补**：旧版 32 条断言全部基于「仅负责人可见」，
  逐条改会改成一团乱麻；拆成「可见性口径」（test_acl_scope）+「管理权」（test_owner_scope）
  两份，各自职责单一。
