# 财务中心「整合管理抓手」平台 · 项目规划汇报

> **汇报对象**：财务中心管理层
> **项目定位**：整合管理抓手
> **文档版本**：v2.0（按平台实况修订）
> **成文日期**：2026-11-09
> **依托平台**：财务综合事务平台 FISP（FastAPI + SQLite，109 个 API 接口，已上线运行）
> **数据口径**：2026-11-08 生产库快照实测，附录有逐项核实记录

## 一、项目定位

### 1.1 一句话定位

**把财务中心散落在各处的日常事务，收束到一个统一的、可查可控可复用的管理平台上。**

不是"再做一个系统"，而是给已经跑起来的 FISP 装上**管理属性**——从"事项记录工具"升级为"财务中心的管理抓手"。

### 1.2 平台实况（2026-11-08 生产库实测）

**已经跑起来的部分：**

| 能力 | 实测状态 |
|---|---|
| 业务看板 | 7 个正式看板（综合 / 资产 / 成本 / 税务 / 收入 / 费用 / 海南专项）+ 1 个副本 |
| 板块 | 263 个，带性质（日常 / 专项）、年份、负责人、参与人、完成情况 |
| 事项 | 1263 条，周数维度 **100% 回填**，含负责人 / 参与人 / 关注人 / 截止日期 / 状态 / 描述 / 标签 |
| 组织架构 | 12 个正式节点（1 中心 + 5 部门 + 6 常规小组）+ 9 类岗位定义 |
| 分级权限内核 | 7 级角色、4 层资源、7 个操作码、fail-closed、实时判定 |
| 审计 | 操作日志 2255 条 + 审计日志 8437 条（登录 / 登出 / 增删改查全留痕） |
| 账号 | 31 个（含 3 个测试账号），登录失败锁定、单点登录、强制下线均已上线 |
| 导入导出 | 26 列单一数据源导出 + 每用户自定义导出模板 |
| 部门主页 | 页面容器已上线（文化区 + 事项统计区 + 部门切换条），**内容为空** |

**还没做、但本次要做的部分：**

| 缺口 | 现状实况 |
|---|---|
| 评优流程 | `dept_honors` 表 **0 条**，无提名 / 投票 / 统计 / 公示任何环节 |
| 重大事项台账 | **表都不存在**，重大事项散在各业务看板里 |
| 部门主页内容 | `dept_profile` 仅 1 条核算部记录（内容是测试占位值），其余 4 部门空白；`dept_posts` / `notices` 均 0 条 |
| 登记台视角 | 现有入口是「架构 → 部门 → 看板 → 板块 → 事项」逐层下钻，**缺按角色聚合的入口** |
| 智能总结 | MCP 部署方案已有文档，未实施 |

**核心矛盾**：数据已经收上来了（底座是有的），但**管理动作仍然发生在平台之外**——微信群、Excel、邮件。

### 1.3 建设目标

| 层次 | 目标 | 验收标准 |
|---|---|---|
| **收** | 财务日常事务统一登记、统一留痕 | 日常事项 100% 走平台登记 |
| **管** | 管理动作有台账、有授权、有追溯 | 重大事项可查、可授权查阅、留痕完整 |
| **评** | 评优流程线上闭环 | 投票 → 统计 → 公示全流程在平台内完成 |
| **省** | 减少重复劳动 | 周报 / 总结由平台生成初稿，人只做校对 |

## 二、核心优势

### 优势一：贴合财务中心架构，权限框架契合管理需求

**做什么**：平台权限内核**直接以组织架构树为基准**——中心 / 部门 / 常规小组 / 专项小组四类节点，配套 9 类岗位定义（中心负责人、总经理、中心骨干、部门长、部门骨干、组长、组员；专项小组复用组长 / 组员），一人多岗、一人多组织任职已由数据模型承载。

**权限内核已经做到什么程度**（`src/app/perm.py`，2026-11-02 落地）：

| 维度 | 实现 |
|---|---|
| 角色等级 | 7 级：超管 > 管理员 > 架构负责人 > 看板负责人 > 板块负责人 > 事项负责人 > 参与人 |
| 资源层级 | 4 层：架构 > 看板 > 板块 > 事项 |
| 操作码 | 7 个：查看 / 新增 / 修改 / 删除 / 指派负责人 / 指派参与人 / 改可见内容 |
| 继承 | 沿「事项 → 板块 → 看板 → 架构」向上回溯，上级角色天然含下级能力 |
| 身份匹配 | 双口径——登录账号 + 绑定成员姓名同时匹配（存量数据里事项存姓名、看板存账号，两套都命中） |
| 兜底 | **fail-closed**：查不到归属就是看不见，不是"看不见就全放开" |
| 时效 | 每次实时查库、无缓存——"被移除负责人后权限立即失效"天然成立 |
| 拒绝形态 | 统一抛 `PermError` → HTTP 403 + 结构化错误体（含需要什么角色、实际什么角色） |

**可见性还有四层收窄**：架构授权集 → 账号级看板白名单（取交集）→ 板块级白名单 → 事项级过滤。关键设计是**把"看得见"和"管得了"分开**——负责人 = 管理权（可改基本信息），不是可见性开关。

**对管理者的意义**：搭一次架构，权限自动跟着走。调岗、设岗、组织调整只改架构树一处，全平台跟着变，不需要逐个模块改规则。

### 优势二：基于用户习惯搭建，灵活满足实际操作需求

**做什么**：不做"一刀切"的模板系统，而是"可配置 + 预置默认"。

**平台已经具备的实际能力**：

| 能力 | 实现 |
|---|---|
| **四层可复制** | 3 个复制接口覆盖四层对象：看板（含"整套复制"，连带板块 + 事项 + 子事项）、板块、主事项 / 子事项（子事项复制需重选所属主事项）；复制时归属部门、性质、状态、备注可重选 |
| **板块双重属性** | 每个板块带「性质（日常 / 专项）+ 年份 + 完成情况（未完成 / 进行中 / 已完成）」，天然承载"日常事务 vs 专项工作"的管理区分 |
| **看板归属配置** | 看板可挂到架构节点上（归属部门 + 部门节点 id），属性分日常 / 专项，状态分启用 / 封存 |
| **26 列单一数据源导出** | 字段集定义一次，导出 / 字段选择弹窗共用，不会漂移；每人可存自己的导出模板 |
| **筛选候选项自带权限过滤** | 人员下拉和周数下拉只出现**当前用户可见范围内**的事项负责人——越权事项的负责人根本不会出现在候选里 |
| **实时协同** | WebSocket 广播，事项变更实时推给其他在线用户 |

**对使用者的意义**：不改变"财务人怎么干活"的习惯，只是把原本在 Excel 和微信群里的动作搬进平台，搬进来之后多了留痕和联动。新人上手直接复制现成结构改，不用从零建。

### 优势三：化零为整，收束日常事务，集中平台统一管理

**做什么**：把散落在各处的财务日常事务全部收进同一平台——数据同源、权限同源、留痕同源。

| 原来在哪 | 收进平台的哪个模块 |
|---|---|
| Excel 台账 / 微信群 | 工作事项登记台 |
| 各人自己的记录 | 工作事项登记台（部门级 + 中心级双通道） |
| 会议纪要里的重大事项 | 重大财务事项汇总台账 |
| 手工统计的评优结果 | 标杆评优平台 |
| 每周手工汇总的周报 | 智能总结 |

**对管理者的意义**：能直接问出"这件事现在什么状态"，不用挨个问人。管理动作从"追人"变成"看板自带"。

### 优势四：功能可脱离 AI 独立使用，安全自主可控

**做什么**：把 AI 放在**增强位**而非**依赖位**。

| 模块 | 依赖 AI | 说明 |
|---|---|---|
| 工作事项登记台 | ❌ | 标准表单 + 流程，纯手工可用 |
| 各部门主页 | ❌ | 配置化页面 |
| 重大财务事项汇总 | ❌ | 台账 + 授权查阅 |
| 标杆评优平台 | ❌ | 投票 → 统计 → 公示 |
| 智能总结 | ✅ | **唯一一个**接 Agent 的模块 |

**安全设计**：

- 平台本体自建、可完全离线运行；服务器资源可向信息部申请并纳入公司管控（当前自建云服务器已验证这条路可行）
- 审计完备：`audit_logs` 记录操作人、IP、对象、详情、结果，仅管理员可查；`actions` 记录每个事项的操作轨迹
- 账号安全：登录失败 5 次冷却 180 秒、10 次永久锁定；密码加盐哈希；会话代数机制支持强制下线
- AI 侧单独隔离：智能总结通过独立 MCP Server 暴露，**默认只读**，写操作不在 Agent 侧开放

**对管理者的意义**：平台是资产不是依赖。关掉 AI 前四个模块照常运转；用了 AI，只是多一个提效工具，不多一份风险。

## 三、功能规划

### 功能一：工作事项登记台

**用途**：登记日常工作事项，工作留痕，统一管理。

**现状**：平台现有的事项数据完整（1263 条，字段齐全、周数全回填），但**入口是组织树下钻**——「架构 → 部门 → 看板 → 板块 → 事项」逐层点进去。想看"我这个月该办什么"必须自己翻。

**本次要做**：加一个**按角色聚合的登记入口**，与现有下钻入口并存。三个固定视角：

| 视角 | 看什么 | 实现口径 |
|---|---|---|
| **我的** | 我负责的 + 我参与的 | 复用现有筛选栏的负责人 / 参与人过滤，叠加当前用户权限范围 |
| **本部门** | 本部门的全部事项 | 按 `board_config.dept_node_id` 归集到架构节点，看板 / 板块 / 事项同源 |
| **全中心跨部门** | 跨部门协同事项 | 复用专项小组语义 + 参与人跨组判定，天然区分日常与跨部门事务 |

**核心能力**：

| 能力 | 说明 | 复用现有 |
|---|---|---|
| **双通道登记** | 部门独立事项 / 跨部门事项（跨部门挂专项小组节点） | ✅ 架构节点类型已有 `special` |
| **统一登记入口** | 一处登记，事项自动带周数、创建日期、负责人、参与人、截止日期 | ✅ 字段已齐 |
| **状态可追** | 状态、截止日期、进度实时可见；评论 / @提及 / 消息中心联动 | ✅ 已上线 |
| **留痕完整** | 创建人、创建时间、修改人、修改时间、操作日志全留痕 | ✅ 已上线 |
| **可导出** | 26 列导出 + 每用户自定义模板 | ✅ 已上线 |
| **按架构选人** | 登记时选人直接从组织架构树选 | ✅ 架构管理已上线 |

**为什么不是新建模块**：事项的数据模型、字段、权限、周数、筛选、评论、导出全都齐备，本期做的增量是**聚合视角 + 登记入口**，底层仍是同一份数据，不产生第二套事实。

### 功能二：各部门主页

**用途**：可灵活配置，根据各部门需求搭建自己的主页。

**现状**：页面容器已上线——顶部部门切换条、文化区（标语 / 职能介绍 / 团队合照 / 标杆模范）、事项统计区（总数 / 已完成 / 进行中 / 未完成 / 逾期 / 未分配负责人 + 负责人承担量排名），统计口径按当前用户可见范围过滤。**但内容全空**：`dept_profile` 仅 1 条测试占位记录，`dept_honors` / `dept_posts` / `notices` 均 0 条。

**本次要做**：把"容器"变成"可配置的内容页"。

| 能力 | 说明 |
|---|---|
| **内容模块化** | 主页由可勾选区块拼装：标语 / 职能介绍 / 团队合照 / 标杆模范 / 部门发文 / 事项概览 / 重大事项概览 |
| **自主配置** | 各部门自行勾选区块与顺序，不做统一模板硬套 |
| **按架构取数** | 数据范围由架构节点决定，自动绑定本部门事项，不手工配可见范围 |
| **发文带图文** | 已有 `dept_posts` 支持发图（单图 512KB 上限），适合部门风采 / 业务通报 |
| **编辑权限** | 内容编辑限管理员，内容展示面向全中心 |

**⚠️ 一个必须先解决的前置问题**：实测 7 个正式看板中，**6 个归属核算部、1 个归属财务中心**（另有 1 个副本归核算部），管理部 / 总账部 / 资金部 / 商务部**名下 0 个看板**。这四个部门的页面即使做好，事项统计区也必然是空的。**主页建设与看板归属补齐必须同步推进**，否则做出来是四张白页。

### 功能三：重大财务事项汇总

**用途**：作为重大事项台账，授权可供查阅。

**现状**：**表不存在**。重大事项散落在各业务看板里，与日常事项混在一起，没有汇总视图，没有单独控制知悉范围的能力。

**核心能力**：

| 能力 | 说明 |
|---|---|
| **统一台账** | 重大事项集中登记，一屏看全 |
| **分级标注** | 中心级 / 部门级 / 专项级，对应不同查阅范围 |
| **逐条授权** | 默认仅相关人员可见；扩大范围时**逐条授权**给指定人员 / 部门，不是一放全开 |
| **状态跟踪** | 登记 → 办结全过程，配合截止日期提醒 |
| **完整留痕** | 谁登记、谁授权、何时授权，全程审计可查 |
| **可导出** | 按需导出汇报材料 |

**为什么必须单独立表而不是复用普通事项**：重大事项的**敏感度**和**生命周期**都与日常事项不同——日常事项做完即止，重大事项往往跨年度跟踪、要向上汇报、要控制知悉范围。混在一个看板里，日常事项的宽松可见性会顺带把重大事项带出去。

**安全设计**：授权粒度强制到**单条事项**。这是硬要求，不能退让到模块级。

### 功能四：标杆评优平台

**用途**：彻底整合财务中心评优事项，平台收束投票及到公示的整个流程。

**现状**：`dept_honors` 表 **0 条**，主页的标杆区块和「小锦旗」样式已实现但没有数据来源。等于"奖品盒子有了，评奖过程没做"。

**核心能力**：

| 能力 | 说明 |
|---|---|
| **候选池管理** | 候选（部门 / 个人）由各部门提名，平台维护名单 |
| **投票** | 范围可指定（全员 / 指定部门 / 指定人员）、可设权重、单选或多选 |
| **结果统计** | 实时票数、得票率、排名，不需人工汇总 |
| **公示** | 结果在平台内公示（公告栏机制现成），公示期可设、可提前结束 |
| **归档** | 公示通过后自动写入 `dept_honors`，落到部门主页对应区块 |
| **历史留痕** | 每届候选名单、票型、票数、结果、公示时间全部存档 |

**流程闭环**：提名 → 投票 → 统计 → 公示 → 归档上主页，五步全在平台内完成。

**为什么值得做**：评优是最典型的"流程散在平台外"场景——发通知靠邮件、投票靠问卷、统计靠 Excel、公示靠群公告、最后手工贴主页。收进平台直接消灭这条链路。

### 功能五：智能总结

**用途**：平台连接 Agent，搭建智能工作总结或工作周报等 SKILL，提升工作效率。

**现状**：MCP 部署方案已有文档（`自建MCP_Server部署指南.md`），未实施。

**技术路径**：

```
FISP 平台（FastAPI + SQLite，109 个接口）
   ↓ 只读暴露工具
MCP Server（Streamable HTTP，SQLite WAL 模式，systemd 托管）
   ↓
Agent 客户端（WorkBuddy / 豆包 / Claude 等）
   ↓
SKILL（工作总结、周报、专项复盘…）
```

**可暴露的工具面**（全部基于现有接口，无需改主链路）：

| 工具 | 对应现有接口 | 用途 |
|---|---|---|
| 查某人事项 | `/api/cards` + 负责人过滤 | 生成"我的工作清单" |
| 查部门事项 | `/api/dept/{dept}/page` | 生成部门周报 |
| 查统计概览 | `/api/overview` | 进度、逾期、完成率 |
| 查筛选候选 | `/api/filter-options` | 人员 / 周数维度枚举 |
| 查操作轨迹 | `/api/cards/{id}/actions` | 事项进展描述 |

**关键安全约束**：

- MCP 侧**只读**：不开放写入 / 删除类工具，AI 无法通过提示注入改动业务数据
- SQL 白名单 + 物理只读连接（`mode=ro`）+ 服务端强制 `LIMIT` 分页
- 工具调用全量记日志，谁在什么时候调了什么工具、传了什么参数都可追溯

**为什么放最后做**：前四个模块是管理闭环的地基，AI 是锦上添花。地基不稳就接 AI，只会把不稳定放大。

## 四、平台底座与复用情况

本规划**不重建轮子**。逐项核对如下：

| 已有能力 | 核实结果 | 本规划中的用途 |
|---|---|---|
| 组织架构 4 类节点 + 9 类岗位 | ✅ `org_nodes` / `org_roles` 实际数据 | 全部模块的权限与数据范围基准 |
| 7 级权限内核 + 4 层可见性收窄 | ✅ `perm.py` 全部实现 + 端到端断言 | 事项、主页、重大事项的可见性判定 |
| 看板 → 板块 → 事项 → 子事项模型 | ✅ 263 板块 / 1263 事项实存 | 工作事项登记台的数据底座 |

## 五、实施路径建议

按"先收、再管、再评、后提效"的顺序推进，**每个阶段都能独立产生管理价值**。

| 阶段 | 内容 | 建议周期 | 阶段价值 |
|---|---|---|---|
| **P0** | **数据体检与清洗**（见下方风险节） | 3~5 天 | 后续所有模块的数据前提 |
| **P1** | 工作事项登记台（统一入口 + 三视角） | 2~3 周 | 日常事务收口，统一留痕 |
| **P2** | 重大财务事项汇总（台账 + 逐条授权） | 2 周 | 重大事项可控可查 |
| **P3** | 标杆评优平台（提名 → 投票 → 统计 → 公示 → 归档） | 3~4 周 | 评优流程全线上闭环 |
| **P4** | 各部门主页（内容模块化配置 + 看板归属补齐 + 全员填充） | 3~4 周 | 部门文化与业务展示统一 |
| **P5** | 智能总结（MCP Server + 周报 / 总结 SKILL） | 3~4 周 | 报表初稿自动化，人只校对 |

**顺序理由**：

1. **P0 必须先行**——数据不干净，后面每个模块都会踩坑（详见下方风险）
2. P1 是所有后续模块的数据入口，先收口才有统一数据可管
3. P2 授权模型复杂度高于 P1，但价值直接（对上汇报）
4. P3 流程最长、涉及面最广（全员投票），底座稳了再推
5. P4 含看板归属补齐（四个部门零看板），工作量比纯页面配置大
6. P5 依赖前四项的数据沉淀——没有结构化数据，AI 也总结不出东西

**资源需求**：

- **开发**：以现有代码为基线增量开发，主要工作在 `src/app/app.py`（后端接口 + 建表）与 `src/static/index.html`（前端页面），按现有双仓库规范提交
- **服务器**：现有云服务器（2 核 2G）已稳定支撑 70 人规模、1263 条事项、263 个板块，余量充足。建议同步向信息部申请公司内网服务器资源，做**双活或备份切换**，规避单点风险并满足数据不出内网的合规要求
- **配合**：P3 评优投票需要中心明确候选范围、投票规则、公示规则；P4 需要明确各部门的看板归属口径

## 六、风险与应对

### 6.1 数据体检发现的问题（P0 必做）

2026-11-08 生产库实测，发现四类需要先处理的问题：

| # | 问题 | 实测数据 | 影响 | 处理 |
|---|---|---|---|---|
| 1 | **架构任职表存在孤儿记录** | 168 条 `org_appointments` 指向 3 个不存在的节点（9001/9002/9003，各 56 条） | 权限范围派生时白算一轮；架构树展示与实际授权对不上 | 按真实节点重建任职关系 |
| 2 | **任职记录指向不存在的成员** | 1035 条 `member_id` 在 `team_members` 中无对应行 | 负责人 / 参与人身份匹配落空，可能出现"配了但没人管" | 清理或补齐成员 |
| 3 | **测试残留** | 架构节点 id=9865「测试」组（7 条任职）；`team_members.workgroups` 混有"测试"字样；账号 `testerB` / `accB` / `accC` | 目录树出现不存在的部门；成员归属统计失真 | 生产库清理 |
| 4 | **四个部门名下 0 个看板** | 7 个看板中 6 归核算部、1 归财务中心；管理部 / 总账部 / 资金部 / 商务部均为 0 | 这四个部门的首页 / 登记台 / 统计全是空的 | 归属口径由中心拍板后统一补齐 |

> 这四条都属于**数据与配置口径问题，不是代码缺陷**。但如果不先处理，"基于架构的权限"和"部门主页"两大优势在汇报现场会立刻被质疑——页面是空的、归属是错的。

### 6.2 推行类风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 各部门使用习惯不一致，推行阻力大 | 高 | P1 先找 1~2 个部门试点，跑通再推开；登记台支持部门自定义，先满足"够用"再谈统一 |
| 部门主页配置自由度太高，后期难维护 | 中 | 配置项做"模板 + 自定义"两档；超管可统一下发样式约束 |
| 评优投票涉及全员，需要中心层推动 | 高 | 需要中心明确规则与时间表；平台侧规则可配置，减少每次改流程的开发量 |
| 重大事项授权范围管不住 | 高 | 授权粒度强制到单条事项；敏感字段默认脱敏；授权变更全量审计 |
| AI 总结口径不可靠 / 泄露敏感信息 | 中 | MCP 只读 + 数据脱敏 + 生成物仅作初稿需人工确认；先在低敏感场景试点 |
| 服务器单点故障 | 中 | 向信息部申请内网资源做双活 / 备份切换；数据库每日自动备份保留 7 天（已有） |
