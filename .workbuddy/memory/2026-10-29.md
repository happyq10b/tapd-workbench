## 12:25 · 筛选功能扩展：「无负责人」+ 创建时间区间

需求：负责人筛选追加「无负责人」选项；追加创建时间区间筛选（可清空）；压缩搜索栏腾空间；
前后端 + 查询参数 + 数据库条件同步更新，并补边界处理。

### 关键设计决策
1. **哨兵值 `__no_owner__`**：空串已被「全部负责人」占用，不能复用；负责人是中文姓名，
   不会与 `__no_owner__` 重名。
2. **参数名 `created_start` / `created_end`**：⚠️ **不能叫 `created_from`** ——
   `cards` 表本身有 TAPD 原始字段 `created_from`（xlsx 导入用），同名必混淆。
3. **创建日期区间下推 SQL**：`substr(created,1,10) >= ?` / `<= ?`。
   用 substr 取日期部分比较 —— `created` 带时分秒（`2026-08-17 01:37:05`）时，
   直接跟纯日期做字符串比较会漏掉当天 00:00 之后的记录。
4. **全量行单独查**：`all_rows` 用于统计每个事项的子事项数（`sub_count`），
   不能被日期区间裁剪，否则子事项计数随筛选漂移。
5. **非法日期值忽略而非报错**：`_norm_date()` 返回 None → 该条件不参与筛选，
   避免一个脏参数让整个列表接口 500。

### 🔴 踩到的坑
- **`renderProgress()` 的 `if(os_.options.length<=1)` 判断失效**：加了静态 option「无负责人」后，
  `options.length` 恒 ≥2 → **负责人列表永远填不进去**。改用 `dataset.filled` 标记。
- **Chrome 的 `input[type=date]` 有固有内高**，不按 padding 走。工具栏因此从 59px 涨到 62/63px。
  解法：`.date-filter` 锁 height:33px（= .filter-select 实测高）、
  `.filter-date` 锁 height:31px（= .search-input 实测高）→ 工具栏回到 **59px，与改动前完全一致**。
- **`.filter-clear[hidden]` 需要显式兜底**：浏览器默认 `[hidden]{display:none}` 会被
  `.filter-clear` 的 `display:inline-flex` 覆盖（类选择器优先级更高）→ 清除按钮会常驻。
- **测试脚本装载**：只取最大的 `<script>` 块会报 `goLogin is not defined`
  （`goLogin`/`apiUrl`/`API_BASE` 在第一个块里）。必须 `blocks.join('\n')` 照浏览器顺序加载。
- **快照文件命名撞车**：同一秒内生成「改动前/改动后」两份快照会互相覆盖 → 文件名必须带来源标识。

## 16:55 · 组织架构模块：新模型（层级类型 / 岗位角色 / 多重归属）

需求：① 层级=中心→部门→常规小组，中心和部门均可设专项小组
② 岗位=小组(组长/组员)、部门(部门长/部门骨干)、中心(中心负责人/总经理/中心骨干)
③ 多重归属=一人可同时挂不同节点（一人多岗、多组织任职）
并要求输出数据模型、接口设计、校验规则。

### 为什么必须新建表（旧模型不够用）
旧 `workgroups` 只有一个 `leader` 字符串 → 无法表达「部门长+部门骨干」并存、
无法区分中心负责人/总经理；无节点类型 → 专项小组与常规小组不可分；
成员归属靠 `team_members.workgroups` 分号串 → 无外键无角色、改名即断链。

### 新模型三表
- `org_nodes`：节点（node_type CHECK center/dept/group/special，UNIQUE(parent_id,name)，
  wg_id 关联旧表作兼容视图）
- `org_roles`：岗位定义（node_type → 岗位，**unique_slot=1 表示节点内至多一人**）
- `org_appointments`：任职关系（node_id+member_id+role_key，
  UNIQUE(node_id,member_id,role_key) → 支持一人多岗与一人多组织）

### 🔴 关键坑：SQLite partial unique index 不能用子查询
最初写的是：
```sql
CREATE UNIQUE INDEX ux_org_unique_slot ON org_appointments(node_id, role_key)
WHERE role_key IN (SELECT role_key FROM org_roles WHERE unique_slot=1);
```
**SQLite 不允许 partial index 的 WHERE 引用别的表**（只能引用被索引的表自身）。
改为把唯一槽位岗位键写死：`IN ('center_head','gm','dept_head','group_leader')`。
**改 org_roles 的 unique_slot 集合时必须同步改这条索引** —— 两层判定会不一致。

### 层级规则的语义坑
`ORG_PARENT_RULES` 存的是**父节点类型**，不是节点类型。
第一版写成 `{0}` / `{'center'}` 混用，导致提示文案变成「部门的上级必须是『无』」。
拆成两张表更清晰：
- `ORG_PARENT_RULES`（本类型允许什么父）
- `ORG_CHILD_RULES`（本类型允许什么子）
前端 `ORG_CHILD_RULES` 与后端保持一致。

### 类型推断：部门不能因「是叶子」就判成 group
存量迁移最初用「有子节点→dept，叶子→group」，
结果管理部/总账部/资金部/商务部（都没有子组）被误判成 group。
**正确规则按业务层级**：`parent_id=0`→center；挂在中心下→dept；挂在部门下→group。

### 三类校验（都实测过）
- 层级完整性：类型合法、父类型匹配、不自指、**不挂到自己的后代下（防环）**、
  中心全局唯一、改类型/移动时校验子节点兼容性
- 角色唯一性：岗位须属该类型；唯一槽位节点内至多一人 →
  应用层 `_check_unique_slot()` 给中文提示 + DB partial index 兜底
- 多归属一致性：一人多岗/多组织均允许；`_org_sync_legacy()` 把新模型回写旧表
  （`workgroups.leader` ← 唯一槽位任职人；`team_members.workgroups` ← 组员任职），
  **旧权限逻辑 `_leader_boards`/`_group_boards` 零改动继续可用**

### 前端改造
架构管理弹窗保持「左树+右配置」两栏：
- 点节点行=看该节点岗位与任职；「编辑」=进编辑模式（职责分离）
- 节点行带类型徽章（🏛️中心/🏢部门/👥常规小组/🎯专项小组）

### 三、双滚轮的真实根因是 **flex 压缩**，不是「两条滚动条难看」

| 方案 | 结果 |
|---|---|
| `max-height+overflow:auto`（上一轮） | 容器自己一条滚动条 → **双滚轮** |
| 只改 `overflow:visible` | 表格被压扁 → **滚不动** |
| `overflow:visible` + `flex-shrink:0`（现） | ✅ 弹窗主体是唯一滚动容器 |

配套：`.tm-table-scroll{overflow:visible;flex-shrink:0}`、
`#teamModal .modal-body>*{flex-shrink:0}`、
`thead th{position:sticky;top:var(--tm-sticky-top);z-index:2}`，
`--tm-sticky-top` 由 `syncTmStickyTop()` 测量常驻筛选栏高度写入（避免表头与筛选栏重叠）。

## 14:35 · 架构管理任命后弹窗未及时刷新

### 根因：**带缓存的加载函数被当「刷新」用**
上一轮把架构树加载抽成 `ensureOrgTree()` 时带了**幂等缓存**：

而任命/免职成功后的「刷新」靠 `await openWgModal()`，
`openWgModal()` 内部调的**正是** `ensureOrgTree()` → 拿旧数据 → 只是重绘旧数据。

> 通用教训：**带缓存的加载函数被当作「刷新」用时，必须提供强制刷新通道。**

### 前端：canvas 自动压缩（重要）
`compressProfilePhoto(file)`：最长边缩到 **1200px**、输出 **JPEG 质量 0.85**。
理由：手机直出的照片常有 3~5MB，直接存 data URL 会把 SQLite 撑大。
压缩后通常落在 100~300KB。实测 2000x3000 → **800x1200**。

⚠️ **压缩时 canvas 先填白底再绘制** —— PNG 的透明区域转 JPEG 会变黑。
（`ctx.fillStyle='#fff'; ctx.fillRect(0,0,w,h);` 再 `drawImage`）

### 交互
- 照片区 `#profilePhotoBox`：点击上传 + 即时预览（`object-fit:contain` 保留比例，不拉伸）
- 右上角「清除」按钮（`clearProfilePhoto(ev)` 需 `stopPropagation`，否则会触发「点击上传」）
- 与头像、个人状态**共用「保存资料」按钮**，一次提交 `{avatar, photo, status_text}`

### 🔴 本轮踩到的坑
- **测试文件里的变量名是 `initSrc` 不是 `initDbSrc`** → 断言全部报 false
- **改了 SQL 写法会让旧断言失配**：`UPDATE users SET avatar=?, status_text=?`
  变成 `avatar=?, photo=?, status_text=?` 后，3 条旧正则不再匹配 →
  **断言要跟着实现一起更新**，否则出现"改了功能测试反而红"
- **headless 截图视口太窄会把弹窗右侧裁掉** → 误以为「清除」按钮没渲染。
  实测 `elementFromPoint(按钮中心)` 命中按钮 → 功能正常，
  改用 1020px 视口重截才看全。**截图视口宽度必须 ≥ 弹窗宽度**
- **canvas `toBlob` 出来的大图可能很小**（纯色图 2000x3000 只有 48KB）→
  压缩断言应验**尺寸**（最长边 ≤1200）而非体积
