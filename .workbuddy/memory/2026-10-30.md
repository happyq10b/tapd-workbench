# 2026-10-30 工作日志

## 16:30 · 看板与板块可见性失效专项（架构权限 filter 失效）

现象：普通用户登录后仍能看到**全部看板和板块**，架构管理里明明做了归属配置。

### 一、根因（4 处叠加 + 2 处口径不一致）

| # | 根因 | 说明 |
|---|---|---|
| 1 | **fail-open 空值语义** | `_dept_stage_boards()` / `_group_boards()` 用 `None` 同时表达「不收窄」与「不适用」。成员**无架构归属**时三层全返回 `None` → 可见集合 = 全部看板 |
| 2 | **账号白名单默认 `*`** | 新建账号 `allowed_boards='*'`（= 不额外收窄），与 1 叠加后架构过滤形同虚设 |
| 3 | **负责范围层恒为空** | 部门/中心节点的绑定读 `workgroups.boards`，该字段对部门/中心**恒为空** → 负责人的范围永远算成空集（`yh`/`wwn` 的 leader_boards 都是 `set()`） |
| 4 | **工作组白名单失效** | 白名单里混进了「归属部门自有看板」→ 集合永远覆盖前两层，本层**收窄不了任何东西** |
| 5 | **超管两套口径** | `user_allowed` 用「账号名 == 'admin'」，`require_admin` 用「角色 == 'admin'」→ `role=admin` 的账号（dsy）被架构过滤，却能调全部管理接口 |
| 6 | **读接口无可见性校验** | 评论 / 操作日志 / 子事项 / 子卡片树只有 `require_auth` → 「前端看不到、API 能读」 |

实测数据佐证（改前）：`testerB` / `accB` / `accC` / `zhangsan` / `lisi`
（无架构归属）→ `visible_boards = ALL`；`scj` / `tyl` / `wwn` 的
`group_boards` 恒等于全部 7 个看板（= 收窄失效）。

### 二、关键设计决策

1. **架构层改为永远返回显式集合（fail-closed）**，`None` 只留给超级管理员。
   「无架构归属」= 只剩公共看板（未归属部门 / 归属中心），而不是「不收窄」。
2. **超级管理员口径统一到 `is_admin()`**（角色口径，含内置 `admin` 账号）。
   `user_allowed()` 对 admin 直接返回 `(None, None)` —— 当前及未来新增的
   全部权限都不受架构过滤限制，新接口沿用 `require_admin` 即可。
3. **账号白名单降级为「收窄器」**：只能砍，不能凭空授予。
   授权入口统一为【架构管理】的任命（与既有文档 §6.5 的「取交集」口径一致）。
4. **节点绑定按类型派生**（`_node_bound_boards`）：
   中心 = 全部看板；部门 = `board_config.dept_node_id` 指向本部门的看板；
   小组 = `workgroups.boards` 手工绑定。修掉「负责范围层恒为空」。
5. **工作组层只取显式绑定**（`merged if bound else None`），不再把部门自有
   看板并进白名单 —— 混进去会让本层永远收窄不了。
6. **新增两个校验函数**：
   - `check_column_access(board_id, column_id, username)` → 写入不可见板块 403
     （接入 新建 / 修改 / 移动）；
   - `check_card_access(card_id, username)` → 按卡片定位看板做读可见性兜底
     （接入 评论 / 操作日志 / 子事项 / 子卡片树）。
7. **看板清单类接口按可见集合过滤**：`/api/boards`、`/api/board-config`、
   `/api/workgroups`、`/api/org/tree`、`/api/dept/{dept}/page`。
8. **WebSocket 广播按看板过滤**（`_ws_message_boards`）——
   不可见看板的卡片 id 不再通过实时通道泄漏。

### 三之二、性能回退与修复（重要技术决策）

改造后实测 `user_allowed()` 从 14~19ms 涨到 25~31ms（普通用户），
根因不在算法，而在**连接开销**：

```
1 conn + 1 stmt     1.153 ms      ← 新建连接 + 执行第一条语句
1 conn + 10 stmts   1.151 ms      ← 同一连接上跑 10 条：几乎免费
1 conn + close      0.062 ms      ← 光开光关很便宜
```

→ 瓶颈是**每新建一个连接的第一条语句**（Windows 文件锁开销），
不是语句本身。原实现 `dbq()` 每次查询都 `connect + close`，
一次权限判定要查 20 多个小表 → 白花 20~30ms。

**修法（不引入新框架）**：改成**每线程复用一个连接**（`threading.local`），
`dbq()` / `dbe()` 不再关连接；出错时 `rollback()`（连接是复用的，
必须回滚，否则未提交事务会留给该线程后续请求）。
两个批量导入接口（`/api/import`、`/api/import/xlsx`）原本 `finally: conn.close()`，
必须改成 `except → rollback`，否则会把线程的连接关掉。

顺带：`PRAGMA journal_mode=WAL` 是**数据库文件级**设置，只需设一次，
去掉每次连接都执行的写法。

**效果**（实测）：

| 指标 | 改前 | 改后 |
|---|---|---|
| `dbq('SELECT 1')` | 1.075 ms | **0.014 ms** |
| `user_allowed()`（普通用户） | 14~19 ms | **0.3~0.5 ms** |
| `GET /api/me` | 12.5 ms | **1.7 ms** |
| `GET /api/overview` | 13.4 ms | **5.7 ms** |

> ⚠️ 读新鲜度验证：Python sqlite3 在默认 isolation_level 下 SELECT 不开事务，
> 每次读都看到最新提交数据 —— `test_perm_scope.py` 直接改库的 `allowed_columns`
> 立刻被服务端读到，实测通过。

## 17:10 · 复制（四层）+ 周数维度

需求：看板 / 板块 / 主事项 / 子事项四层都能复制；复制后重新选择上级归属；
主事项与子事项新增【周数】维度（自然周）；筛选栏加周数多选。

### 关键设计决策

1. **四个层级 = 三个接口**：主事项与子事项共用 `POST /api/cards/copy`
   （用源记录有没有 `parent_id` 区分层级），另加 `POST /api/boards/{id}/copy`
   与 `POST /api/columns/copy`。
2. **只复制本级、不复制下级内容**（复制看板不带板块与事项、复制事项不带子事项目录）。
   理由：需求里"复制后重新选择上级归属"意味着归属要显式确认，级联复制会
   "悄悄改归属"；而且级联后副本标题全带「（副本）」反而不堪重负。
   → 这一点已在弹窗提示里写明，若用户要级联再加。
3. **副本 = 全新记录**：`copy_from` 字段记来源（boards/board_columns/cards 三张表都加），
   标题默认「原标题（副本）」可编辑，同名冲突自动加序号。
   运行态字段一律重置：状态=未完成、完成时间清空、创建人/创建时间=当前账号、
   置顶/锁/评论/附件/子事项目录不复制。
4. **看板复制仅管理员**：看板的新建与配置本来就是管理员级，复制同级别。
5. **归属重选的选项来源 = 已按权限过滤的接口**（这是需求里"重点校验权限过滤"的落点）：
   - 目标看板 ← `/api/me` 的 boards
   - 目标板块 ← 新增 `GET /api/boards/{id}/columns`（复用 `visible_columns`）
   - 所属主事项 ← `/api/cards`（列表接口本身已过滤，且只取主事项）
   服务端再校验一遍（`check_card_access` / `check_board_access` /
   `check_column_access` / `perm_pass`），越权一律 403。
6. **周数按 ISO 周算**：`date.isocalendar()` → `2026年第44周`。
   自然周 = 周一~周日；归属年按 ISO-8601（该周**周四**所在年份），
   所以 `2027-01-01` 属于 `2026年第53周` —— 不要用「年内第几天/7」的土办法。
   老数据由 `init_db()` 幂等回填（Python 循环，不用 SQL 的 strftime 拼周数）。
7. **列表列位置**：`负责人 / 周数 / 创建日期 / 截止日期` —— 周数在创建信息列之前。
   ⚠️ 需求原文写的是「位于【创建人】字段之前」，但**列表里并没有【创建人】列**
   （只有创建日期；创建人只存在于板块弹窗的只读输入框）。已按「创建信息列之前」
   实现 —— 即周数排在【创建日期】之前，与该列同款样式（定宽 + nowrap + 省略号）。
8. **主/子事项对齐**：`.fcols` 与 `.sub-node .fcols` 的 `grid-template-columns`
   （`166px 118px 146px 178px`）与容器宽（648px）**必须完全一致**，
   否则父子两行的字段列起点会错位。已用 headless Chrome 量过实际计算样式。

### 🔴 踩到的坑

- **测试夹具残留会污染其它用例**：经接口新建的记录 id 不含前缀（卡片 `NC…`、
  看板 `BCP…`），只按前缀清理会残留；残留卡片会让「按 cards 派生的看板」
  继续可见 → 可见性测试突然多出一个看板，误判成权限逻辑坏了。
  清理必须同时按 `board_id` / `copy_from` 删。
- **CDP 测试脚本的三连坑**（`ops/ui_check_copy.py`）：
  ① 复用旧 Chrome profile 会带上 localStorage 旧状态 → 每次 rmtree 重建 profile；
  ② 固定 sleep 不可靠 → 轮询等 `.item-card` 出现；
  ③ `Array.prototype.slice.call(new Set())` 返回 `[]`（Set 不是类数组）→ 用 `[...SET]`。
- **JS 少一个冒号就整段 SyntaxError**：`mainWidth:getComputedStyle(f).width:''};`
  多了个冒号 → 整段脚本解析失败，CDP 只报 "Unexpected token ':'"，
  看起来像"元素查不到"。排查时先把测量脚本单独跑一遍。
