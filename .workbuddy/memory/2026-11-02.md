③ 删除多余的「全部负责人」筛选；④ 缩小人员/周数筛选框，日期区间与其它筛选同行。

### 根因与修法

**① 浮空圆点** —— 那是「个人状态栏」的状态点 `.my-status-bar .ms-dot`。
个人状态栏 HTML 带 `hidden` 属性（状态文字为空时 JS 设 `bar.hidden=true`），
但 CSS `.my-status-bar{display:flex}` **优先级高于浏览器 UA 对 `[hidden]` 的
`display:none`** → hidden 形同虚设 → 状态文字被 `.ms-text:empty{display:none}`
藏掉，只剩圆点孤零零浮在左上角。
修法：补 `.my-status-bar[hidden]{display:none}`。
💡 通用经验：元素同时写 `display:flex/grid` 又用 `hidden` 控制显隐时，
**必须**补 `[hidden]{display:none}`（项目里已有 8 处同类兜底）。

**② 标题** —— `.tb-band-title` 改 `font-size:13px;font-weight:700`，
竖条 `::before` 同步加高到 13px。「板块」→「可选板块」。

**③「全部负责人」下拉下线** —— 它与「👤 人员」都作用于 owner 字段，功能重复。
- HTML 删 `<select id="ownerFilter">`；JS 清 `renderProgress()` 的动态填充、
  `reload()` 的 `ps.set('owner')`、`syncFilterHint()` 的负责人分支；
- **「无负责人」不能跟着丢** → 并入人员面板作固定第一条候选项，
  哨兵 `__no_owner__`（前端常量 `OWNER_NONE` + `personLabel()` 显示中文）；
- 后端 `/api/cards` 的 person 分支扩展为识别 `__no_owner__`
  （`want_none` → 匹配 owner 为空/纯空白）；owner 参数保留给外部 API 调用方；
- ⚠️ 架构树回填要**排除** `__no_owner__`（不是真实人员，永远匹配不上），
  但勾选人员时要**保留**它。

**④ 筛选栏同行** —— `.toolbar-left` 改 `flex-wrap:nowrap`；
`.cf-field` 150→104px（max 420→220）；`.cf-input` min 110→52px；
`.filter-date` 140→122px；`.date-filter` 加 `flex:0 0 auto`；
`.search-input` min 140→100 / flex 1 1 150px / max 280→230；
`#filterHint` 加 max-width 260 + 省略号。窄屏 ≤1024px 恢复 wrap 防溢出。
实测 1600px 视口：6 个子元素中心线 y 完全一致（rowSpread=0），不与右侧按钮组重叠。

### 🔴 踩到的坑

- **测试写死日期 → 假性失败**：`test_copy_week.py` 写死「副本周数 = 2026年第44周」，
  但副本 `created` 取**服务端当前时间** → 过了那一周必失败（今天 11-02 已是第 45 周）。
  修法：动态算 `week_label(datetime.now())`；只有**夹具**固定数据才写死周号。
- **断言「源码里没某词」会被注释误伤**：注释里提到「全部负责人」也命中。
  改为针对**元素结构**断言（`<select class="filter-select" id="ownerFilter"`）。
- **CDP 测「是否同一行」要用中心线**（`y + height/2`），不能直接比 `y` ——
  不同高度控件 `align-items:center` 对齐时 y 天然不同。
- **`setLet` 用 JSON 序列化传不了 Set**：`vm.runInContext("PERSON_SEL=new Set([...])", sandbox)`。

## 10:00 · 周数排序修正 + 人员筛选入口彻底转移到树状图

### ① 周数排序

**根因**：用的是**字符串排序**（`sorted(weeks)` / `.sort()`）。
字典序下比较到 `'3'` 与 `'周'` 时 `'3'` 更大 → 「第3周」被排到「第31周」**后面**，
列表变成「第31周、第33周、第3周、第44周、第4周」这种乱序。

**修法**：折成组合整数再比 —— 「2026年第41周」→ `2026*100+41 = 202641`。
- 后端 `week_sort_key(v)` → `(年, 周号, 0, 原串)`，非标准标签排最后
- 前端 `weekSortKey(v)` → `parseInt(y)*100+parseInt(w)`
- ⚠️ **四处排序点都要改**，漏一处就"接口排对了、面板又乱"：
  后端 `/api/filter-options`、后端 `/api/cards` 的 week_options、
  前端 `paintFilterCombos()`、前端 `renderWeekFilter()`

## 10:40 · 修复搜索框无法输入中文（IME 兼容）

现象：树弹窗搜索框打不出拼音 —— 输入第一个字母就没反应 / 拼音上不了屏。

### 根因（三个叠加）

**① 每次输入都重建整个面板 DOM**
`tpSearch()` → `renderTreePick()` → `p.innerHTML = ...` 重建工具栏+搜索框+树+底栏。
→ 输入框 DOM 节点被销毁重建 → 焦点/光标丢失；
→ 更致命：**IME 的拼音组合状态绑定在原生 input 元素上**，元素被替换后组合被打断
→ 表现为「只能打第一个字母」。
修法：拆出 `renderTreePickBody()`，只替换 `#tp_body` 的 innerHTML，搜索框节点不变。

**② 组合期间用拼音过滤 → 树被清空**
IME 组合期间 `input.value` 是**拼音字母**不是汉字，用它过滤 → 匹配不到人 → 树空。
修法：`compositionstart`/`compositionend` + `input` 的 `isComposing` 双重判定，
组合期间完全不刷新树，`compositionend` 拿到汉字后再过滤。

**③（隐蔽坑）内联事件处理器访问不到顶层 `let` 变量**
最初用内联属性 `oncompositionstart="tpSearchCompositionStart()"`，
标志位写作 `let TP_COMPOSING=false`。
⚠️ **顶层 let/const 不在 window 上**，而**内联 handler 的作用域链是
element→form→document→window，不经过 script scope** → 处理器里赋值抛
ReferenceError → 标志永远设不进去 → 组合期照样过滤 → 树空。
**极具迷惑性**：`Runtime.evaluate` 里能读到/改到该变量（走 script scope），
所以单元测试全绿、真实用户路径却是坏的。
修法：标志位用 **`var`**（顶层 var 挂 window）+ 事件改 **`addEventListener`** 绑定。

### 顺带改进的搜索体验

- **自动展开到命中路径**：`tpSubtreeHasMatch()` —— 搜索时子树有匹配的节点自动展开，
  否则命中的人藏在折叠容器里看不见
- **无匹配空态提示**：显示「未匹配到「xxx」的人员」而非留一片空白
  （判定要看 treeHtml 里有没有人员条目 —— 节点行在无匹配时仍会渲染，treeHtml 始终非空；
  也不能查 body，此刻 body 还是旧内容）
- **关键词未变则跳过重绘**：IME 的 compositionend 后常会补一个 input 事件

### 🔴 踩到的坑

- **用 CDP 手工 `dispatchEvent` 模拟 IME 测不准**：真实 IME 选词上屏会**替换**
  input.value，而 CDP 的 `imeSetComposition` 不替换 → 手工 dispatch 的
  compositionend.data 与真实行为不同。必须用 `Input.imeSetComposition` +
  `Input.insertText` 走真实输入管线。
- **「组件存在」≠「组件可用」**：顶层 let + 内联 handler 的组合在
  Runtime.evaluate 里完全正常，只有真实用户路径才炸。

## 16:20 · 术语纠正（看板≠板块）+ 看板/板块 ACL + 空板块清理

用户提四项要求：① 术语（"可选板块"其实是看板）② 看板级 ACL（owner+participants）
③ 板块级 ACL ④ 空板块/空看板清理。

### ① 术语：先查清数据模型再改

层级是 **部门 → 看板(boards 表) → 板块(board_columns 表) → 事项(cards 表)**。
前端 `#tbBoards` 渲染的是 `ME.boards`（=boards 表=**看板**），标题却写「可选板块」
→ **标题与内容不符**是术语混乱的源头。改了 30+ 处文案 + 核心函数注释。
保留没改：板块弹窗、年份筛选、展开/折叠板块按钮（那些「板块」是对的）。
**判定口径写进注释**：`ME.boards`=看板，`board_columns`/`column_id`=板块。

### ② 看板 ACL 的根因（重要）

`boards.owner` 字段**早就有**，但 ① 从没写入过（7 个看板全空）
② **从没参与过任何权限判定** —— 权限链只有「架构归属→账号白名单→板块白名单」三层。
而且**根本没有 participants 概念**。所以"看板权限隔离"无从谈起。

**关键设计决策**：
- 未配置 ACL（owner/participants 皆空）→ **不额外收窄**（否则现有 7 个看板当天锁死系统）
- 配置了 ACL → 仅 owner/participants 可见，且与既有链**取交集**（fail-closed）
- 🔴 **只在 `user_allowed()` 一处接入** → 所有读接口都从它取 (boards, columns)
  再走 filter_rows/visible_columns → **不可能出现"某接口忘了过滤"的漏网路径**
  （这是本条最重要的工程决策，用户明确要求"不得因任何遗漏路径而泄露"）

实测 8 个入口全部过滤：/api/me、/api/boards、/api/boards/{id}/columns、/api/cards、
/api/cards?q=（搜索）、/api/overview、/api/dept/{dept}/page、/api/filter-options

### ③ 板块 ACL：所属看板仍可见，该板块隐藏

`_acl_filter_columns` 要**预取「看板→全部板块 id」**（否则 227 板块 → 227 次查询，N+1）。
ACL 只能再收窄：白名单排除的板块，ACL 命中也救不回来。

### ④ 数据清理

两处：`cleanup_empty_columns_and_boards()`（运行时，删事项后调用）
+ `ops/cleanup_empty.py`（一次性全量，幂等，`--dry-run`）。

**判定按 `column_id` 匹配**（不是 column_name —— 后者改名就变）。
**安全约束**：板块全空但还残留孤儿事项的看板**不删**（否则连带删数据）。
生产库现状：0 空板块、0 空看板（dry-run 已验证）。
